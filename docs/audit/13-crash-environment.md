# AUDIT 13 — crashes, environment, mod interaction, unknown-unknowns

**Surface**: everything outside the mod's own logic that can end a session or hide a fault — the Rockstar crash-dump folder and what it actually contains, the documented crash families and what in ARS could still reach them, the SHVDN build the mod is compiled and run against, the other ASIs and scripts installed beside it, the assumptions every other audit inherits (exceptions caught, reload clean, one instance), and the places ARS's behaviour depends on this machine.
**Date**: 2026-10-25.
**Build audited**: deployed `Scripts\AutosportRacingSystem\build-number.txt` = **958**; source `HEAD` = **`9bdb9af`**. Live evidence: `Log.log` one race `13:26:23`–`13:29:28`, `ScriptHookVDotNet.log` of the same launch, `asiloader.log`/`ScriptHookV.log` of the `11:25` launch, **152 crash-dump files** (2026-03-05 → 2026-10-23) in `%LOCALAPPDATA%\Rockstar Games\GTAV\CrashLogs`, and the Windows Application log.
**Method**: read-only. No edits, build, deploy, commit or game run. Three sources are binaries rather than source: every `.dmp` was parsed with a scratch user-minidump reader (header, exception stream, module list — recipe in "How to re-run the census"), the four managed-exception dumps were opened in **`cdbX64.exe` 10.0.29617.1000** (already installed at `%LOCALAPPDATA%\Microsoft\WindowsApps\`, contrary to the record's "install WinDbg" note) with `!pe -nested`, and `SHVDN.ScriptDomain` was decompiled out of the live `ScriptHookVDotNet.asi` (`ilspycmd`).
**Verdict**: **two blockers.** (1) The wheel-pointer scan pair is the only memory scan in the mod with no miss path, and a miss turns a read of `*(vehicle + 0)` into a wheel array and an unbounded dereference loop over whatever count the same miss produced. (2) **Three of the four fatal managed-exception dumps are a `ThreadAbortException` landing in ARS code during a script abort, followed by an `ObjectDisposedException` on SHVDN's own domain lock — i.e. reloading the scripts is a game-crash path, and the record says reload is free.** The rest is record-keeping: the crash inventory describes **3 of 151** parseable dumps and undercounts its largest family by 8×, and the two logs that would let anyone separate ARS from the loader are destroyed by the next launch. On the card's central question, the **newest** crash (2026-10-23) is now attributed from its own stack: `VSLooseStream.asi` → `GTA5` handling parse → fault, with no script anywhere in the frame.

### What the dumps' own stacks say (`cdbX64.exe`, `.ecxr; k`)

- **Newest dump, `0bd8b268…`, 2026-10-23 15:06:09, `GTA5+0xF0977A` read 0x8** — the innermost frames are `GTA5+0xf0977a` ← `GTA5+0xf853c8` ← **`VSLooseStream` (nearest export `VSLooseGetEntryInfo`+0x5541)** ← **`VSAssetWatch`+0x2451** ← `VSAssetWatch`+0x154f ← `GTA5+0x135456c` ← three more `GTA5` frames ← `kernel32!BaseThreadInitThunk`. The chain runs from the game's thread through the asset-watch hook into the loose-stream reader and back into the game's handling parser. **No managed frame, no `ARS.dll`, no `ScriptHookVDotNet` anywhere in it** — this one is the loader's end to end, and it is also the crash that happened two days before this audit.
- **`0xE0434352` family, three of four dumps** (`ceb5b698…` 2026-09-10, `86472633…` 2026-08-19, `ec37e621…` 2026-09-11) — `!pe -nested` on `ceb5b698…` prints **two** exceptions on one thread: `System.Threading.ThreadAbortException` — *"Thread was being aborted."* — with its innermost frame at `ARS!Unknown+0x35c0`, and then `System.ObjectDisposedException` — *"Cannot access a disposed object."* — thrown from `System.Threading.ReaderWriterLockSlim.TryEnterReadLockCore` inside `ScriptHookVDotNet!Unknown+0x54`, unhandled, out of `KERNELBASE!RaiseException`. The other two show the same two-part shape with ARS at `+0x3f02` and `+0x2510`. **Read: SHVDN aborted the script thread while ARS was executing, the abort's own unwind called a disposed `ScriptDomain`, and the game died on the reporting path — not on an ARS exception.**
- **`0x136AF5B` breakpoint family** (`afcac845…`, 2026-10-10) — a bare `int 3` (opcode `cc`) with `rcx = 0x00000000ffffffff`, `rdx = 0`, `r14 = 0x0ffffffffffffff0`, and a stack of nine frames that are **all `GTA5`** down to `kernel32!BaseThreadInitThunk`. A deliberate trap in game code with a null/-1 argument; no mod frame. What the trap is *for* still needs `GTA5.exe` symbols, which do not exist publicly.
- **`793c156a…` (2026-07-29)**, the fourth CLR dump, is a different shape: `ScriptHookVDotNet!DomainBoundILStubClass.IL_STUB_ReversePInvoke` — a native→managed reverse P/Invoke, no ARS frame in the walked stack. It is the one member of the family that does not fit the abort pattern.

## What would separate ARS from the loader

The record's answer to "could ARS have caused this?" was "no dump shows a mod module". That is true and useless: a managed fault cannot name `ARS.dll`, because it surfaces as `0xE0434352` raised inside `KERNELBASE.dll`. The **stacks** decide it, and `cdb` reads them on this machine:

1. **A managed exception is decided by `!pe -nested`, not by the module list.** Three of four have ARS in the stack — not as the thrower but as the frame the `ThreadAbortException` landed in — and the fatal exception is SHVDN's own `ObjectDisposedException` on a disposed domain lock. The fourth (`793c156a…`) is a reverse P/Invoke with no ARS frame.
2. **A game-side fault is decided by the frames above it.** The newest crash runs `GTA5` ← `VSLooseStream` ← `VSAssetWatch` ← `GTA5` — the loader, proven. The breakpoint family is nine `GTA5` frames and nothing else. If a future `0x652263`-shaped dump ever showed an `ARS` frame, that would be the first hard evidence against the mod; none does.
3. **The 3 `VSAssetWatch.asi` and 2 `VSLooseStream.asi` dumps fault *inside their own modules*** on 2026-09-21 — the loader stack can crash the game with no script involved, from the other direction.
4. **Time correlation is the cheap test and this install has lost it** (R5): `ScriptHookVDotNet.log` prints `Instantiating script ARS.ARS` with a timestamp (today `13:26:23`); a dump whose `Header.TimeDateStamp` precedes that line on the same launch proves no ARS code ran. Copy both logs **before** the next launch.
5. **`crashcontext.log`** carries game state at the last crash only — the record used it to prove the `0x6057E1` crashes happened before the player existed (`:474`). It is overwritten by the next crash.

## Blockers, ranked

1. **B1 — the unguarded wheel-pointer pair** (`AutosportRacingSystem.cs:3042-3089`). One guard, and it is the difference between "the cars read zero grip on a new game build" and "the game faults inside the mod's read path with no log line". The only pure code defect on this surface.
2. **B2 — the abort/reload crash** (`!pe -nested` on three dumps). Nothing in ARS can stop SHVDN from aborting a thread, but two things must change before the tag: the record must stop calling reload free (the build→reload→drive loop in `AGENTS.md` and the `Insert` advice in `AGENTS/AGENTS-SHVDN.md:93` both need the caveat), and `BuildRosterFromEnum`'s `Script.Yield()` (`:2741`) should go or be gated, because parking the script thread is how a tick reaches the 5 s timeout that triggers the abort.

## How to re-run the census

The reader is ~60 lines of Python over the user-minidump structures: header (`MDMP`, `NumberOfStreams` at `0x08`, `StreamDirectoryRva` at `0x0C`, `TimeDateStamp` at `0x14`), directory entries of `(streamType, dataSize, rva)`, the **exception stream** (type 6: thread id, `ExceptionCode`, `ExceptionAddress`, `ExceptionInformation[15]`) and the **module list** (type 4: `BaseOfImage`, `SizeOfImage`, then a UTF-16 name at `ModuleNameRva`). Resolve `ExceptionAddress` against the module ranges for `module+offset`; `ExceptionInformation[0]` is the access type (0 read / 1 write / 8 execute). The live script is `C:\Users\Usuario\AppData\Local\hermes\cache\scratch\dumphead.py`; the folder is `%LOCALAPPDATA%\Rockstar Games\GTAV\CrashLogs`. **Sort by each dump's own `TimeDateStamp`, never by filename** — alphabetical order is not chronological and the two disagree on every family here. For a stack: `cdbX64.exe -z <dump> -y "" -c ".ecxr; k; q"`; for a managed exception: `.loadby sos clr; .ecxr; !pe -nested`.
