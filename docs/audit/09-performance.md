# AUDIT 09 — performance: allocations, per-tick scaling, logging, native calls

**Surface**: everything that runs while a race is live — `ARS.OnTick` (`AutosportRacingSystem.cs:1802`), the per-frame racer pass `Racer.ProcessTick` (`Racer.cs:3403`), the AI core pass `Racer.RunTimedCore` (`Racer.cs:3660`) with the batch that paces it (`AutosportRacingSystem.cs:2158-2174`), the periodic racer scans (`UpdateRivals`, `UpdatePressure`, `UpdateRivalInfo`, `UpdateCornerRequirements`), the wheel-memory helpers in `AutosportRacingSystem.cs:3004-3257`, the HUD and leaderboard draw path, and `Log`.
**Date**: 2026-10-25.
**Build audited**: **958** (`scripts/AutosportRacingSystem/build-number.txt` → `958`), source `HEAD 9bdb9af`, `src/` 14,011 lines. Session evidence is the live `Log.log` (`scripts/AutosportRacingSystem/Log.log`, 273,091 B, 13:26:23–13:29:28, **14 racers**, one track: 2,350 → **2,405 route nodes** after densification, **9 corners**).
**Method**: read-only. No edits, build, deploy, commit or game run. Two classes of fact were taken from binaries: every "is this property a native call" claim is decompiled from `libs/ScriptHookVDotNet2.dll` with `ilspycmd`, and the counts per call site are counted in the source, not estimated.
**Verdict**: **no blocker.** Nothing on this surface is unbounded, quadratically wrong in the live population, or capable of killing a tick on its own. What it is: **one always-on per-frame cost that dwarfs every other one** (the leaderboard, ~992 native calls per frame), **a per-core-tick block that re-queries engine constants fixed at spawn** (~5,400–7,200 native calls/s at 30 cars), and **allocation churn concentrated in the wheel-memory helpers** (~2,200 `List` allocations/s). All of it is reducible to near zero without changing a driving law, because none of it computes a decision — it recomputes facts.

Basis for every rate below: **60 fps**, `n = 30` AI racers, both stated because the numbers scale linearly with frame rate. The AI core pass runs **6 cars per frame** (`AutosportRacingSystem.cs:2164-2172`, `count = clamp(Racers.Count, 1, 6)`), so each car gets a core tick every `ceil(n/6)` frames — **12 core ticks/s per car at 30**, 25.7/s at the 14 the audited session ran.

## The top three, ranked by cost per tick

Ranked by native calls per second at 30 cars and 60 fps, which is the same ordering as per frame because every term is linear in frame rate.

1. **P1 — the leaderboard, 992 native calls per frame (~59,500/s).** More than the entire AI side of the tick combined, for a board whose underlying values update at 5 Hz. It is also the cheapest to fix: the strings and the ordering already exist on a 200 ms tick (`:2208-2210`), so caching them there and drawing from the cache removes ~98 % of the cost with no behavioural change. This is the one item worth doing before anything else on this list.
2. **P2 — per-core-tick engine constants, 15–20 natives per car per core tick (~5,400–7,200/s).** `Car.UpVector` alone is 5 calls where one `Rotation` read would do; `Model.GetDimensions()` is a native plus two unmanaged allocations for a constant; `HasBone` is a native for a model fact. Caching the model facts at grid build (where the wheelbase, dimensions and PI are already read) and reading `Rotation` once per core tick would take this to 3–4 natives.
3. **P3 — `UpdatePressure`'s rival scan, 3,480 natives/s, 1,740 of them the same value.** A one-line hoist. It stays third because the remaining 1,740 are the genuine per-pair read; making the scan cheaper than that means widening the refresh interval or sharing one pass with `UpdateRivals`, which are design changes rather than fixes.

Next in line: **P6** (1,800/s) and **P8** (1,800/s) are each a moved or guarded line; **P7** (900/s) is a call moved inside the gate it already has. **P4** sits outside that ranking on purpose — 2,160 allocations/s is gen0 garbage rather than native dispatch, so it costs less than the three above, and it is the only item that needs a signature change (`GetWheelPtrs` writing into a caller-supplied buffer) rather than a line moved.

## What is *not* wrong here

Worth recording, because this is the class of audit where a future session optimises the healthy parts:

- **No LINQ on the AI core path that allocates.** The racer tick carries three chains: `:2558-2561` (ChillOut only) and `:2622` (`FirstOrDefault`, only when `RubberbandingPct > 0` — `ComputeRubberBandFactor` returns at `:2619` otherwise) are behind a mode; `:2572` (`Brain.Rivals.Any(...)`) runs on every core tick but its lambda captures nothing, so the compiler caches the delegate and it iterates the ≤4 rival slots without allocating. The LINQ that *is* unconditional and *does* allocate lives in the draw path (`:2352`, per frame) and on the 1 Hz field scans (`:441-445`), not in the driving path.
- **`Function.Call` allocates nothing.** Decompiled: SHVDN supplies 16 non-`params` overloads up to 16 arguments, each using `stackalloc` and returning through `ObjectFromNative<T>` — no boxing, no array, for a `Vector3` return either. So the cost model here is dispatch, not garbage; the allocation findings are all in ARS's own code (P4, P5, P11).
- **`new Vector3(...)` is a struct** and appears throughout the draw path; it is not an allocation and is not counted anywhere above.
- **The batch pacing does what its comment says** (`:2162-2163`): 6 cars per frame, `10 / (Racers.Count / count)` clamped at 1 ms, so a core tick per car lands every `ceil(n/6)` frames. At 30 cars that is 12/s each and 360/s total, which is the denominator every core-tick figure above uses.
- **The wall fold, the rival lift and the throttle/brake composition read only published fields** (P13). The per-tick design of those is already the one this audit would recommend.

## Not verifiable read-only

- **Any wall-clock figure.** Every rate above is a count × a stated frame rate. Nothing here was profiled in game; SHVDN native dispatch is not instrumented and no timing appears in `Log.log`. The relative ordering is safe (it is arithmetic on counts), the absolute milliseconds are not claimed.
- **P8's fix.** Whether the handbrake write can be skipped depends on whether the engine resets the flag per physics step. The code makes that claim for a different field (`:3741-3743`) and makes none for this one — so it is a drive, not a read.
- **Whether a 5 Hz leaderboard is acceptable to the eye.** The data's own rate is 5 Hz (`:2210`), so no information is lost, but "the number ticks rather than flows" is a driver's judgement, not a code one.
