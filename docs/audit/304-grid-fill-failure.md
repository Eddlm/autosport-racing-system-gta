# AUDIT 304 — the grid could not be filled (the Max PI Deviation refusal)

**Surface**: the AI grid-fill path — the Race menu's *Build Grid* / *Start Race* entries, `InstanceGrid`, `FillCachedCandidates`, `VehicleSelector.SelectClosestByPace`, the **Max PI Deviation** window, `LoadGrid` / `SpawnRacer` / `GridBuilder.Place`, and every message the empty-candidate case raises — against the three `No vehicles within N PI of the target` Errors of 2026-10-25 at 23:46:00, 23:46:18 and 23:46:23. This report closes the item audit 200 listed as untriaged (`docs/audit/200-audit-0.9.0.md` §4.8).

**Date**: 2026-10-26.

**Build audited**: deployed **1105** — `Scripts\AutosportRacingSystem\build-number.txt` = 1105, installed `ARS.dll` byte-identical to `bin/Release/ARS.dll`, sha256 `0e3b2d13ec0f7b09eedc347f3cb16369174e1b7c709e7745baae2a6a8a261a65`, source `HEAD 6a1fcbc`. **The log was written by build 1092** (`HEAD e851a09`, per audit 200); `git diff e851a09..HEAD` over `AutoSportRacingSystem.cs`'s grid region and `VehicleSelector.cs` is **0 lines**, so every source line cited below is the code that failed last night. The live `Settings\Menu-*.ini` and `Log.log` (mtime 23:50, not truncated since) were read as found.

**Method**: read-only — no edit, build, deploy, commit or game run. Instruments: the source at `6a1fcbc`; the live `Log.log` (1370 lines — with the shipped `LogLevel = Error` only forced lines and Errors are written, which is itself part of the evidence); the live `Settings\Menu-Race.ini` (mtime **23:46:29**, i.e. between the last failure and the successful fill) and `Menu-Settings.ini`; `git` history. **VERIFIED** = read in the code / log / ini, or arithmetic on those. **PROBABLE** = one step rests on state no artefact records. Nothing here is driver-verified.

**Verdict**: the three Errors are the new **Max PI Deviation** window refusing the grid as `TEST-PLAN.md:438` specifies ("A window nothing fits must give the explicit no-vehicles-in-window error rather than a silent solo grid") — and that whole batch sits under TEST-PLAN's **"NOT DRIVEN — compile-verified only"** heading, so last night was the path's first in-game exposure. The refusal is the design; what the incident exposes is everything around it. The window's only advertised remedy — "widen Max PI Deviation" — **could not work**: the menu ladder is `Off, 2, 4, 6, 8` and that night's target sat **16.46 PI** from the nearest model in the pool, so every rung failed, and the remedies that did work (Off, or a target nearer the fleet) appear nowhere the player was pointed. The UI pointed at the wrong folder. The one line that shows the counts is Info-level, invisible at the shipped `LogLevel = Error` — the very line the test-plan item tells a tester to read. And the same Error line is also raised by three other situations, two of which make it **false**: a solo grid (`Grid Size 0`, a shipped choice) prints it on every Build Grid, and the startup fill prints it at script load before any grid was requested.

## The incident, reconstructed

Every timestamp below is a live `Log.log` line or a file mtime.

- **23:41:57** — script init into a race in progress: `Pace span 120.2..587.8 over 472 models, 233 PI Target value(s).` (forced line, `AutosportRacingSystem.cs:1692`). The startup fill (`:377`) left **no** Error, so the stored target+window had candidates at load.
- **23:43:26 → 23:45:33** — race 1 running: cards for a ten-car field clustered tightly around **PI 205–207** (values 205.04, 205.12, 205.41, 205.71 ×2, 205.79, 206.12, 206.63, 206.76). The `Racer.cs:714` name suffix is each car's **live pace index**, the same metric the grid ranks by.
- **23:46:00** — attempt 1: `(Error): No vehicles within 2 PI of the target - widen Max PI Deviation or the pool.` (`Log.log:193`).
- **23:46:18 / 23:46:23** — attempts 2 and 3, 5 s apart, after the window was raised: `No vehicles within 8 PI …` (`Log.log:194-195`). One Error per attempt — each call to `InstanceGrid` runs one fill.
- **23:46:29** — `Menu-Race.ini` written (mtime): `PaceMode = Absolute`, `PaceTarget = 350`, `PaceDeviation = Off`, `GridSize = 12`, `Track = …\Figureight.xml`, `ReverseRoute = True`.
- **23:46:45 →** — race 2 running: cards for **twelve** AI cars, PIs 286.21, 293.16, 296.53, 299.18, 300.91, 308.54, 315.94, 316.29, 317.26, 333.54, 391.58, 409.28. No settings write follows 23:46:29 (mtime unchanged), so the fill ran under **target 350, deviation Off, grid 12**.
- Between 23:45:33 and 23:46:45 the log is empty for **72 seconds** — no cards, no OnTick exceptions. The exceptions are per-racer (each throw is one racer's `ComputeSteering`), so their absence says the track held **no AI cars at all** across the three attempts.

**Why ±2 and ±8 both found nothing — arithmetic on the log itself.** With the window Off, `SelectClosestByPace` takes the twelve models of smallest |pace − 350|, so the twelve observed PIs **are** the twelve nearest and every other model is ≥ 63.79 away. Distances to 350: 16.46, 32.74, 33.71, 34.06, 41.46, 41.58, 49.09, 50.82, 53.47, 56.84, 59.28, 63.79 — strictly ordered, as a nearest-N selection must be. The nearest model to 350 is therefore **333.54, at 16.46**; and no model exists between 333.54 and 391.58 (any model inside would outrank the 63.79 entry and replace it). The pool carries a **hole ≈58 PI wide around the target**, so the commit's windows [348,352] and [342,358] were both empty, and the ladder's maximum rung (8) was still half the distance to the nearest car. The first attempt's own target is not recorded anywhere; that it was 350 is **PROBABLE** (the ini's value 29 s later, and the fact that ±2 failing requires a hole at the then-target — the race-1 target around 206, where the pool is dense, could not have failed).

## What emits the line, and the path it runs

VERIFIED, in order:

1. **Race menu → *Build Grid*** (`InstanceGrid`, `AutosportRacingSystem.cs:1528`) or **Start Race** (`StartRace` auto-runs the missing phases, `:2506-2520`).
2. `InstanceGrid` fades out and calls **`CleanRacers()` first** (`:1539`, body `:2550-2565`) — any field already in the world is destroyed before the new one is looked for.
3. It resolves the target (`:1543-1549`), builds grid slots (`TrackLoader.BuildGridSlots`, `:1554`), caps the size — `gridSize = Math.Min(_intendedOpponents, Math.Max(0, GridSlotsAvailable - 1))` (`:1555`) — and calls `FillCachedCandidates(gridSize)` (`:1557`).
4. `FillCachedCandidates` (`:3969-3986`) → `VehicleSelector.SelectClosestByPace(_vehiclePool, ModelPaceIndexCache, maxcars, …, _resolvedPaceTarget, PaceDeviationLimit)` (`:3982`).
5. `SelectClosestByPace` (`VehicleSelector.cs:13-44`) drops every pool entry with `|round(pace) − round(target)| > limit` (`:24`); all 472 dropped → `ranked` empty → `candidates` empty.
6. `:3984` logs the Error; `LoadGrid` (`:4011`) then spawns nothing; back in `InstanceGrid`, `Racers.Count == 0 && _intendedOpponents > 0` → `UI.Notify("~o~No vehicles found with a performance index. Check the Vehicles folder.")` (`:1563`), `_gridInstanced = false`, fade back in, **return** (`:1561-1567`). The race cannot start.

## What remains in the world when it fails

- **No empty slots and no racer-less racers.** Nothing is placed at all: a `Racer` is only constructed around a live car (`AddRacer` `:4104-4122`); a candidate whose model fails to load returns before creating anything (`:4135-4139`); a car whose driver ped fails is **deleted** (`:4154-4159`). There is no object that holds a slot without a car.
- **The previous field is gone.** `CleanRacers()` ran before the fill (`:1539`), deleting every AI car and ped. The player's own car survives — `Racer.Delete` keeps it when `ControlledByPlayer` (`Racer.cs:5312-5319`). Last night's 72-second quiet window in the log is the world with no AI at all (the failed path cleans the field whether or not a race was live; whether race 1 was ended by the player or wiped by the first attempt is not recorded — PROBABLE that the attempt did it).
- **No race.** `_gridInstanced = false` makes `StartRace` return at `:2520`; `RaceStatus` stays `None`; the player sits alone in their car with the notify above.
- **Fewer rivals than requested is a *different* branch** — it needs at least one candidate/spawn to succeed. Then the race starts short and only an Info line records it (`Grid: X of Y cars spawned…`, `:4187`, non-forced → invisible at the shipped level). With Force-Fill on (shipped default `True`, `SettingsRepair.cs:146`; live ini `True`) a short-but-nonzero grid is refilled by repeating the models that did spawn (`:4179-4186`) — but with an empty candidate list there is nothing to repeat: `failures < spawnedKeys.Count` is `0 < 0`. Force-Fill cannot rescue this failure, only the short one.
- **No spawn/load failure occurred last night.** The log carries no `Model … failed to load`, no `Skipping …`, no `Failed to load racer` — all are forced Errors that would print at any level. The failure is entirely in the ranking, before any model was touched.

## Can it repeat? Player on track, track, Grid Size, models

- **With the player on track: yes — it did, three times.** Nothing on the path gates on the player: the attempts ran with the player's car present, and the same call is reachable while a race is running (`InstanceGrid` has no `RaceIsRunning` guard; `Restart Race` routes through `StartRaceFromMenu`, `:1580-1587`), where the failure **deletes the live field first** (`:1539`) and leaves the track empty.
- **Track: not the trigger.** The track only caps `gridSize` through the slot count (`:1555`). `BuildCircuitGrid` (`TrackLoader.cs:1218-1228`) samples nodes from the route's end down to index 50 at ≥6-node spacing, so only a route of roughly ≤60 nodes could yield ≤1 slot — no shipped track is near that (the route is ~1 m per node). On Figureight the cap could not have fired: twelve cars spawned on the retry, so `gridSize` was 12, uncapped.
- **Grid Size: yes, as a separate false positive.** `GridSizeChoices` contains **0** (`:268`). With `_intendedOpponents = 0`, `gridSize` resolves to 0, `FillCachedCandidates(0)` requests zero cars, `SelectClosestByPace` breaks its loop at once (`VehicleSelector.cs:37`) and returns empty — so a **solo grid prints the same Error on every Build Grid**, with the pool untouched (and with the window Off it prints the other false message, "No vehicles in the pool with a pace index"). See B2.
- **Models: only through the pool's pace distribution.** The failure is a property of (pool file × target × window), never of a specific model failing to appear. The pool is `VehiclePool = cars.txt` (828 lines, 472 paced models after the hash rewrite). A player who edits the pool hollows or fills the region around their target; the shipped roster already has a ~58-wide hole at 350 — and the **span middle, 354** — because `_powerTargetValues` runs 122→586 in steps of 2 (233 rungs, `AddPowerValues` `:1755-1763`) and the no-stored-target autoselect takes index 116 → **354**, inside the same hole. The only combination that is safe out of the box is the shipped default window, `Off`.

## `Initialize` and a car that never appeared

`SetupRace` (`:2593-2645`) loops `r.Initialize()` over **existing** racers (`:2601-2604`); there is no branch for a car that did not appear, because no `Racer` exists for it — the absence is handled one step earlier, in `SpawnRacer` (returns `false`, adds nobody) and in Force-Fill (repeats only what did spawn, `:4179-4186`). `Racer.Initialize` (`Racer.cs:645-722`) re-reads the car's handling and model stats, resets per-race state, seeds `GridWait`, repairs the car, and re-probes the model's three stat natives **live** for the name suffix and `PowerScale` (`:703-714`) — it never re-checks the window or the target, so a car that spawned is trusted as whatever the ranking chose. `AddPlayerToGrid` (`:2569-2579`) is the only way the player becomes a racer, and it runs after the grid exists.

## What this report did not verify

1. **Nothing was driven**; no row is driver-verified. The driver's evidence is the three log lines and the two ini files.
2. **The target in force during the first two failed calls is not recorded** anywhere — no line logs a grid attempt, its target, or the pool at Error level (that absence is R1). 350 is PROBABLE for all three calls, certain for the fill that followed.
3. **The pool's pace indices could not be recomputed offline** — they come from the game's live model stats (`Racer.cs:703-711`); the hole and the nearest-distance figure are arithmetic on the log's own twelve values, not a reading of `cars.txt`.
4. **The empty-cache cause (B2b) was not reproduced** — it needs a failed power-cache pass, which no artefact shows.
5. **The 208 `OnTick` exceptions in the same log are audit 200's B1**, a separate defect; they are cited here only as the gauge that told an empty field from a running one.
