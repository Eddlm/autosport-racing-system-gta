# AUDIT 210 — performance per tick: allocations, native calls, logging

**Surface**: everything that runs while a race is live — `ARS.OnTick` (`AutosportRacingSystem.cs:1868`), the per-frame racer pass `Racer.ProcessTick` (`Racer.cs:3602`), the AI core pass `Racer.RunTimedCore` (`Racer.cs:3857`) with the batch that paces it (`AutosportRacingSystem.cs:2237-2246`), the periodic scans (`UpdatePressure`, `UpdateRivals`, `UpdateRivalInfo`, `UpdateCornerRequirements`), the wheel-memory helpers (`AutosportRacingSystem.cs:3077-3344`), the leaderboard draw path (`:2380-2448`), `ApplyNoCollision` (`:1792`), `VehicleMemory` (`VehicleMemory.cs`), and `Log` (`:3729-3735`).
**Date**: 2026-10-25.
**Build audited**: **1092** (`build/build-number.txt` = `1092`, and the deployed `Scripts\AutosportRacingSystem\build-number.txt` = `1092`), source `HEAD e851a09`. Read-only: nothing edited, built, deployed, committed or driven. The only file written is this one.
**Method**: every row was read in the source at the line quoted. Where a claim depends on the API rather than on ARS, `libs/ScriptHookVDotNet2.dll` was decompiled with `ilspycmd` — including the **IL** of `bin/Release/ARS.dll`, which is what settles the allocation model below. Measured figures come from the live `Scripts\AutosportRacingSystem\Log.log` (125,635 B, 10:47:15 PM → 11:22:15 PM, 2,100 s, build 1092).
**Verdict**: **no blocker.** Nothing here is unbounded, and nothing is quadratic in the field except a mode that ships off. What it is: **the leaderboard and the native-argument machinery under it are one cost, and it is ~four times the whole AI side of the tick** — 672 native dispatches and 1,092 heap allocations *per frame* at 20 cars, for a board whose data changes at 5 Hz. Second, **the API allocates one object per native argument**, which audit 09 explicitly denied and which makes every native call in the mod a small garbage source. Third, **three engine facts are re-queried per core tick that are constants**: the model box twice per car (while the same box sits cached on the racer), the wheel pointer list three times per car, and the game clock once per gate.

---

## Basis of every rate below

Stated once so no row has to repeat it: **60 fps**, **n = 20 AI racers**. The AI core pass runs **six cars per frame** (`:2237`, `count = Clamp(Racers.Count, 1, 6)`) and re-arms itself 3 ms later (`:2245`), which is inside a frame at any field size — so the **total is 360 core ticks/s regardless of n**, and the per-car rate is 360/n: **18 Hz per car at 20 cars**, 12 Hz at 30. Every figure below is a count from the source or the IL multiplied by that basis; **no profiler ran and no millisecond is claimed** (see "Not verifiable read-only").

Where a row says "per frame", it means per rendered frame of `OnTick`, which during a race includes the racer loop and the HUD.

## What the brief asked, answered directly

**"What is paid per frame with 20 cars on track."** Two blocks and a tail. The leaderboard: **672 natives + 1,092 allocations per frame** (P1). The racer loop, 20 × `ProcessTick`: **~200 natives per frame**, made of `UpdateTickData` (2 `GET_ENTITY_SPEED_VECTOR` + 1 clock), `ApplyInputs` (1 `IsSittingInVehicle`, 1 engine-running probe, 1 handbrake write, 1 clock), `GetThrottle`'s `Exists` (P5) and `ApplyPowerMultiplier` (1 clock + 1 `SET_VEHICLE_CHEAT_POWER_INCREASE`) — **~12,000 natives/s**. The tail is the HUD: 3 more `DrawText` once the player has a racer in the field (`:2358`, `:2370-2372`). Everything else on the frame — `SmartTuner.Tick`, `TickQueuedFlares`, `UpdateChecker.TryNotify`, the menu pool — returns on a field test before doing work (`SmartTuner.cs:247-252`, `TrackLoader.cs:1241`, `UpdateChecker.cs:57`).

**"Which natives could be cached per tick."** Three families, in order of size. (a) **Facts that never change after spawn**: the model box (`SlidingBoundingBoxWidth`, P3 — the value is already cached on the racer), `HasBone("spoiler")` and `GET_VEHICLE_MODEL_ESTIMATED_MAX_SPEED` in `GetDownforceGsAtSpeed` (`AutosportRacingSystem.cs:3855`, `:3859`), and the handling floats in `VehicleMemory` (already memoised by offset, but each read still pays `CanWeUse` → `Exists`). (b) **One value read many times in one tick**: `Car.Velocity`/`Position`/`ForwardVector` in `ComputeSteering` (P11) and in `UpdatePressure` (P7); `Game.GameTime` everywhere (P12). (c) **A field scan repeated per car**: the nearest-neighbour search in `ApplyNoCollision` (P10) and the rival scan in `UpdateRivals` (P7) both answer a question about the whole field from inside every car.

**"`WheelSideSlipAngles` and `GetWheelPtrs`: how many, at what cost with 20 cars."** `GetWheelPtrs` is called **three** times per core tick per car — 1,080 times/s, **2,160 `List`/array objects/s, ~170 KB/s** (P4). `WheelSideSlipAngles` is called **zero** times per tick: its only caller is the debug sphere drawing behind `ShowWheelSlip`, which ships false and draws for one car. The brief's premise is right about the allocation and wrong about the frequency.

**"Logging: what is evaluated even at `LogLevel = Error`."** The level test is correctly first inside `Log` (`:3732`), so no timestamp, no path concatenation and no file I/O happens for a rejected line. Everything on the **call site** still happens: the concatenations, the `ToString` formats, and — the part that matters — the calls embedded in those strings, several of which are natives (`Car.DisplayName` = 2) or allocate (`MaxWheelSlip` = 1 list + 1 array) (P9). All of them are gated to ≥500 ms per car, so the cost is bounded at ~20 lines/s for 20 cars. The unbounded half is the other direction: the code tells the user to raise the level in three places, and at `Info` every line is a separate file open/append/close.

## Negative findings — do not "fix" these

- **N1** — `_trackPositionScratch` is pre-sized to 13 (`Racer.cs:113`), cleared and refilled each core tick: **no allocation**, and the `Clear()` keeps its array. The window scan at `:4087-4108` is the shape the rest of the tick should copy.
- **N2** — The wall fold (`Racer.cs:1687-1797`) and the rival-facing throttle lift (`:2940-2945`) read only published fields on `Brain.Rivals` — no native, no allocation, no LINQ. Carried from audit 09/N-P13, still true at 1092.
- **N3** — `Brain.Rivals.Any(r => r.RivalRacer != null && r.Distance < 100f)` (`:2748`) captures nothing, so the compiler caches the delegate and `Enumerable.Any` over a `List` uses the struct enumerator: **no allocation**. The allocating LINQ on this surface is in the draw path (`:2425`), not the driving path.
- **N4** — The batch pacing does what its comment says (`:2235-2246`): six cars per frame, re-armed at 3 ms, so a full cycle is ceil(20/6) frames. At 20 cars that is 18 core ticks/s per car and 360/s in total — the denominator of every core-tick figure here, and constant in n.
- **N5** — `Log.log` is truncated at load (`:396`), so it cannot grow without bound across sessions; and `FindPattern` is memoised on the pattern string (`VehicleMemory.cs:99-110`), so a pattern miss costs one module walk per pattern, not one per call.
- **N6** — `SyncCornerContexts` is called from every `TryGetCornerContext` (`Racer.cs:391`), i.e. once per corner per tick, but it early-returns on a revision compare (`:411`). Its O(corners²) prune only runs when the corner table changes, which is a track load.
- **N7** — `ShowPeakStats` is `const false` (`:2378`), so `DrawLapStats` compiles down to the best-lap column plus four `ToString` calls that are gone. The leaderboard costs 4 columns, not 8; a reader who counts the source will overcount it.

## Corrections to audit 09, at build 1092

- **The leaderboard is 84 `DrawText` × 8 natives, not (4 header + 4 cells × 30 rows) × 8.** The peak columns are compiled out (`ShowPeakStats`, `:2378`) and the board draws 4 cells per row, so at 20 cars it is **672 natives/frame**, not 992 at 30. The per-frame shape is unchanged; the figure scales with the field.
- **"`Function.Call` allocates nothing" is false.** The `params` array is `stackalloc`, but every argument is a new `InputArgument` class instance (P2). This is the single most consequential correction in this audit: it turns every native call on the surface into an allocation, and it makes P1's cost ~1.5 MB/s rather than "dispatch only".
- **`UpdateRivals` runs at 4 Hz, not 1 Hz** — `RivalRefreshMs = 250` (`:104`). Audit 09 costed it at 1 Hz, so the rival-scan term is four times what that audit reported.
- **`WheelSideSlipAngles` is not on the tick path** (P4). Audit 09 correctly excluded two dead wheel helpers but priced the list-building as if all callers were live.
- **The `UpVector` finding is still live and is now the largest single per-tick native in `UpdateSlideAndBoundingBox`**: `Car.UpVector` is `Vector3.Cross(RightVector, ForwardVector)`, and `RightVector` dereferences `Rotation` **four** times, so 5 natives for an axis that is `SignedAngle`'s reference (`Racer.cs:3876-3878`). Unchanged from 09/P2 and unchanged in cost.

## Not verifiable read-only

- **Any wall-clock figure.** Every rate above is a count times a stated frame rate. SHVDN native dispatch is not instrumented and `Log.log` carries no timing. The *ordering* is safe (arithmetic on counts); the milliseconds are not claimed, and a native call's true cost depends on the engine side, which is not on this surface.
- **What `Game.Version` costs.** `GetWheelsPtr` and `GetNumWheels` each begin with `GameVersion gameVersion = Game.Version;` and **never use it** (`AutosportRacingSystem.cs:3117`, `:3156`) — the dead local is verified. What it *costs* is not: `Game.Version` is `NativeMemory.GetGameVersion() + 1` and the `NativeMemory` type is not present in `libs/ScriptHookVDotNet2.dll`, so whether that call is a native, an ABI read or a cached field is not decidable from the shipped API. Six calls per core tick hang on it (2 per `GetWheelPtrs` × 3).
- **Whether an enum-keyed `Dictionary` boxes on this runtime.** `DebugToggles[Options.…]` and `LookAheads[LookAhead.…]` are looked up per frame and per tick. On .NET Framework 4.8 `EnumEqualityComparer<T>.GetHashCode` should be a constrained call with no boxing, which would make them free — that is reasoning about the BCL, not a measurement, and at ≤5 lookups per frame it cannot matter either way.
- **Whether the frame actually drops.** The live log holds **173 `OnTick error` lines in 2,100 s, every one of them the same `Math.Sign` NaN out of `ComputeSteering`** (`grep -c` on the deployed `Log.log`). The cause belongs to audit 203; the *performance* fact is new and is not a claim about milliseconds: each throw unwinds out of `RunTimedCore` (`AutosportRacingSystem.cs:2243`) into the `catch` at `AutosportRacingSystem.cs:2326`, so the rest of that frame — the remaining core ticks, the whole `ProcessTick` loop, the ranking pass and the HUD — is skipped. One dropped frame every ~12 s at that rate. Nothing in the log dates the frames, so how much of a frame is lost is not measurable here.
- **P8's fix and P10's**, in the sense that matters: whether skipping a redundant `UpdateRivalInfo` or sharing one nearest-neighbour pass leaves the published fields fresh enough is a driving question (rival gaps feed the wall fold and the throttle lift), not a reading one.
- **Whether a 5 Hz leaderboard is acceptable to the eye.** The data's own rate is 5 Hz, so no information is lost, but "the number ticks rather than flows" is a driver's judgement, and it is the only thing standing between P1 and a 98 % cut.
