# AUDIT 208 — menu and settings

**Surface**: `src/SettingsRepair.cs` (schema and its three passes), `src/MenuSettings.cs` (the store), the menu tree in `src/AutosportRacingSystem.cs` (`AddSub` / `ApplyMenuTrails` / `InitializeMenu`), the load path (`LoadSettings`, `RefreshPowerControls`, `RefreshTrackList`, `RefreshCarPoolItem`), the four live `Menu-*.ini`, and the two third-party semantics every claim about item behaviour rests on.
**Date**: 2026-10-25.
**Build audited**: **1092** (`build/build-number.txt` = `1092`), source `HEAD e851a09`. Read-only: nothing was edited, built, deployed, committed or driven. The only file written is this one.
**Method**: every row below was read in the source at the line quoted. Where a claim depends on a library, the library was decompiled rather than assumed — `libs/LemonUI.SHVDN2.dll` 1.5.2 (`NativeListItem<T>.SelectedIndex` / `Items` / `UpdateIndex`) and `libs/ScriptHookVDotNet2.dll` (`ScriptSettings.Load/Save/GetValue`) with `ilspycmd`. The four live inis in the game folder were read verbatim as evidence of what a real install holds.
**Verdict**: **no blocker.** The crash the brief remembers was the trail pass (`6192bf0`); it is closed and the fix is sound. What is left is the upgrade path: **two migrations that silently do not run** (`MaxCrestLift`, `AiNitro`), the optional-key contract defeated by the code that was meant to honour it (`PaceTarget`), and one class of repaired value that reaches the file but not the car.

## What the brief asked, answered directly

**Two submenus sharing a title, or an item added after the trail pass.** Neither crashes. Titles are not keys in LemonUI — `_menuParents` is keyed by the menu object — so duplicates would only make two rows read alike, and none of the twelve titles repeats. Adding an item after the pass is safe when it is not a submenu, which is exactly the one case that exists (`resetItem`, `AutosportRacingSystem.cs:1444`). Adding a *submenu* after the pass loses its trail silently; that is F2, and the fix is one equality check against the count the log already prints.

**The same value in three houses.** Only `RubberbandingPct` disagrees (F1). Everything else matches, including the two cases where the unit differs by design (`HillGripEffect` 100 ↔ 1.0) and the two where the fallback is deliberately not the spec (`AbsEnabled`, `StagedSpawns` — both forced off at load). The 06-era checker still reports `0 error(s), 0 warning(s) over 43 literal key(s)`; it cannot see a field initialiser, so F1 is outside its reach by construction.

**What a rename loses.** Two things, both migration-shaped. `MaxCrestLift` (R1): the new key is seeded before the old one is read, so the value is replaced by the default. `AiNitro` (R2): the new spelling is migrated, the old one is not, and the file carrying it is then pruned and deleted. The deliberate retirements are not losses: `SpeedOffset` and `RouteSpeedLimit` were replaced by the two offsets that ship, and `Options.ini` / `MemoryOffsets.ini` have no reader in `src` and are deleted on purpose.

**Disabled rows, and rows that only exist with a car on track.** The only gate that can strand a *setting* is Development (F4). ABS, Show Track & Grid Rows, PI Target/Offset and Reset To Track either gate an action or gate a duplicate control, and each of them says so on its own row.

## Negative findings, so a later pass does not "fix" them

- **N1** — The trail crash is genuinely closed. `ApplyMenuTrails` walks a parent map instead of reading a parent's subtitle that may not have been written yet; the recursion visits each of the 12 edges once and cannot cycle because `AddSub` only ever links a child to the root or to a sibling. `git show 6192bf0` for the shape it replaced.
- **N2** — `Menu-Development.ini` is now completed: the 06/S2 defect is fixed, the store is in `CompleteOwnedKeys`'s dictionary, and the file is repaired like the other three (`SettingsRepair.cs:252-258`).
- **N3** — `CompleteOwnedKeys` never fights the legacy reads: every retired-key read (`:3532-3540`, `:3565-3583`, `:3613`, `:3637-3641`) happens either before the prune or against an object loaded before it, which is why R1 stands out as the one violation and R2 as the one key nobody reads at all.
- **N4** — Assigning `SelectedIndex` before a handler is attached still protects the two items that would otherwise act mid-build (`CornerCeiling` would rebuild the apex table at construction). The pattern is right; R4 is about the *other* direction, a value coming back from the repair.
- **N5** — A clean install still has no crash path: `Dist\AutosportRacingSystem\Settings\` ships `.gitkeep` only, `ScriptSettings.Load` returns an empty object for a missing file, and the getters seed every key before the completion pass runs.
- **N6** — `ReverseRoute` having two homes is deliberate and load-bearing: the debug copy must stay declared or the seeding read in the load loop re-creates it every start (`:3649-3651`). The live files show the split working — `Menu-Race.ini` says `True`, `Menu-Debug.ini` says `False` — and `TrackLoader.cs:105` is the only reader that matters.
- **N7** — **An empty list item is not a crash**, which is worth stating because the code reads as if it were. `_trackListItem` and `_powerTargetItem` are both constructed with zero entries (`:771`, `:851`) and filled by the load task (`:376-378`), so a failed load leaves two dead rows. LemonUI 1.5.2's `GoLeft`/`GoRight` both guard `if (Items.Count != 0)` and `UpdateIndex` renders an empty string when the index is -1, so the rows simply do nothing. The only throw is an explicit `SelectedIndex` assignment on an empty list (`InvalidOperationException("There are no available items.")`) — which is exactly what the `_powerTargetValues.Count == 0` guard at `:1691` exists to prevent.
