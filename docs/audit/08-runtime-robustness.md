# AUDIT 08 — runtime robustness: nulls, indices, exceptions, degenerate modes

**Surface**: the per-tick path of the shipped script — `ARS.OnTick` (`AutosportRacingSystem.cs:1802`), the racer frame tick `Racer.ProcessTick` (`Racer.cs:3403`), the racer core tick `Racer.RunTimedCore` (`Racer.cs:3660`), the steering chain it drives, the mode paths (NoCollision, DNF / Hide DNFs, spectate / player off the grid), the log floor a stranger gets, and every file write reachable from a tick.
**Date**: 2026-10-25.
**Build audited**: **958**. Live `Log.log` covers one race, `13:26:23`–`13:29:28`. Source `HEAD 9bdb9af`. The log is the same session AUDIT 01 read; its "out of this surface" note (`01-build-toolchain.md:42`) is where this audit starts.
**Method**: read-only. No edits, build, deploy, commit or game run. Two facts were taken from binaries rather than source: the `GTA.Math.Vector3` implementation, decompiled out of the **live** `ScriptHookVDotNet2.dll` (`ilspycmd -t GTA.Math.Vector3`).
**Verdict**: **one blocker** — a live NaN reaches `Math.Sign` inside `Racer.ComputeSteering` and throws out of the tick, **38 times in 77 s** on this build. It does **not** kill the script thread (see the correction below), but it aborts the whole frame's remaining work every time it fires, and the NaN that causes it silently corrupts that car's steering on the tick it appears. Everything else on this surface is latent: unguarded indices that today are held off only by the order in which two cleanup calls run, and a logging floor that a stranger's bug report will find empty.

---

## Correction to the brief's premise

The task states "one exception in `OnTick` kills the script thread for the session". **That is not what this build does, and the log proves it.** `OnTick`'s entire body sits in one `try` (`AutosportRacingSystem.cs:1804`) with a `catch (Exception ex)` at `:2253` that logs and returns; the session that produced the 38 exceptions kept racing for another two minutes, with the AI's own lines resuming immediately after each stack trace (`Log.log:596` onward). SHVDN also wraps each script tick itself. So the failure mode is not a dead thread — it is **a dead frame**: everything after the throwing statement in that tick is skipped, then the next tick starts clean.

That changes what an exception costs, not whether it matters. The blast radius is the whole rest of the tick: the remaining cars of the core batch, the per-frame `ProcessTick` loop for **every** racer (`:2188`), finish detection (`:2193`), race completion and `CleanEverything` (`:2229`–`:2236`), the help-message queue (`:2242`), `HandleCheats` (`:2251`), and the HUD (`:2044`). One bad float in one car's steering therefore costs all thirty cars their frame.

## Blockers, ranked

1. **B1 — the NaN at `Math.Sign`** (`Racer.cs:864`/`:874`, produced at `:3677`). One guard, two candidate inputs. The fix is a value check at the producer (`:3677` — the codebase already carries exactly that pattern at `:1003`, `:1030`, `:1096`, `TrackLoader.cs:218`), not a try/catch around the tick. Shipping with it live means every user's log carries a stack trace the mod cannot explain, and one car's frame is lost each time it fires.
2. **B2 — the single-try tick** is the multiplier on B1 and on every future one. It is not a defect to fix before the tag (per-racer isolation is a restructure, and it buys nothing once B1 is closed); it is the reason B1's severity is what it is, and it belongs in the record so the next exception is read correctly rather than as "the mod died".

Nothing else on this surface blocks. **F1/F2/F5 are one guard in three places** — worth doing in the same pass as B1 because it is one commit, not because any path reaches them today.

## What the log floor actually gives a stranger

At the shipped default a failing session writes: the exception and its stack (`forced`, so it always appears), "Initialization complete." (`:377`, forced), the pace span (`:1626`, forced), and "Creating needed freecam object." (`:1849`, forced). Everything that would let someone reconstruct the run — which track, how many corners, which grid, what the pace target was — is `Info` and suppressed. B1's line names `ComputeSteering` and nothing else: not the racer, not the speed, not the node. The cheapest improvement is not a new log level; it is one extra field on the existing line (`Log.log` already proves the stack is enough to find the function, and lacking only the car).

## Not verifiable read-only

- **Which input goes non-finite in B1.** The log carries no `SlideAngle`, no `Car.Exists()` result and no per-tick racer identity on the error line, so `Velocity` versus `ForwardVector` cannot be separated from the existing trace. A one-line probe at `Racer.cs:3677` (print the three vectors on the first NaN per racer) settles it on the next drive.
- **F1/F2/F5 reachability.** No live path reaches them today; the claim is a code reading of the ordering that currently prevents it, not an observed crash.
- **The per-frame cost numbers in F6** are arithmetic from the source (`Racers.Count² × 2` native `Position` reads per frame), not a measurement.
- **S1's write loop** needs an unwritable file; this install has none, so the mechanism is code-only.
