# AUDIT 06 — menu and settings: symmetry, defaults, migration, disabled rows

**Surface**: `src/SettingsRepair.cs` (the schema and its three passes), `src/MenuSettings.cs` (the store), the menu builders and load path in `src/AutosportRacingSystem.cs` (`InitializeMenu`, `LoadSettings`, `SaveRacerSetting`, `RefreshPowerControls`, `RefreshTrackList`), the shipped key checker `docs/check-settings-keys.py` with its build hook, the four live `Menu-*.ini`, and the settings values that reach a car.
**Date**: 2026-10-25.
**Build audited**: **958** (`build/build-number.txt` = `958`; `bin\Release\ARS.dll` and the live `Scripts\AutosportRacingSystem\ARS.dll` are one file, sha256 `12fb8b8ff31667a6…`; source `HEAD 9bdb9af`). The settings surface was read on a session that ran 13:26–13:29 (`Log.log`), so the four live inis are the ones this build wrote.
**Method**: read-only. No build, deploy, commit or game run. Three third-party behaviours the claims depend on were read rather than assumed: SHVDN v2 `ScriptSettings.Load/Save/GetValue` from upstream (`source/scripting_v2/GTA/ScriptSettings.cs`), LemonUI `NativeListItem<T>.SelectedIndex` decompiled from the shipped `libs/LemonUI.SHVDN2.dll` (1.5.2, `ilspycmd`), and the four live ini files verbatim.
**Verdict**: **no blocker.** The schema and the store hold up: all **42** literal keys and the **15** loop-declared debug keys have a declared home, the four live files repair clean on a load, and every seeding fallback equals its `KeySpec` default except the deliberately forced-off ABS row. The defects are all at the edges — a migration that can never run because a getter seeds first, one file outside the completion pass, a repair whose fix does not reach the session in one specific case, and a save path that is neither atomic nor checked.

## The four homes, and the ones that are missing

The schema is one home for the key set, `OptionsFor` is the second for anything list-backed, and the writer and reader are the other two. Measured against the code: **8** keys in `Menu-Race.ini`, **33** in `Menu-Settings.ini`, **1** in `Menu-Development.ini`, **15** loop-declared in `Menu-Debug.ini` (57 total), with every literal read and write matching a declaration — the checker's 0 errors is a true result for the literal population it covers.

The exceptions, all above: `AbsEnabled` has a writer and no reader (**S4**); `ReverseRoute` has four homes across two files and one of them is dead (**S9**); `Menu-Development.ini`'s key is declared, written and read but never validated (**S2**); `PaceOffset`'s list has two independent sources (**S11**). Everything else holds — including `PaceTarget`, whose absence is a meaningful state and whose read is `TryGetFloat`, non-seeding (`MenuSettings.cs:65-70`), so the autoselect is not defeated by a sentinel.

## What a clean install does, and what a second load does

`Dist\AutosportRacingSystem\Settings\` ships **only `.gitkeep`**, and `ScriptSettings.Load` returns an empty object for a missing file (upstream), so a packaged install is a true first run with no crash path: `CreateMissingFiles` creates the folder (`SettingsRepair.cs:187-205`), the getters seed their keys, the completion pass fills the rest, and the four files exist by the end of the load. `Menu-Development.ini` is created by its one seed-on-read.

A **second** load of the live files repairs nothing: every value in all four files parses and sits inside its declared domain (checked key by key against `SettingsRepair.cs:124-183`), so `Repair` returns null for all 42, and the 13:26 session log carries no `Settings repair:` line. Two caveats belong with that statement. Three of the four inis are older than the session (`Menu-Race.ini` 13:03, `Menu-Settings.ini` 11:35, `Menu-Development.ini` Oct 24) and `Menu-Debug.ini`'s mtime equals it (13:26) — a menu toggle explains that one, and nothing in the load path writes the others when every value parses — so read this as "the content is stable", not "nothing was written". And under the shipped default `LogLevel = Error` the repair's own lines are `Info` (`SettingsRepair.cs:270`, default at `:169`), so a repair **that did** happen on a default install would be invisible in `Log.log`; the developer's own file says `Info`, which is why repairs are visible here at all.

## The disabled rows

- **ABS** — the row the brief names. Greyed, built false, and the static is forced false at load, so **no stored value can reach the car** (S4). The defect is the file/UI disagreement, not the physics.
- **PI Target** — greyed in Relative To Mine, and the grid resolves its pace from the player's car plus offset in that mode, so the disabled row's value cannot reach the grid (`AutosportRacingSystem.cs:1475-1483`). Symmetrically, **PI Offset** is greyed in Absolute and cannot reach it either.
- **Development submenu** — the entry is disabled unless a race is running with exactly one racer (`:1375-1376`), but its stored `BrakeLearningNotify` still applies; the switch only gates a notification (`Racer.cs:2361`), never the car, and S7 is the misleading half.
- **Reset To Track** — enabled from `RaceIsRunning` on the menu's `Shown`; a button, no stored value.

## The write path, in one paragraph

A setting is persisted by `MenuSettings.Set` → `ScriptSettings.Save`, which truncates the file and rewrites every key, returning a bool nobody checks (S5). Each list step is its own write, because LemonUI raises `ItemChanged` from `GoLeft`/`GoRight`; the equality guard in `Set` is the only thing preventing a no-op write. That is the known trade in `council-minors` (a dirty flag plus a flush on close would collapse a scrub, at the cost of losing the value on a crash mid-scrub). The part not previously written down is that the file is **truncated before it is rewritten** while the repair's own writer is atomic — so the crash case is not "lose the value you were scrubbing", it is "lose every key after the truncation point and have the next load refill them from defaults, silently under the default log level".

## A hand-edited file

Handled correctly: a non-numeric or non-finite number → the declared default (`SettingsRepair.cs:40-52`); a bool that does not parse → default; a text value outside its domain → canonical spelling or default (`:54-57`); an optional number that does not parse → the line is dropped (`:61-66`); an out-of-ladder number → the nearest offer, and the menu follows when the snapped index is not 0. Not handled: the snap to the **first** offer (S3), a vanished `Track` (S6), a key in a foreign section (ignored by the store, kept by the prune — `:227` requires the section to be `MENU`), and a **duplicate key line**: the prune keeps both, `GetValue` reads the first and `SetValue` rewrites only the first, so a second line is inert but survives forever and makes the file read as if it said something else (upstream `ScriptSettings.GetValue`/`SetValue`/`Save`). The one thing the schema deliberately does not do is validate that a `Track` path exists — stated at `AGENTS/AGENTS-TECHNOTES.md:377`.

## Negative findings, so they are not "fixed"

- **N1** — the literal key set is symmetric: 0 checker errors over 42 keys, and no key is read or written through a store that does not declare it. The four exceptions are S2, S4, S9 and S11.
- **N2** — every seeding getter's fallback equals its `KeySpec` default across all **55** comparable pairs (40 literal keys with a default — `Track` and `PaceTarget` are optional — plus the 15 debug keys, compared by construction against the same dictionary), including the unit-converted `HillGripEffect` 100 ↔ 1.0. The single mismatch is `AbsEnabled` (True ↔ false), which is S4.
- **N3** — a value stored by an older session **cannot** reach the car through a disabled control: the ABS static is forced false (`:3508`), the PI rows are overridden by the pace-mode resolution (`:1475-1483`), and the Development switch only gates a log line.
- **N4** — no retired settings file ships and none is left behind: `Dist` carries `.gitkeep` only, and the live folder holds the four `Menu-*.ini` and nothing else. The seven retired names are read-then-deleted or never read (`Options.ini` has no reader anywhere in `src`) — `SettingsRepair.cs:340-356`.
- **N5** — the repair's order is load-bearing and correct where it counts: legacy reads (`:3444-3453`) and the rename migrations (`:3472-3478`) all run before `CompleteOwnedKeys` (`:3558`), and the `Menu-Settings.ini` legacy keys the prune removes are read from an already-loaded object, so the prune cannot eat them (S1 is the one violation of that rule).
- **N6** — `Track` is stored as the path the scan discovered (relative to the game root), and the live value matches the discovered spelling, so the selector restores correctly while the file exists.
