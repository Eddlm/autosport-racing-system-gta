## Nitrous system facts (researched, The Contract-era natives)

- **Nitrous system facts (researched, The Contract-era natives)**: "vehicle has nitrous" = **vehicle mod slot 17** (`VMT_NITROUS`) — detect with `GET_VEHICLE_MOD(veh, 17) != -1` (already in SHVDN2's Hash enum; what LS-Tuners-style shops and trainers write). All nitrous natives are plain game-binary VEHICLE natives (SP-safe, raw-hash calls): `SET_OVERRIDE_NITROUS_LEVEL` 0xC8E9B6B71B8E660D (**must pass all 6 args** — 2-arg calls zero out level/power/recharge on b2060+), `FULLY_CHARGE_NITROUS` 0x1A2BCC8C636F9226, `CLEAR_NITROUS` 0xC889AE921400E1ED, `IS_NITROUS_ACTIVE` 0x491E822B2C464FE4 (BOOL, boost firing now), `_GET_REMAINING_NITROUS_DURATION` 0xBEC4B8653462450E (float charge), `SET_NITROUS_IS_ACTIVE` 0x9E566EA551F4F1A6, `_SET_NITROUS_IS_VISIBLE` 0x465EEA70AF251045, `_SET_REMAINING_NITROUS_DURATION` 0x1AD0F63A94E10EFF, `_SET_VEHICLE_USE_HORN_BUTTON_FOR_NITROUS` 0x1980F68872CC2C3D (global horn→nitrous). Installed state persists in mod data; charge is runtime-only per entity. Vanilla SP LS Customs does NOT sell nitrous (Online workshop feature) — in SP, slot 17 is set by trainers/modded shops only. **Verified in-game**: `_GET_REMAINING_NITROUS_DURATION` is useless for detection (always reads ~full, only drops on fire, never recharges exactly — a below-full charge implies a past fire but is unreliable and resets per entity), and trainer-forced nitro has no detectable installed state — the only fire-side signal is `IS_NITROUS_ACTIVE`. **ARS detection is therefore a latch**: `PlayerHasNitro` turns true on mod slot 17 installed, the player firing nitro (`IS_NITROUS_ACTIVE`, probed in OnTick), OR a below-full charge read; it is cleared at each race start (`StartRace` — a per-race latch, not a whole-session one). A silent OnTick probe (no debug display) runs the poll. **Menyoo 2.0 source audit** (cloned `itsjustcurtis/MenyooSP` to `_research\Menyoo2`): Menyoo declares the full nitrous native set but **never calls any of it** — its "Race Boost On Horn" is fake nitro (`SET_VEHICLE_BOOST_ACTIVE` toggled one frame + a raw forward force + hand-rolled NOS PTFX); its "Infinite Native Boost" targets the separate **rocket-boost family** (Oppressor-style, unrelated to nitrous). This explains why trainer "nitro" is undetectable: it never engages the real nitrous system, so neither charge nor IS_NITROUS_ACTIVE can see it; only slot 17 or genuinely-fired nitrous can latch. Menyoo also has **no vanilla nitrous toggle at all** (its `VehicleMod` enum names slot 17 `Unknown17`). Also note an ecosystem hash-name conflict: Menyoo binds 0x465EEA70AF251045 as `SET_NITROUS_IS_ACTIVE` (our notes call it `_SET_NITROUS_IS_VISIBLE`), so trust behavior over name for that hash.

## Two-projection route speed (future idea)

- **Two-projection route speed (future idea)**: the user rates the projection layer very highly — long-term, `followTrackSpd`'s geometric `√(g·grip·r)` could be replaced by a two-projection system: a *true* projection (ballistic `ProjectAhead`, self-calibrating via measured acceleration — no grip-model disagreement) and a *pessimistic* projection at reduced grip ("could I still hold this if the surface worsens?"). Design caveats the rebuild must solve: a projection is a **limiter, not a planner** — it assumes current velocity+accel continue, so it cannot see future braking decisions (the apex braking map stays for long-horizon work; projections cap what the plan may attempt); multi-second ballistic horizons are physically wrong; and a target derived from a projection that depends on current speed risks a self-referential feedback loop (needs damping or latched verdicts). The pessimistic variant's real value is anticipatory: ease speed *before* the edge instead of the current offshoot cap's after-the-fact emergency. Reference pattern: `ApplyOffshootBlend`'s shape.

## TRlat ladder

- **TRlat ladder — the slide-response envelope is parameterized by `Handling.LateralTractionCurve` alone.** The *slide-handling* rungs: **×0.3** = the countersteer *priority* blend start; **×0.6** = priority saturation and the full-countersteer pedal gate. **The ladder's two steering-limit rungs are RETIRED** — **×0.33**, the allowance base, and **×0.5**, its ceiling (`min(TRlat × 0.33 + |slide|, TRlat × 0.5)`, so the base is two thirds of the ceiling) — replaced by the two-sided corner-geometry ceiling (vanilla's grip-scaled, shift-free curve vs Ackermann — AGENTS.md pipeline step 4). The formula is kept as history, not as a fallback: Ackermann sits **below** it above the ~17 mph crossover, so restoring the ladder would *loosen* the limit rather than tighten it. The rungs that still live are the slide-handling pair above (**×0.3** blend start, **×0.6** saturation). Do not confuse either with the removed MaxBrake rampdown's threshold (`2 + TRlat × 0.2`) — a different use of the same fraction. (The base-vs-flat-`2°` discussion further down this bullet belongs to that dormant form.) **Re-verified against the source and corrected** — this note used to claim ×0.5 for the blend start and a "×1.2 slideScale ceiling" that exists nowhere in the code. Two things to keep in mind: the blend lerps the final steer toward "damped course steer − countersteer correction" (the course/recovery/side-by-side PD plus yaw damping with the countersteer correction applied, **lane steer live again**), with the correction itself at **1 × slip**; and the old `+2°` base was replaced by that TRlat-scaled one because the base *is* a non-sliding car's whole allowance: a high-grip car slides least, so it lives in the base regime and could barely steer (found in game), while the `×0.5` ceiling it was sized for stayed unreachable — the same fixed 2° felt right only on low-TRlat cars. The flip side: a scaled base is **tighter** than the flat 2° below TRlat ≈ 10 (≈2° at TRlat 6), so on a very low-grip car the constant — not the ceiling — is the knob if it turns out not to steer enough. `_slideCountersteerDegrees`, which this note used to cite as the stored countersteer, **no longer exists** — the live value is the local `countersteerTarget`. **Measured band (parsed from the live `Log.log` `TRlat for <car>` lines)**: the field runs ~10.75–12° with the drift variants far above (`ISSI8` 21.75°, `DRIFTCHAV6` 28°), so "a slide" is a per-car quantity up to 2.5× apart within a single race. The `[1,100]` guard's fallback is 22 — check that log line after any handling swap, because every threshold in the ladder doubles if the read falls out of band.

Related durable lesson (kept in AGENTS.md too): **corrections are corrections — never reuse one as an absolute target.** A value stored as "subtract from the PD" (the old per-frame countersteer) carries the *opposite* sign of the steer direction it wants; lerping the final steer toward it as a target steers **into** the slide. This exact mistake inverted the countersteer at full slide priority and was caught in-game (car sliding rightwards steered leftwards, off-track). When blending toward a slide-response target, reconstruct the full target (trajectory terms + correction applied), not the correction alone.

## Steering limit (`ApplySteerLimits`)

- **Steering limit** (`ApplySteerLimits`): **two side limits, one clamp, and it runs last.** `SteerLimitRight` / `SteerLimitLeft` both default to `min(vanilla, Ackermann)`. Vanilla's curve is `SteeringLock / (1 + k × v)` with **`k = 0.075 / √(grip / 1)`** and the **`− 5` shift removed**; Ackermann is `atan(wheelbase × grip × g / v²)` — the tightest corner the grip allows, the same 9.8 and grip that `SteerLimitedSpeed` inverts, on a **bone-derived wheelbase** (`ARS.GetWheelBase`: both axle centres averaged — which cancels the offset steering puts on the front pair — projected on forward, bounded 1–6 m, fallback 2.7). The pair crosses at ~17 mph and **Ackermann owns everything above it**. Countersteer is **not exempt**: the side the wheel is on is *raised* — gated on the steer-vs-yaw sign test **and** the slide blend being engaged (`|SlideAngle| ≥ TRlat × 0.3`) — to `Math.Max(ceiling, min(|SlideAngle|, lock))`, a raise that can never lower a limit. That replaced a sign-test exemption which let the countersteer side run **unbounded**; the two-variable form makes every allowance a *number* (whitelist, not blacklist). **Two order constraints.** The limiter sits after every writer of the steering request in `ProcessAI` — the stuck-recovery override had to be converted from writing `Control.SteerInput` to writing `Control.SteerDegrees` to stay inside it — and `TranslateSteerToInput` converts the request to input afterwards, so **a steering writer added below the limiter is a silent bypass**. The brake release moved out to `ConvertSpeedToPedals` (its consumer, the post-slew `Min`, is there and `ConvertSpeedToPedals` runs first now). **Grip source is `CurrentMechanicalGrip`, not `BaseMechanicalGrip`**: the base has the downforce term divided out (`/= 1 + 0.035 × downforce`) and gets it back only through `Current`, so the base reads *low* on downforce cars and would tighten the cap for exactly the grippiest ones. Of the things once tied to the limiter, only the **countersteer brake release** remains (the **MaxThrottle cut** was removed as a no-op that would have fought TCS — see AGENTS-BACKLOG — and the MaxBrake *rampdown* (the brake cap easing to 0.8 as the slide grew) was **removed for the WIP release** and returns after the v0.9 feedback (AGENTS-BACKLOG). The release past the full-countersteer threshold still drops `MaxBrake` to zero, which lands as the post-slew `Min`, so the brake is released instantly rather than ramped — but the **cap is now stateful**: it recovers at the `MaxThrottle` rate (`Control.MaxBrake += 2 × TickScale` in `ConvertSpeedToPedals`, mirroring the throttle line beside it), so full braking returns over ~0.5 s instead of on the next tick, and the value self-heals without a per-tick reset. The stale speed-reduction zombie that used to sit here (hardcoded `0.5`, threshold `0.001`, plus a TRLateral `×0.3` min-steer floor, and fields that no longer exist) is **deleted** — the live ceiling is that same idea carrying vanilla's real constants, applied as a limit instead of as a division. The earlier **empirical peak-memory** system — it learns the steer angle that produced the best *measured* lateral G. **Its remains are deleted** — `GripRefGain`, `ExploitUtilization`, `UtilizationFloorFactor`, `SpikeCapFactor`, `OversteerCutMargin`, `_latGRef`, `_peakSteerDeg` and `_nearGripPeak` had no readers left (the constants were the only survivors of that system), so the whole paragraph below is the record of *removed* code, not live behavior; recover the values from git if it is ever rebuilt. The `MaxThrottle` cut is additionally gated on the limiter having authority (see the steer-limiter tie-in in AGENTS-BACKLOG). **Corrected, then corrected back**: the "steering D term" this note called a feel-based carve-out **is `steerKD` again** (the local now fed by the derived `SteerDamping` property — see the damping section below) — the PD assembly was restored from `1f4516d` and the damper is live — `− SteerDampingGain × (yawRate − yawTarget)`, the target being the yaw the **aim point** requires (`Racer.cs:589`, `:596`) — while the steer PID's `SteerTrim` / `SteerI` / `SteerD` are **gone**. An earlier revision of this line claimed the exact opposite; if you meet that claim anywhere, it is the abandoned law talking. The **speed-based steering reduction** this note used to lump in with it (`steer /= 1 + factor * (fwdSpeed - threshold)`) is **not live**, and the dead `ZOMBIE` block that held it has since been deleted outright — the `SteerReductionPerMps` that survives is the **vanilla ceiling's own k**, live and applied (`Racer.cs:990`, `:1031`). **Everything is in Gs** (latG = `AverageAcceleration·right ÷ 9.8f`; `_bestLatG` stored in Gs; declared grip ceiling = `CurrentMechanicalGrip`, NOT × gravity — a lingering 9.8× unit bug lived here, never multiply grip by gravity and treat it as G). **The reference is now a linear proportional controller, not an exponential filter**: `ref += (Gs − ref) × gain × dt` (gain ≈ 5 → ~0.2 s time constant), symmetric rise/fall, no deadband — the input is spike-clamped before integrating (a collision impulse must not lift the reference even one frame's step). Utilization (current/ref) drives explore vs exploit: near the peak → exploit (limit = remembered steer + small margin, floored); below → explore (limit = `min(steerLock, bestSteer·1.5 + 2)`, floored — *bounded* per audit MAJOR-3, since full lock would map to ±1 input and make the clamp a no-op). Declared grip is only the spike-rejection sanity cap (`×1.1`). The two old limit systems (grip-saturation formula; slide-angle lerp) are commented out above. Hitting the limit caps `MaxThrottle` (pegged → 0.9, 10° past → 1/s cut). TRlat/declared curves are not trusted. (The `STEERING_AUDIT.md` file this section used to reference no longer exists in the repo; its surviving conclusions are the MAJOR notes above.)

## Side-by-side heading match (`ComputeSideBySideSteerCorrection`, `Racer.cs`)

- **The match is one-way**: it applies only while the overlapping rival is moving toward this car's side, tested as the rival's *own* velocity against the axis that separates the two cars. A rival drifting away is leaving room, and matching their heading there steers this car across the gap after them; this car's own closure stays the rival walls' business.
- **The side convention, verified**: `+ = right` — `SignedLaneOffset` (`AutosportRacingSystem.cs:550`) and `RelativeOffset.X` / `LateralGap` (`DataStructures.cs:163`) are the same `Cross(dir, WorldUp)` dot and `Cross(forward, up)` really is world-right. `TryPickAvoidanceSide`'s `passLeft` names the side it *passes on* (a rival on the right → pass on the left), so reading it as the rival's side makes it look inverted when it is not.

## Lane steer — one flat P, and deliberately no ceiling

- **The lane term is a single proportional law on the lane error, and it must stay uncapped.** A ceiling looks like the gentler instrument and is not: it flattens the top of the P, so most of a big lane move runs at a constant command that builds lateral velocity the short proportional tail cannot shed — bang-then-taper, which is exactly the overshoot it was added to cure. Driven both ways in one session, and uncapped won.
- **Two levers came out of that session**: the gain, halved for the move out to the outside because that is the big deliberate one (`LaneGainDegPerMeter` / `LaneSteerOutsidePercent`), and the low-speed ramp on the ceiling, which is what lets the P's taper reach the tyres at the speeds lane moves actually happen. A position-only P carries no rate feedback of its own, so the damped approach survives only because the yaw damper is opposing the rotation the P has just started.

## Steering damping (`SteerDamping`)

- **The gain is stored, not derived** (`a9603c4`): `SteerDamping` = `ARS.SteerDampingGain` verbatim, an absolute gain in **seconds** applied to `(yaw − target)` (the reference is the **aim point's** required yaw today — `SteerDampingAimReference` `Racer.cs:960`, fed by `_steerAimCurvature` at `:714`; the zero reference and the old `SteerDampingTrackReference` switch are both gone). The dial is no longer pre-divided by grip — it used to be a *scale* (`scale / baseGrip`, floor 1, menu `0.50–2.00`) and `a9603c4` replaced it with the direct gain, menu `0.00–2.00` in 0.1 steps, per the rename rule below — but the **term still divides by `max(BaseMechanicalGrip, 1)`**, so grip scheduling moved out of the stored value rather than going away (`Racer.cs:970`). The old rationale (uniform multiplier on damping ratio, the grip ≈ 3.5 crossover, `1/grip` vs `1/√grip`) lives in `AGENTS-STEERING.md`'s ranked list. **Corrected — the `grip` column of `pidump.txt` is NOT a damping input**: the column is the **model** native `GET_VEHICLE_MODEL_MAX_TRACTION` read raw in `BuildPowerCache`, while live grip reads the **spawned-handle** native and then applies `/= 1 + 0.035 × Handling.Downforce` (`UpdatePerceivedGrip`) — so on a winged car live grip is **lower** than the column and the dump cannot show it. TRlat is a **slip angle in degrees** and is not the same quantity as the TCS's read — see the wheel-memory bullet below. Any grip span quoted from the column (a stock install once read 1.20–3.25 G, mean 1.89) is **installation-dependent** — re-derive it with the `arspidump` cheat rather than trusting a recorded band.
- **Why a per-car gain cannot be a static**: `ARS.SteerKD` used to hold the gain directly, and a grip-derived value there would have every racer overwrite the others' gain every tick, because grip is per-car. The old design moved the derivation to the racer property; the hazard now only bites if a *derived* gain is reintroduced — **a per-racer value stays a racer property, never a static. Read the property, not the static, when reasoning about one car's damping.**
- **Off-road gravity, not grip, is the flag's only effect (still unmodelled, fix specified)**: it scales `BaseMechanicalGrip` by the gravity multiplier (×1.2 when `gravityGs > 1`) in `UpdatePerceivedGrip` — a permanent per-car property applied once in `Initialize` (`Racer.cs:392`), never a surface state, so it must not be described as an off-road condition (that misreading has been made once already). It double-counts, verified in the leaked engine: the flag raises **only the wheel integrator's gravity** (`Vehicle.cpp:31323`, `m_fGravityForWheelIntegrator = fGravity × fGravityMult`) and leaves the traction coefficient alone — the native ARS reads is `m_fTractionCurveMax × fTractionMult` with downforce terms only (`commands_vehicle.cpp:6250`), so the "increased grip" the flag lists quote *is* the load rise, and scaling grip as well counts it twice. Multipliers are `Vehicle.cpp:449-451` (1.1 / 1.2 / quadbike 1.2), chosen at `:31304-31311` by `if (HF_OFFROAD_ABILITIES) … else if (_X2 || _INCREASED_GRAVITY_NO_FOLIAGE_DRAG)` — **mutually exclusive, the base bit winning** — with a hard-coded Mesa3 exception at `:31314`. ARS tests only bits `0x200000` and `0x800000`, so the base ×1.1 tier, the precedence and both special cases are unmodelled.
- **The setting key was renamed, not reused — the third instance of that idiom.** A stored value under old semantics trips the repair pass's "snap an in-list numeric to the nearest offer" rule and becomes a plausible, invisible wrong number (a stored absolute `0.45` under a scale dial would have become `0.50`, halving the damping on upgrade; `SteerDampingScale` → `SteerDampingGain` renamed again for exactly that reason — `a9603c4`). **Rule: when a setting's *meaning* changes, change its key too — a repaired value is worse than a reset one, because it is plausible and invisible.**
- **A menu list lookup must be formatted to match the list's own strings.** `GetFloat(...).ToString(InvariantCulture)` renders `1f` as `"1"`, which is not in a list of `"1.00"` — so `IndexOf` returns −1, the `Math.Max(0, …)` snaps to the **first** item, and assigning `SelectedIndex` fires `ItemChanged`, which *writes* that first value. A bare `ToString()` against a two-decimal list therefore silently rewrites the setting to the first option on every load. Format with `"0.00"`. **This trap is latent in any numeric list whose entries are not in the same string form as the default's `ToString()`.**
- **Wheel memory (`wheel+N` over `GetWheelPtrs`)**: the TCS read at `+0x174` is a per-wheel **slip RATIO**, dimensionless — 0 = free rolling, traction peaks at argument 1.0, flat from 2.5 (`sfTractionPeakAngle` / `sfTractionMinAngle`, leaked `wheel.cpp:94–97` — the constants' "Angle" names are historical; the curve's true argument is the ratio, `:8364–8365` the definition `(averageWheelSpeed − groundSpeed)/groundSpeed`, and `m_fEffectiveSlipAngle` is *derived* from the ratio, `:4682`, so the ratio is primary). ikt32's MVT labels the same slot "overheat" — an unverified +8 guess off the rotation-speed anchor, superseded here. `+0x198` = the per-wheel surface grip multiplier, ~0 lifted (read by `MeanWheelGripMultiplier`; the `WheelsOnGround` test that first used it was removed), and `steer+8` = per-wheel drive power (pattern-learned, `0x1D8` fallback). **Slip ratio ≠ slip angle in either direction**: `LateralTractionCurve` is an angle in degrees on the *lateral* curve, and a wheel's cornering slip angle never enters `MaxWheelSlip` — only rotation slip does. **The scale, settled by the driver against live values** (a stopped wheel reads ~15, mingrip onset at 2.5): the curve peaks at 1.0, degrades linearly to CurveMin at 2.5 and is flat past it; the earlier reading that put these ÷2.5 lower (via `m_fFwdSlipAngle` = raw × 2.5, `wheel.cpp:4497`/`:5220`) was a scale transcription error, and moved every target down until the re-anchor. Coefficients × `fMult × fLoss` at `:3194`. The engine's own cheat TC clamps at ±`MinAngleInv × LossInv` = ±0.4/fLoss (`:4508-4511`) — its own peak-hold — and spin-direction reads negative (`:5233`), matching ARS's convention. **The TCS targets are three points on that curve** (scaled by the same grip floor the slip-target always used): peak-traction 1.0 for normal driving, the CurveMax↔CurveMin mid-traction point 1.75 with a linear taper back to 1.0 over 0–30 mph from a standstill, and the fixed (not surface-grip-scaled) 0.5 off-track — the shipped −1.25 deep-saturation target and its slide deepening both retired.

## Pedal map (`ComputeCombinedInput`)

- One linear map for both pedals, **no feedforward**: `Clamp(speedError / divisor, ±1)`, the brake's divisor being the throttle's × `BrakeErrorMultiplier`. It replaced a `signsDisagree` shortcut that returned full brake for *any* deceleration above 10 mph — **redundant**, because a genuine direction swap's error is the sum of the magnitudes and saturates on its own.
- **What that shortcut was hiding is droop, and it is live again**: a P-only map holds a decel only at a standing error of `divisor × brakeFraction`, so under sustained braking the car tracks the plan *above* it by roughly that much. At the current divisor that is a handful of m/s; if braking ever under-brakes in long zones, this is the cause, not the decel formula.
- **The fix belongs on the pedal side, not the plan**: apply the plan's own demand as feedforward — `EffectiveBrakeFactor(apexNode)` is already the brake fraction it budgets for — and let the error trim. **Do not restore `PedalTrackingOffsetMps`/`BrakeDemandScale`** (added `b767c19`, removed `07d5e57`): that aimed the *solve* a fixed margin below the ballistic profile, which coupled the plan to the pedal map's gain and scaled the learner's output on its way into the solve.

## ShowCheckpoints — full marker details (restored verbatim from b845170)

Each corner renders **two primitives**:
    1. **Standing torus ring** — `(MarkerType)1` (the SHVDN2 enum hides this as `Cylinder` but the prop renders as the classic torus; cast through `World.DrawMarker` rather than raw `Function.Call` to dodge texture-arg marshalling). Anchored **below** `TrackPoints[corner.Node]` (dropped into the ground), X/Y scale = `trackPoints[node].TrackHalfWidth * 2` (full track width, so the ring spans the entire road at the apex), camera-facing. The wrapper does NOT crash like raw `DRAW_MARKER` with `textureDict=""` did — the wrapper sidesteps the marshalling issue.
    2. **Centered exit chevron** — `(MarkerType)20` (`ChevronUpx1` / `PROP_MK_RACE_CHEVRON_01`). Anchored **directly above** `TrackPoints[corner.Node]` (kept centered), lifted above ground (matching FiveM `client.lua:452`). Direction = `(nextApex - apex).Normalized` (zeroed Z); rotation per FiveM `client.lua:466–491`; `faceCamera=false` so the direction vector is honored.
  **LOD strategy**: a corner renders if and only if the node delta from the player is within a window with a small negative grace (so a ring doesn't pop the instant it's crossed; delta = node − playerNode, plain subtraction for point-to-point, modulo for circuits via `ARS.IsPointToPoint`). The player Racer is passed into `DrawCornerCheckpoints(Racer player, …)` — its live `CurrentTrackPoint.Node` (updated each tick by the normal track-position pipeline) gives the player node, no extra scan. Runs from `OnTick` (player found via `Racers.FirstOrDefault(r => r.Driver != null && r.Driver.IsPlayer)`), guarded by a `playerRacer != null` check. FiveM reference is `racingsystem/client/client.lua:393–491`; ARS adapts this to corners-only via `ARS.Corners` instead of every node.

## Pace selection — current state, and two lessons from the window→ranking switch

**Current**: selection is a **ranking** — `VehicleSelector.SelectClosestByPace` does one pool pass, sorts by `|pace − target|` and takes the closest N (shuffled for ties). The bracket, the widen loop (`Options.WidenBracketFill`), `PowerBracketScale` and `VehicleSelector.Select` (plus its never-called `CreateDuplicate`) are deleted; a stale `PaceBracket`/`WidenBracketFill` key in an existing ini is never read, because `LoadSettings` walks the `DebugToggles` **dictionary**, not the enum, so an orphaned key is simply not visited. `Pace Offset` is a fixed signed integer list (−10..+10); Relative resolves `playerPace + offset` **once per `InstanceGrid`** into a local, and must never be written back into `PowerTargetScale` — that write-back is the one real trap (it corrupts the persisted absolute target). Pace Mode alone decides the anchor for every grid; `ComputePlayerCarPaceIndex` (the join's old fallback wrapper) is gone with the join override. The b845170-era wording for all of the above (bracket + widen loop, offset −50..+50, `Clamp(playerPace + offset, 0..200)`) is in git at `b845170` if ever needed.

**Lesson 1 — clamping an anchor is inert for a ranking.** Clamping into `[min,max]` cannot change a distance *ordering*: every candidate's pace lies inside the span by construction (same cache), so both distances stay monotonic in pace and the sequence is identical. The fleet-span clamps were load-bearing only for a **fixed-width window** (moving a window's centre changes which cars fit), so they were removed with it. The single surviving span use is a diagnostic log when the anchor sits outside the fleet.

**Lesson 2 — the switch inverted non-finite-pace handling.** A window *excluded* non-finite paces (`NaN <= bracket` is false); `OrderBy` over a ranking sorts **NaN first** (`Comparer<double>` places NaN below every value), so a NaN score would have been preferred — the opposite of before. Root cause: `BuildPaceIndex` filtered grip and mph but **not** `accel`, the one raw stat taken straight from a native and defaulted via `TryGetValue`. The computed score is now validated before entering `ModelPaceIndexCache`. (An infinity would additionally have emptied the Pace Target list: `GetPaceSpan` has no filter, and `AddPowerValues` computes `(int)Math.Floor(Inf / step)`.)

**Electric detection — a real bug found and fixed (`96f5a72`)**: this file used to record `GET_IS_VEHICLE_ELECTRIC` as `0xD839450756ED5A80`. That hash **is not a native at all** — it isn't in SHVDN2's `Hash` enum and no member name contains "ELECTRIC" — and calling it returned non-zero for *every* model, so `ModelElectricCache` flagged all 488 cars as electric and the electric correction was silently applied **to the whole fleet** (petrol cars gained 5–9 PI). The real native is `0x1FCB07FE230B6639`, model-hash based, build 3258+; verified in game: 19 electrics, petrol reads 0. The lesson worth keeping: a native hash that nobody has verified in game is a guess, and a wrong hash here fails *silently and plausibly*. **Follow-up worth knowing**: `96f5a72` repointed only the *selection* path — `Racer.Initialize` and the player-pace fallback kept calling the discredited hash, so every car's **spawn-time** pace over-applied the electric bonus while the grid was ranked on the corrected flag. `Racer` now reads `ModelElectricCache` (the very flag selection used, which makes the two agree by construction) and the fallback calls `ARS.IsElectricModel`, which owns the single availability probe; the bad hash appears nowhere in `src`. "TopUpNitrous returns success" was an audit fragment that does **not** exist in any committed AGENTS.md — the nitro-pacing rework (`Racer.NitroChargedLap`, replacing the idle 1 Hz top-up) supersedes that line of inquiry entirely, so it is closed.

## Settings folder — declared inventory + repair (`3fa7737`, `0fd4e0a`)

`src\SettingsRepair.cs` is the inventory: which ini files ARS expects, which keys each must hold, and what a healthy value looks like. Three passes run from `LoadSettings`, in an order that is load-bearing:

1. `CreateMissingFiles()` — first, before anything reads a store. Creates `Settings\` and moves `DevSettings.ini` to its legacy migration name when necessary.
2. `PruneOwnedFiles()` — still before any store reads its file, so no cached `ScriptSettings` object exists that could later `Save()` a pruned key back into the file. Line-level filter: inside `[MENU]`, a `key = value` line survives only if the schema declares the key; every other line (blank, comment, foreign section) is preserved verbatim. Rewrite goes through a temp file + `File.Replace` so no half-written ini can exist.
3. `CompleteOwnedKeys(...)` — last, **after** the legacy migrations and after the `LoadSettings` reads. Fills missing keys with their declared defaults and normalises rejected values, all through the existing `MenuSettings` API (`Get(key, null)` is a side-effect-free existence probe — `SeedIfMissing` returns early when the fallback is null).

**Ownership rule** — `Menu-*.ini` are the only active settings files and the schema owns them outright. `Settings.ini`, `Options.ini`, `DevSettings.ini`, `DevConfig.ini`, and `MemoryOffsets.ini` are retired: the remaining migratable values are copied into the menu stores, then all are deleted.

**Invariant: a created file holds exactly the values the code would use if the key were absent**, so creating one cannot change behaviour. That is also why `Track` and `PaceTarget` are declared *optional* (no default): absence is meaningful for both (no track chosen; and an absent `PaceTarget` is what triggers the fleet-span middle autoselect in `RefreshPowerControls` — writing any default there would silently pick the slowest cars in the fleet instead).

**Value policy**: `Bool` and plain numbers must parse (garbage → declared default); a number with a domain list (`TimeoutSeconds`, `AIRacerAutofix`) **snaps to the nearest offered value** — an off-list value is what makes the menu silently show index 0 while the file holds something else (the long-standing wart in the Council backlog); list-backed strings (`GridSorting`, `AiNitro`, `PaceMode`) must match a spelling exactly, a case-only difference is rewritten to the canonical spelling, anything else resets to the default; `GridSize` is range-clamped to the same 0..12 the menu enforces. Optional keys (no default to repair them to) are handled by the prune pass instead: a declared **numeric** key that does not hold a finite number has its line dropped, because absence is its healthy state. That rule exists because of a defect caught in-game (`0fd4e0a`): `RefreshPowerControls` probed `PaceTarget` with `GetFloat("PaceTarget", float.NaN)`, and seed-on-read wrote the **sentinel** — a file containing `PaceTarget = NaN` — which additionally defeated the "absent → auto-pick the middle of the span" branch that key is declared optional for. **Gotcha: never hand a non-value sentinel (NaN) to a seeding getter as its fallback; probe with `MenuSettings.TryGetFloat` (non-seeding) when absence is meaningful.** A wrongly-typed *non-numeric* optional key (e.g. `Track = junk`) is still left alone.

**The inventory** (owned files, `[MENU]` section, in schema order):

| File | Keys (default) |
| --- | --- |
| `Menu-Race.ini` | `Track` *(optional)*, `Laps` (4), `GridSize` (4), `PaceMode` (`RelativeToMine` — the menu calls the item `Grid PI Mode` and spaces the option to "Relative To Mine"), `PaceOffset` (0), `PaceTarget` *(optional)*, `ReverseRoute` (False) |
| `Menu-Settings.ini` | General, AI, and Advanced menu keys, including Hotkeys (True), MenuModifierKey (Left Shift / 160), MenuKey (E / 69), and LogLevel (Info); exact defaults and domains live in `SettingsRepair.BuildSchema()` |
| `Menu-Debug.ini` | one key per `DebugToggles` entry — the table *is* the schema, so retiring a toggle retires its key automatically |

`Menu-Settings.ini` **carried the retired `PaceMode` key** (`9b8da25`) before the Settings store took that name: `LoadSettings` reads its `PaceMode` **before the prune pass** (the key is undeclared now, so the prune would drop it first) and carries it into `Menu-Race.ini`. That file is then pruned and repopulated as the Settings store, so this legacy read is one of the two that cannot move below the prune — the other being `Menu-DevSettings.ini`'s `BrakeLearning`/`StagedSpawns`. **The rename migration follows the same rule**: `Menu-Racers.ini` → `Menu-Settings.ini` and `Menu-DevSettings.ini` → `Menu-Debug.ini` are migrated key-by-key from `SettingsRepair.DeclaredKeys` (never a hardcoded copy of the key list) and the old files are then **deleted**, so the folder never holds the same settings under two names.

No standalone settings file is created. The old `Options.ini` catch-up keys and `ReverseRoutes` read were write-only/dead and were removed; `MemoryOffsets.ini` had no reader. `DevConfig.ini` general values migrate to Advanced Settings, while its legacy `[DEBUG]` values migrate to `Menu-Debug.ini`. Neither a `Disciplines` key nor per-car appearance data survives.

Two wrinkles worth knowing: `ReverseRoute` lives in `Menu-Race.ini` (the Race menu's checkbox passes `RaceMenuStore` through the optional `store` overload), yet a `ReverseRoute` key **also** keeps appearing in `Menu-Debug.ini` because the load loop reads every `DebugToggles` key from the dev store before overriding that one from the race store — so the dev schema must keep it or the repair and the load loop would fight on every start. And `OverspeedEnabled` has no `Migrate` call at all; it is seeded purely by the `LoadSettings` read (seed-on-read), which is exactly the kind of key the completeness pass now guarantees.

**What the repair does not do**: it does not validate that a `Track` path still exists on disk, does not reorder or reformat foreign files, and does not touch `Settings.ini`, `Tracks\`, `Vehicles\`, `Drivers\` or `sillynames.txt`.

## Grid pace selection - pace score, electrics and PI ballpark, moved out of AGENTS.md

- **Pace score** (`ModelPaceIndexCache` + `ComputePaceIndex`): a raw per-model score, **not** 0–1 (`topSpeedMph + cornerSpeedMph + effectiveAccel × k`, the three terms sized to a 50/30/20 top/grip/accel split by `f3fc274`; the old normalized/ceiling/weights consts were dead code, since removed). **Electrics** are flagged live at table-build time by `GET_IS_VEHICLE_ELECTRIC` (model-hash native, build 3258+, probed once so an older build degrades to "no electrics") and their raw G is scored at the **peak of the game's own drive-force ramp** — ×5 at standstill falling linearly to ×0.9 at top speed — with **no top-speed discount** (the 0.9 is the ramp's endpoint, not a reduction of top speed; the old code misread it that way *and* used a hash that flagged all 488 cars as electric). **`f3fc274` replaced the ×2.95 midpoint that `96f5a72` had driver-verified with the ramp's peak, and that was measured rather than assumed: off the `pidump.txt` taken after it, the four fastest electrics (tezeract, virtue, suzume, X-treme) score above the fastest ICE model in the whole fleet, and the rest sit 20-70 PI above their class's ICE median — so the fast electrics are effectively unselectable against an ICE-based target, deliberately left that way.** The `arspidump` cheat dumps the whole table to `pidump.txt` for this kind of analysis. `Racer` recomputes at spawn with the same function, reading the **cached** flag selection used (`ModelElectricCache`, falling back to `ARS.IsElectricModel` for a car the roster never scored), so **the leaderboard number equals the selection metric**.

## Gs-aware preview steering (lane error blend) — moved out of AGENTS.md

**This design is LIVE again** — the authority chain that contained it was restored from `1f4516d`, so the lane error blend and the proportional lane conversion are running. (They had been dead code for the life of the aim-error PID and were briefly deleted along with it.) The notes are kept because they describe what is actually executing, not as history.
- Nose-aimed steering measures lane error at the car's position, but at speed centrifugal force (already measured by `ProjectAhead`) curves the real path, so it overshoots. The lane error in `ComputeSteering` therefore blended legacy (at the car) with the **0.5 s Gs-aware projection** (`LookAhead.HalfSec` + `ProjectAhead(0.5f)`, a hardcoded local half-and-half — there was no knob); the **1 s** slice is the off-track cap's read, not this one.
- **Lane steer conversion (proportional, `b333dc4`)**: lane error (metres) → steer angle by a **flat degrees-per-metre gain with no ceiling**, halved (3 → 1.5 °/m) when heading to the outside of a tight curve — a two-value step, **not** a speed-scaled clamp. An earlier revision of this line claimed "a ceiling that eases with speed (descending-input Remap)"; the code has neither, and the live method's own comment says "no ceiling". The old `atan2(laneError, lookahead)` is gone: its gain was `1/lookaheadDist` with lookahead = speed/grip, so authority shrank exactly when speed rose or grip fell. A NaN guard sits before the clamp. `LaneGainExponent` is a dead field — declared, never read, and in no ini (it is not a save-compatibility key).
- **Physical repulsion** (velocity-oriented box, separate from walls): inside it, react only to rivals **actually closing laterally** and **add** a steer-away term to the lane steer — never overwrite it (overwriting broke the lane steer: parallel traffic made the sign filter coin-flip and replaced the bias with ~0). Magnitude scales with closing speed × distance.
- The projection read is one frame stale by design (`RunTimedCore` runs before `ProcessTick` refreshes `AccelerationVector`) — same staleness all projection consumers accept.

## Corner outside approach — the release window (moved out of AGENTS.md)

**The release is a flat time before the entrance, not a width-scaled one.** `ComputeCornerTargetLane` gates the hold on `timeToEntrance`, and the window is `[OutsideReleaseSeconds, OutsideReleaseSeconds + 3 s]` — so the outside phase is always 3 s long and retuning the release **shifts** the whole phase rather than lengthening it. `timeToEntrance = fwdToEntrance / max(speedMps, 1f)`, where `fwdToEntrance` is a **node count** (treated as metres; measured spacing is near but not exactly 1 m — see the track-facts line in `AGENTS.md`; modulo-wrapped on circuits): a straight along-track distance over the speed the car has *now*.

- **Driven: 0.5 s let go too late to help the apex; 1.05 s has the cars touching the apex better** (driver-verified), which is why the value moved. Release distance at 1.05 s is ~9 m at 20 mph, ~19 m at 40, ~28 m at 60, ~47 m at 100, ~70 m at 150.
- **The current-speed divisor makes it release early under braking, never late.** The real remaining time exceeds `d / v_now`, so the car always has slightly *more* than the nominal time left — the safe direction — but the error grows with the nominal time (~0.3 s early in a hard stop from 100 mph, versus tens of ms at 0.5 s). Dividing by a predicted entrance speed is the fix if it ever reads short.
- **A separate hard kill at `fwdToEntrance <= 2` clears the latch**, so a released hold cannot re-engage mid-corner. It beats the time gate only below `v ≈ 2 / OutsideReleaseSeconds` (~1.9 m/s at 1.05 s), i.e. it is a crawl-speed backstop rather than the normal release.
- **`OutsideReleaseSeconds` is a `static float` with no writer** — effectively a constant, left mutable; it is not a menu item and not a save key.
- The entrance is the corner's own: `c.StartNode` when the track file supplies it, else `apexNode - c.LengthStart`. Returning `0f` means *no override* — the caller keeps the high-speed line's answer, and the car's own lane when that has none — so the release hands the car to the inside line, not to the centre (`Racer.cs:413-417`).

## Steer-In Bias — the deliberate skew on the steer ceiling

**The one knob that is knowingly not physics.** The ceiling is computed 1:1 (vanilla curve vs Ackermann, whichever is lower) and then the AI Settings **Steer-In Bias** adds a fixed number of degrees, floored at half the geometry and clamped to the car's lock (`Racer.cs`, `ApplySteerLimits`). It is **additive, not multiplicative, and that choice is the whole design**: a multiplier scales with the number it multiplies, so its absolute effect is largest at low speed (+3.8° at 20 mph on the ×1.2 end) and negligible at speed (+0.15° at 100 mph) — the opposite of what "steer in" needs. A bias applies the same degrees everywhere, so it is proportionally largest exactly where the ceiling is smallest, i.e. at speed, where a couple of degrees dwarfs a sub-degree geometric limit. Driven and kept in the positive direction: the negative half saturates against the floor above ~70 mph, which is what made it the less useful end.

- **The floor is not optional.** `geometry + bias` can go negative at speed (0.76 − 2), which would invert the clamp, and even exactly zero is a car that physically cannot steer — so the result is held at **half the geometry**.
- **Wiring is the `SteerDampingScale` pattern, four places**: the static in `AutosportRacingSystem.cs` assigned in the item's own `ItemChanged` (a `Racer`-read static must be, or the save only lands on restart), `SaveRacerSetting` into `Menu-Settings.ini`, the `LoadSettings` read, and the `SettingsRepair` `KeySpec`. A numeric key **snaps an out-of-range stored value to the nearest offer**, so a hand-edited value cannot survive a load.
- **The range is deliberately not recorded here** — it is a tuned value; the options array and the `KeySpec` are the source of truth.

## Logging — levels, and why `None` is the default

`LogImportance` is a **floor**, not a switch: `Log()` returns when `LogLevel > i`. `None` is therefore deliberately the **last (highest) enum member**, so it silences every level through that same test with no second branch — and it is the **shipped default** (code static *and* `SettingsRepair` KeySpec), so a fresh install does not hammer the user's disk with routine lines. Levels persist by **name**, so adding the member renumbers nothing and an existing install keeps whatever it had.

Two writes survive it, both deliberate:

- **The session banner** (truncate + separator) is written in the ctor **before `LoadSettings`**, so it cannot consult the stored level — 2 writes a session. It is also what stops a stale log from a previous session reading as current evidence.
- **`forced: true` calls**, which are all error paths: settings repair, model and ped load failures, the `OnTick` catch, and the bridge probe. Keeping those is the whole reason `None` is a floor rather than a hard kill — `VerifyScriptBridge` runs *before* `LoadSettings`, so at that moment the level is still the code default, and a suppressed forced line would make a bad SHVDN asi/dll pairing completely silent in our log. That is also why the release README's "the log names the reason" stays true under the default.

Verified in game the cheap way: with `None` the live `Log.log` is exactly the two banner lines plus the single forced `Initialization complete.` line.

## Crash triage — Rockstar writes the dump, and this install has a recurring crash

**Rockstar's own handler captures a game crash, so there is a record even when Windows reports nothing.** A crash writes a minidump plus a context file to `%LOCALAPPDATA%\Rockstar Games\GTAV\CrashLogs\`:

- `<guid>.dmp` — a **user minidump** ("Only registers, stack and portions of memory are available"). Its own structures are readable without a debugger: the **exception stream** gives the exception code, the faulting address, the faulting thread id and — for an access violation — `ExceptionInformation[0]` = read(0)/write(1)/execute(8) and `[1]` = the address touched; the **module list** resolves that address to module+offset; each thread's **stack range** is in the file, so scanning it for pointers into module ranges gives a crude backtrace. The Windows Application log stays **silent** for these (no `Application Error`, no WER, no `%LOCALAPPDATA%\CrashDumps` entry) — a missing WER event is not evidence that nothing crashed.
- `crashcontext.log` — the **last** crash only (it is overwritten), with game state at the crash: `Game State`, process uptime, frame, player/camera position, mission/ambient ped and car counts, pools, streaming. Useful for "what was the session doing", useless for older crashes.

**A real unwind needs a debugger, and the CLI is one install away**: `winget install Microsoft.WinDbg` registers execution aliases in `%LOCALAPPDATA%\Microsoft\WindowsApps` — **`cdbX64.exe`** is the classic engine and runs headless. `cdbX64.exe -z <dump> -y "" -c ".ecxr; k; !analyze -v; q"` gives the faulting instruction with operands, the properly unwound stack (x64 unwind info comes from the image, so game frames unwind without symbols), and the `AV.Type` / `WRITE_ADDRESS` / `FAILURE_BUCKET_ID` verdicts. `GTA5.exe` has no public symbols, so a game offset **cannot be resolved to a function name** — module+offset and the call chain's offsets are the fingerprint to compare against, and the bucket reads `INVALID_POINTER_WRITE_c0000005_GTA5.exe!Unknown` for game-side null writes.

**This install's recurring crash (three occurrences, one signature).** `GTA5+0x652263`, `mov byte ptr [rdx+rcx+10h],al` with `rcx = rdx = 0` — a **one-byte write to address 0x10, i.e. into a null object's field** — from a thread rooted at `kernel32!BaseThreadInitThunk`. The unwind is **18 frames, every one of them `GTA5`** (no mod module, and not JIT-managed code), and it is byte-identical across all three: `0x652263 → 0x63c7e3 → 0x638fab → 0x6416cc → 0x168e909 → 0x16946c4 → 0x169b630 → 0x169b7be → 0x16a2de5 → 0x8157dc → 0x1687bad → 0x168739f → 0x28574 → 0x21c4b → 0x1686fa8 → 0x13cc → 0x1344e07 → 0x187f5d0`. Only the ASLR slide differs. Sessions: **08-15, 09-04 and 09-19**, all with `ARS.dll`, `LemonUI.SHVDN2.dll`, `NativeUI.DLL`, `TrainerV.asi`, `RTHandlingEditor.asi` and `HandlingReplacement.asi` loaded (the newest session additionally carried `HandlingIsolation.dll`, `HandlingIsolationDemo.dll`, `ModManager.*` and `NewChaseCam.dll`, so those are not its cause either).

**What that fingerprint does and does not settle.** It **exonerates any change made after 09-04** — the same crash predates it by five weeks, which is the cheap way to answer "did I just cause this?" for a code path that was not previously suspected: compare the faulting instruction *and* the call chain against the older dumps rather than reasoning about coincidence. It does **not** exonerate the mods present in all three sessions, ARS included: a deterministic null write in game code is the usual shape of the game reacting to an entity a script deleted or invalidated behind its back (the `*Delete()` / teardown / script-reload lifecycle), so if it needs chasing, the repro candidates are a **scripts reload mid-race** and the **race-end entity cleanup**, not the raw memory writes. Other crash modes already on file in the same folder: `0xE0434352` (a CLR exception faulting in `KERNELBASE.dll` — a managed script throwing on a thread that kills the process, four occurrences) and `0x80000003` (int3 breakpoints, five in one 09-12 session — hooking/debug tooling, not a game fault).

**Possible misleading load failure — an external USB hard disk (observed once, not reproduced).** With a plain external HDD connected, GTA5 launched straight into a fatal `ERR_GFX_D3D_SWAPCHAIN_ALLOC_2` dialog and stopped responding; disconnecting the disk made the game load. WER already held earlier `AppHang_GTA5.exe` (`AppHangB1`) entries, so the condition is neither new nor ours — but the disk stays a **possible** cause, not a rule, until reconnecting it brings the failure back. The trap is the error's name: it points at the DXGI swapchain and steers diagnosis to D3D/DXVK/display, while the hang it reports is a stalled main thread, which is the shape a slow or failing disk produces while the game enumerates drives at startup.

**Clearing the C# mods for a pre-script load failure is cheap and decisive.** On the failing launches `ScriptHookVDotNet.log` stayed stale while `ScriptHookV.log` and `asiloader.log` were rewritten, so the .NET script domain never started and no SHVDN script ran — ARS included. Same discipline as the crash fingerprint above: establish the load order before reasoning about whether a recent change caused it.

## Vehicle memory layer — one implementation, memoized scans

**`VehicleMemory.cs` owns every offset and every pattern scan.** The four control-struct setters, the handling-struct readers and the shared AOB scanner all live there, and `Racer` calls nothing else: the `ARS` class's parallel copies — four setters with their own static offset fields, a second `FindPattern`, `GetHandlingPtr` and three dead getters — were deleted with it. Three of the `ARS` versions were unreachable, and **`ARS.SetThrottle` was the only write path in the codebase with no `CanWeUse` guard**, dereferencing `handle.MemoryAddress` unchecked — the exact shape of the `NullReferenceException` a ScriptHookVDotNet maintainer reported against the tracker's issue #8 after a game update moved the pattern.

**The scanner is memoized, and that is the load-bearing part.** `FindPattern` caches per `pattern|mask` in a static dictionary, which is sound because the module base cannot move inside a game process. Before, an **unmatched** pattern bought a full module walk *on every call*, and every caller is per-tick and per-car — the four control writes plus grip, steering lock, downforce, handling flags and the wheel pointers. On a build where the pattern moved, that would have presented as a **frozen game** rather than as "the brakes don't work": on the order of a hundred module scans per tick across a full grid. The cache reduces a miss to a dictionary lookup, so the failure mode is degradation instead of a hang.

**Two misses report once, and forced** (`LogImportance.Error` with `forced: true`, so Log Level `None` cannot hide them): the control pattern (*"ARS cannot drive the cars"*) and the handling pattern (*"grip, steering lock, downforce and handling flags all read as zero"*), both naming `Game.Version`. Every other pattern miss stays at `Info` on purpose — the wheel-power pattern has a documented `0x1D8` fallback, so its absence is not an error.

## Randomness helpers — the exclusive max, and what it silently costs

**`ARS.GetRandomInt` is `Random.Next`, so its `max` is EXCLUSIVE.** An *index* bound written `Length - 1` therefore loses the last element for good: that is how Steel Gray in `_randomColors`, the last matching Menyoo tuning file and the last `StreetRacerModels` ped were unreachable, while index bounds written as the length itself, and every *jitter range* (`(10, 50)`, `(0, 500)`), are correct as they stand. The helper now says so where it is declared — check that, not the call sites, before "fixing" a `-1`.

**The sweep above missed five more sites, all in `SmartTuner`** (`9517976`): the style pick, the chosen group's livery options, `veh.SetMod(slot, random(0, count))`, the palette pick and the matte pick each passed `Count - 1`, so the last style, the last livery of every group, the last mod option of every slot and the last palette and matte colour could never be chosen. They now pass the length — so when this trap is next suspected, grep **every** `random(0,` call site rather than trusting the list here.

**The shuffle idiom is `random(0, i + 1)`**: `Tips.cs` and `GridBuilder.cs` have it right, and `VehicleSelector.Shuffle` was a character short — passing `i` gives Sattolo's algorithm, uniform over *cycles*, so a shuffled list could never keep its own order and a two-item list always reversed. **One off-by-one of this family is deliberately left in place**: the tip roll is `GetRandomInt(1, Denominator)`, i.e. 1 in `D - 1` against a documented 1 in `D` — a rate, not an index, so fixing it is a tuning decision rather than a bug fix. That decision was tested: the `9517976` audit changed it to `Denominator + 1` and the change was reverted, so treat the line as settled until someone actually wants a different tip rate.

## Cross-session hindsight notes (moved out of AGENTS.md, verbatim)

- **`TrackLoader` sets `Thread.CurrentThread.CurrentCulture = en-US` and never restores it**, so every later `ToString`/`TryParse` on the game thread is silently reformatted — and the track files already carry several incompatible culture conventions. Same family of bug: `TrackFile`'s `int.TryParse(float.ToString())` truncates fractional widths and writes 0 with no else branch.
- **Crest handling has a sign and a home.** `CrestGs` negative = crest / positive = dip; the crest multiplier belongs on the grip-limited decel base, not the grade term, and a positive value must be discarded before the floor. The behind-guard is the **extent test**, not the sign of `toCrest` (`CrestDecelFactor` `Racer.cs:3194` bails when the whole ramp is behind the car), and that is right: a car still inside the crest's extent keeps the portion ahead of it, which a bare `toCrest < 0` guard would wrongly drop. The earlier note calling this a point-to-point bug is retired — the wrap on circuits and the extent test on point-to-point both land correctly.
- **The brake learner's full-pedal threshold sits above the downshift gate, so its own target pushes the car into engine braking it cannot see.** Separately, `Corner.SecondsToEntrance` is declared and never assigned (dead field); the real value is computed locally in `ComputeCornerTargetLane`.

## Durable gotchas — code, helpers, rendering, settings (moved out of the project memory, verbatim)

**Trigger**: inverted gate, De Morgan, negated filter, early continue, Remap, NaN, dead null-check, OnTick pause, positional Options enum, `DrawMarker` budget, marker rotation and pitch, prop `RightVector`, streaming ptfx.

- **`if (1 == 2) return;` is an INVERTED gate — it disables nothing**, because the return only fires when the condition is true and it never is. Correct idioms are a bare `return;` or the block form; this bit the start-line flare disable (`bdd1b29`) for weeks.
- **Remap with a descending output range + `clamp=true` is inverted** by `Clamp` when `min > max`, and NaN compares less-than-anything. Keep output clamps ascending and use a descending *input* range for a reversed map.
- **NaN discipline**: `Clamp(NaN, -limit, +limit)` returns the min bound, i.e. instant full-lock — guard steering outputs and any clamp input that can be non-finite. Never hand a non-value sentinel to a *seeding* getter either, or it writes the sentinel into the ini.
- **An early-continue guard is the accept filter negated, so De Morgan inverts its NaN case**: `!(A && B)` is `!A || !B`, and a NaN makes every comparison false — the filter `Distance <= 30f && Gap < 0f` drops a NaN rival, while its rewritten guard `Distance > 30f || Gap >= 0f` does not fire and passes it. Rewriting a `Where` into a loop keeps the positive accept form (`bool closes = ...; if (!closes) continue;`), which a NaN fails exactly as before and which reads better besides (`Racer.cs` card scans, `601313c`).
- **A null-check on a freshly `new`-ed object is dead code.** Two "cannot find file" popups lived behind `if (new XmlDocument() == null)` while the real failures *throw*, so those paths have **no** error handling.
- Synchronous setup work can pause `OnTick` and temporarily suppress per-frame debug visuals; make it incremental if that matters.
- **`Options` enum values are positional**, so retiring a member renumbers the rest and one must never be persisted or exchanged as an int. Nothing does today, but re-check before any numeric consumer appears.
- **`World.DrawMarker` has a per-frame render budget**: markers past it are **silently not drawn** and draw order decides who loses, so long debug geometry belongs in `DRAW_LINE` instead. The budget is shared with every other marker the script draws that frame, so a visual can break because something *else* got greedy.
- **A marker's rotation vector collapses at a 90° middle slot**: with the middle component at 90 — the value that lies a chevron flat — the first slot yaws and the last two roll in opposite senses, so **no single slot can pitch it**, however many are tried; three builds went into guessing which. Pitch a marker by tilting the `direction` vector it faces along and leave the rotation at the flat pointing configuration (the input trail's chevrons, `6111f6c`).
- **Two traps the flare rebuild exposed, both reusable**: a prop's own `RightVector` is perpendicular to *that prop's* forward, so an offset applied after its heading is turned 90° comes out parallel to the track — offset from the source direction instead; and a **named ptfx asset streams between frames**, so requesting it in a same-frame loop can never succeed — queue the entity and attach it from a tick (`TrackLoader.TickQueuedFlares`), logging a failed start rather than swallowing it.
