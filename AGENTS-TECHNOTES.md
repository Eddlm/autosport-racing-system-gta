## Nitrous system facts (researched, The Contract-era natives)

- **Nitrous system facts (researched, The Contract-era natives)**: "vehicle has nitrous" = **vehicle mod slot 17** (`VMT_NITROUS`) — detect with `GET_VEHICLE_MOD(veh, 17) != -1` (already in SHVDN2's Hash enum; what LS-Tuners-style shops and trainers write). All nitrous natives are plain game-binary VEHICLE natives (SP-safe, raw-hash calls): `SET_OVERRIDE_NITROUS_LEVEL` 0xC8E9B6B71B8E660D (**must pass all 6 args** — 2-arg calls zero out level/power/recharge on b2060+), `FULLY_CHARGE_NITROUS` 0x1A2BCC8C636F9226, `CLEAR_NITROUS` 0xC889AE921400E1ED, `IS_NITROUS_ACTIVE` 0x491E822B2C464FE4 (BOOL, boost firing now), `_GET_REMAINING_NITROUS_DURATION` 0xBEC4B8653462450E (float charge), `SET_NITROUS_IS_ACTIVE` 0x9E566EA551F4F1A6, `_SET_NITROUS_IS_VISIBLE` 0x465EEA70AF251045, `_SET_REMAINING_NITROUS_DURATION` 0x1AD0F63A94E10EFF, `_SET_VEHICLE_USE_HORN_BUTTON_FOR_NITROUS` 0x1980F68872CC2C3D (global horn→nitrous). Installed state persists in mod data; charge is runtime-only per entity. Vanilla SP LS Customs does NOT sell nitrous (Online workshop feature) — in SP, slot 17 is set by trainers/modded shops only. **Verified in-game**: `_GET_REMAINING_NITROUS_DURATION` is useless for detection (always reads ~full, only drops on fire, never recharges exactly — a below-full charge implies a past fire but is unreliable and resets per entity), and trainer-forced nitro has no detectable installed state — the only fire-side signal is `IS_NITROUS_ACTIVE`. **ARS detection is therefore a latch**: `PlayerHasNitro` turns true on mod slot 17 installed, the player firing nitro (`IS_NITROUS_ACTIVE`, probed in OnTick), OR a below-full charge read; it never resets during the session. A silent OnTick probe (no debug display) runs the poll. **Menyoo 2.0 source audit** (cloned `itsjustcurtis/MenyooSP` to `_research\Menyoo2`): Menyoo declares the full nitrous native set but **never calls any of it** — its "Race Boost On Horn" is fake nitro (`SET_VEHICLE_BOOST_ACTIVE` toggled one frame + a raw forward force + hand-rolled NOS PTFX); its "Infinite Native Boost" targets the separate **rocket-boost family** (Oppressor-style, unrelated to nitrous). This explains why trainer "nitro" is undetectable: it never engages the real nitrous system, so neither charge nor IS_NITROUS_ACTIVE can see it; only slot 17 or genuinely-fired nitrous can latch. Menyoo also has **no vanilla nitrous toggle at all** (its `VehicleMod` enum names slot 17 `Unknown17`). Also note an ecosystem hash-name conflict: Menyoo binds 0x465EEA70AF251045 as `SET_NITROUS_IS_ACTIVE` (our notes call it `_SET_NITROUS_IS_VISIBLE`), so trust behavior over name for that hash.

## Two-projection route speed (future idea, 2026-09)

- **Two-projection route speed (future idea, 2026-09)**: the user rates the projection layer very highly — long-term, `followTrackSpd`'s geometric `√(g·grip·r)` could be replaced by a two-projection system: a *true* projection (ballistic `ProjectAhead`, self-calibrating via measured acceleration — no grip-model disagreement) and a *pessimistic* projection at reduced grip ("could I still hold this if the surface worsens?"). Design caveats the rebuild must solve: a projection is a **limiter, not a planner** — it assumes current velocity+accel continue, so it cannot see future braking decisions (the apex braking map stays for long-horizon work; projections cap what the plan may attempt); multi-second ballistic horizons are physically wrong; and a target derived from a projection that depends on current speed risks a self-referential feedback loop (needs damping or latched verdicts). The pessimistic variant's real value is anticipatory: ease speed *before* the edge instead of the current offshoot cap's after-the-fact emergency. Reference pattern: `ApplyOffshootBlend`'s shape.

## TRlat ladder

- **TRlat ladder — the slide-response envelope is parameterized by `Handling.LateralTractionCurve` alone.** Every slide-handling threshold is a fraction of it, handing off in sequence as a slide grows: ×0.2 = steer-limiter grip floor + brake-rampdown trigger (rampdown spans to ×0.4, i.e. 2× gripSteerAngle); ×0.5 = slide-countersteer *priority* blend start (final steer lerps toward "trajectory steering − countersteer correction" — the heading/recovery/side-by-side PD plus yaw damping with the countersteer correction applied, **lane pursuit dropped** — so a slide takes priority over the lane target without ever becoming the steer target itself); ×1.2 = slideScale ceiling (countersteer can reach 120% of slip) + priority saturation. Known band: between ×0.2 and ×0.5 the limiter already treats the slide as beyond grip but the countersteer is still legacy-only — if medium slides still steer inwards, start the priority ramp at ×0.2. The stored per-frame countersteer is `_slideCountersteerDegrees` (Racer), available for debug display.

Related durable lesson (kept in AGENTS.md too): **corrections are corrections — never reuse one as an absolute target.** A value stored as "subtract from the PD" (like `_slideCountersteerDegrees`) carries the *opposite* sign of the steer direction it wants; lerping the final steer toward it as a target steers **into** the slide. This exact mistake inverted the countersteer at full slide priority and was caught in-game 2026-09 (car sliding rightwards steered leftwards, off-track). When blending toward a slide-response target, reconstruct the full target (trajectory terms + correction applied), not the correction alone.

## Steering limit (`ApplySteerLimits`)

- **Steering limit** (`ApplySteerLimits`): **currently a slide-angle limit** — max steer = `Remap(speed_mph, rampSpeed→0, limitAngle → steer lock)`: full lock at standstill, collapsing to the limit angle by the ramp speed (both in code), applied equally for steering-in and countersteer. The limit angle is a small margin plus `max(|slide angle|, grip-based allowance)` (formula in code). The MaxBrake rampdown and MaxThrottle cut remain tied to the limiter. The old **speed-based reduction** (`steer /= 1 + 0.5 * fwdSpeed`, always-on, plus a TRLateral `×0.3` min-steer floor) is **zombie code** — preserved in a `/* ZOMBIE */` comment block inside `ApplySteerLimits` if this slide-angle approach is abandoned. The earlier **empirical peak-memory** system — it learns the steer angle that produced the best *measured* lateral G. The separate **speed-based steering reduction** (`steer /= 1 + factor * (fwdSpeed - threshold)`) and the **steering D term** (`steerKD`) are temporary feel-based carve-outs; both were lowered because the previous values felt overly restrictive/damped, but they are not grounded in measured tire behavior. **Everything is in Gs** (latG = `AverageAcceleration·right ÷ 9.8f`; `_bestLatG` stored in Gs; declared grip ceiling = `CurrentMechanicalGrip`, NOT × gravity — a lingering 9.8× unit bug lived here, never multiply grip by gravity and treat it as G). **The reference is now a linear proportional controller, not an exponential filter**: `ref += (Gs − ref) × gain × dt` (gain ≈ 5 → ~0.2 s time constant), symmetric rise/fall, no deadband — the input is spike-clamped before integrating (a collision impulse must not lift the reference even one frame's step). Utilization (current/ref) drives explore vs exploit: near the peak → exploit (limit = remembered steer + small margin, floored); below → explore (limit = `min(steerLock, bestSteer·1.5 + 2)`, floored — *bounded* per audit MAJOR-3, since full lock would map to ±1 input and make the clamp a no-op). Declared grip is only the spike-rejection sanity cap (`×1.1`). The two old limit systems (grip-saturation formula; slide-angle lerp) are commented out above. Hitting the limit caps `MaxThrottle` (pegged → 0.9, 10° past → 1/s cut). TRlat/declared curves are not trusted. (The `STEERING_AUDIT.md` file this section used to reference no longer exists in the repo; its surviving conclusions are the MAJOR notes above.)

## ShowCheckpoints — full marker details (restored verbatim from b845170)

Each corner renders **two primitives**:
    1. **Standing torus ring** — `(MarkerType)1` (the SHVDN2 enum hides this as `Cylinder` but the prop renders as the classic torus; cast through `World.DrawMarker` rather than raw `Function.Call` to dodge texture-arg marshalling). Anchored **below** `TrackPoints[corner.Node]` (dropped into the ground), X/Y scale = `trackPoints[node].TrackHalfWidth * 2` (full track width, so the ring spans the entire road at the apex), camera-facing. The wrapper does NOT crash like raw `DRAW_MARKER` with `textureDict=""` did — the wrapper sidesteps the marshalling issue.
    2. **Centered exit chevron** — `(MarkerType)20` (`ChevronUpx1` / `PROP_MK_RACE_CHEVRON_01`). Anchored **directly above** `TrackPoints[corner.Node]` (kept centered), lifted above ground (matching FiveM `client.lua:452`). Direction = `(nextApex - apex).Normalized` (zeroed Z); rotation per FiveM `client.lua:466–491`; `faceCamera=false` so the direction vector is honored.
  **LOD strategy**: a corner renders if and only if the node delta from the player is within a window with a small negative grace (so a ring doesn't pop the instant it's crossed; delta = node − playerNode, plain subtraction for point-to-point, modulo for circuits via `ARS.IsPointToPoint`). The player Racer is passed into `DrawCornerCheckpoints(Racer player, …)` — its live `CurrentTrackPoint.Node` (updated each tick by the normal track-position pipeline) gives the player node, no extra scan. Runs from `OnTick` (player found via `Racers.FirstOrDefault(r => r.Driver != null && r.Driver.IsPlayer)`), guarded by a `playerRacer != null` check. FiveM reference is `racingsystem/client/client.lua:393–491`; ARS adapts this to corners-only via `ARS.Corners` instead of every node.

## Pace selection — current state, and two lessons from the window→ranking switch

**Current**: selection is a **ranking** — `VehicleSelector.SelectClosestByPace` does one pool pass, sorts by `|pace − target|` and takes the closest N (shuffled for ties). The bracket, the widen loop (`Options.WidenBracketFill`), `PowerBracketScale` and `VehicleSelector.Select` (plus its never-called `CreateDuplicate`) are deleted; a stale `PaceBracket`/`WidenBracketFill` key in an existing ini is never read, because `LoadSettings` walks the `DebugToggles` **dictionary**, not the enum, so an orphaned key is simply not visited. `Pace Offset` is a fixed signed list (−10..+10, step 0.5, labels like "+2.5"); Relative resolves `playerPace + offset` **once per `InstanceGrid`** into a local, and must never be written back into `PowerTargetScale` — that write-back is the one real trap (it corrupts the persisted absolute target). Pace Mode alone decides the anchor for every grid; `ComputePlayerCarPaceIndex` (the join's old fallback wrapper) is gone with the join override. The b845170-era wording for all of the above (bracket + widen loop, offset −50..+50, `Clamp(playerPace + offset, 0..200)`) is in git at `b845170` if ever needed.

**Lesson 1 — clamping an anchor is inert for a ranking.** Clamping into `[min,max]` cannot change a distance *ordering*: every candidate's pace lies inside the span by construction (same cache), so both distances stay monotonic in pace and the sequence is identical. The fleet-span clamps were load-bearing only for a **fixed-width window** (moving a window's centre changes which cars fit), so they were removed with it. The single surviving span use is a diagnostic log when the anchor sits outside the fleet.

**Lesson 2 — the switch inverted non-finite-pace handling.** A window *excluded* non-finite paces (`NaN <= bracket` is false); `OrderBy` over a ranking sorts **NaN first** (`Comparer<double>` places NaN below every value), so a NaN score would have been preferred — the opposite of before. Root cause: `BuildPaceIndex` filtered grip and mph but **not** `accel`, the one raw stat taken straight from a native and defaulted via `TryGetValue`. The computed score is now validated before entering `ModelPaceIndexCache`. (An infinity would additionally have emptied the Pace Target list: `GetPaceSpan` has no filter, and `AddPowerValues` computes `(int)Math.Floor(Inf / step)`.)

**Kept for the record**: `GET_IS_VEHICLE_ELECTRIC` hash `0xD839450756ED5A80` fills `ModelElectricCache` in `BuildPowerCache`. "TopUpNitrous returns success" was an audit fragment that does **not** exist in any committed AGENTS.md — the nitro-pacing rework (`Racer.NitroChargedLap`, replacing the idle 1 Hz top-up) supersedes that line of inquiry entirely, so it is closed.

## Settings folder — declared inventory + repair (2026-10)

`src\SettingsRepair.cs` is the inventory: which ini files ARS expects, which keys each must hold, and what a healthy value looks like. Three passes run from `LoadSettings`, in an order that is load-bearing:

1. `CreateMissingFiles()` — first, before anything reads a store. Creates `Settings\` and each **foreign** file from a literal template. Also prints the old "check you've installed ARS properly" case, now as a restoration notice.
2. `PruneOwnedFiles()` — still before any store reads its file, so no cached `ScriptSettings` object exists that could later `Save()` a pruned key back into the file. Line-level filter: inside `[MENU]`, a `key = value` line survives only if the schema declares the key; every other line (blank, comment, foreign section) is preserved verbatim. Rewrite goes through a temp file + `File.Replace` so no half-written ini can exist.
3. `CompleteOwnedKeys(...)` — last, **after** the legacy migrations and after the `LoadSettings` reads. Fills missing keys with their declared defaults and normalises rejected values, all through the existing `MenuSettings` API (`Get(key, null)` is a side-effect-free existence probe — `SeedIfMissing` returns early when the fallback is null).

**Why owned vs foreign** — `Menu-*.ini` are written by the menu stores, so the schema can own them outright. `Options.ini` / `DevSettings.ini` / `MemoryOffsets.ini` are hand-editable, and SHVDN's `ScriptSettings.Save()` writes back only the sections/keys it parsed: **comments are lost**, which would destroy the MemoryOffsets header. They are therefore created when missing but never rewritten. `Settings.ini` is a legacy migration *input* (its `[RACERS]` keys seed `Menu-Racers.ini`) — creating it would fabricate legacy state, so it is deliberately not expected.

**Invariant: a created file holds exactly the values the code would use if the key were absent**, so creating one cannot change behaviour. That is also why `Track` and `PaceTarget` are declared *optional* (no default): absence is meaningful for both (no track chosen; and an absent `PaceTarget` is what triggers the fleet-span middle autoselect in `RefreshPowerControls` — writing any default there would silently pick the slowest cars in the fleet instead).

**Value policy**: `Bool` and plain numbers must parse (garbage → declared default); a number with a domain list (`TimeoutSeconds`, `AIRacerAutofix`, `AITuningLevel`) **snaps to the nearest offered value** — an off-list value is what makes the menu silently show index 0 while the file holds something else (the long-standing wart in the Council backlog); list-backed strings (`GridSorting`, `AiNitro`, `PaceMode`) must match a spelling exactly, a case-only difference is rewritten to the canonical spelling, anything else resets to the default; `GridSize` is range-clamped to the same 0..12 the menu enforces. Optional keys (no default to repair them to) are handled by the prune pass instead: a declared **numeric** key that does not hold a finite number has its line dropped, because absence is its healthy state. That rule exists because of a defect caught in-game (2026-10): `RefreshPowerControls` probed `PaceTarget` with `GetFloat("PaceTarget", float.NaN)`, and seed-on-read wrote the **sentinel** — a file containing `PaceTarget = NaN` — which additionally defeated the "absent → auto-pick the middle of the span" branch that key is declared optional for. **Gotcha: never hand a non-value sentinel (NaN) to a seeding getter as its fallback; probe with `MenuSettings.TryGetFloat` (non-seeding) when absence is meaningful.** A wrongly-typed *non-numeric* optional key (e.g. `Track = junk`) is still left alone.

**The inventory** (owned files, `[MENU]` section, in schema order):

| File | Keys (default) |
| --- | --- |
| `Menu-Race.ini` | `Track` *(optional)*, `Laps` (4), `GridSize` (4), `PaceOffset` (0), `PaceTarget` *(optional)*, `ReverseRoute` (False) |
| `Menu-Racers.ini` | `GridSorting` (Power), `TimeoutSeconds` (30), `AIRacerAutofix` (1), `AITuningLevel` (1), `AiNitro` (IfPlayerHas), `UseMenyooSkins` (True), `OverspeedEnabled` (True) |
| `Menu-Settings.ini` | `PaceMode` (Relative) |
| `Menu-DevSettings.ini` | one key per `DebugToggles` entry — the table *is* the schema, so retiring a toggle retires its key automatically |

Foreign files created when missing: `Options.ini` (`GENERAL_SETTINGS` Laps/ReverseRoutes, `CATCHUP` OnlyLastHalf/OnlyBehindPlayer), `DevSettings.ini` (`GENERAL` Hotkeys/LoadAtStart/LogLevel, `CREATOR_DEFAULTS` TracksideModel/TracksideModelFrecuency), `MemoryOffsets.ini` (comment header + three `0x0` offsets). A `Disciplines` key is no longer created or read anywhere — the discipline *selection* filter was retired 2026-10 (see the selection bullet in AGENTS.md); the `<Disciplines>` XML tags remain appearance data for `ApplyCarAppearance`/`CreateDriverPed`/`ApplyDriverClothes`.

Two wrinkles worth knowing: `ReverseRoute` lives in `Menu-Race.ini` (the Race menu's checkbox passes `RaceMenuStore` through the optional `store` overload), yet a `ReverseRoute` key **also** keeps appearing in `Menu-DevSettings.ini` because the load loop reads every `DebugToggles` key from the dev store before overriding that one from the race store — so the dev schema must keep it or the repair and the load loop would fight on every start. And `OverspeedEnabled` has no `Migrate` call at all; it is seeded purely by the `LoadSettings` read (seed-on-read), which is exactly the kind of key the completeness pass now guarantees.

**One resurrection path** (narrow, cosmetic): `InitializeMenu` captures store objects in the `store`-overload checkboxes, and an `arssettings` reload re-runs `LoadSettings` (new stores) *without* rebuilding the menu — so a stale handler can `Save()` a pre-prune in-memory view and briefly bring a pruned key back. The next load prunes it again. Same family as the already-known "`arssettings` reload leaves pace-mode enable-states stale until next refresh".

**What the repair does not do**: it does not validate that a `Track` path still exists on disk, does not reorder or reformat foreign files, and does not touch `Settings.ini`, `Tracks\`, `Vehicles\`, `Drivers\` or `sillynames.txt`.
