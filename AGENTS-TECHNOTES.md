## Nitrous system facts (researched, The Contract-era natives)

- "Vehicle has nitrous" = **vehicle mod slot 17** (`VMT_NITROUS`); detect with `GET_VEHICLE_MOD(veh, 17) != -1`.
- Nitrous natives — all plain game-binary VEHICLE natives, SP-safe raw-hash calls:
  - `SET_OVERRIDE_NITROUS_LEVEL` `0xC8E9B6B71B8E660D` — **pass all 6 args** (2-arg calls zero level/power/recharge on b2060+)
  - `FULLY_CHARGE_NITROUS` `0x1A2BCC8C636F9226`
  - `CLEAR_NITROUS` `0xC889AE921400E1ED`
  - `IS_NITROUS_ACTIVE` `0x491E822B2C464FE4` (BOOL, firing now)
  - `_GET_REMAINING_NITROUS_DURATION` `0xBEC4B8653462450E` (float charge)
  - `SET_NITROUS_IS_ACTIVE` `0x9E566EA551F4F1A6`
  - `_SET_NITROUS_IS_VISIBLE` `0x465EEA70AF251045`
  - `_SET_REMAINING_NITROUS_DURATION` `0x1AD0F63A94E10EFF`
  - `_SET_VEHICLE_USE_HORN_BUTTON_FOR_NITROUS` `0x1980F68872CC2C3D` (global horn→nitrous)
- Installed state persists in mod data; charge is runtime-only per entity.
- Vanilla SP LS Customs does **not** sell nitrous (Online feature); in SP slot 17 is set only by trainers/modded shops.
- **Verified in-game**: `_GET_REMAINING_NITROUS_DURATION` is useless for detection (always ~full, drops only on fire, never recharges); trainer-forced nitro has no detectable installed state — the only fire-side signal is `IS_NITROUS_ACTIVE`.
- **ARS detection is a per-race latch** (`PlayerHasNitro`): set on slot 17, on `IS_NITROUS_ACTIVE`, or on a below-full charge; cleared at each `StartRace`.
- **Menyoo 2.0 source audit** (cloned `itsjustcurtis/MenyooSP` → `_research\Menyoo2`): declares the full set but **calls none of it** — "Race Boost On Horn" is fake (`SET_VEHICLE_BOOST_ACTIVE` one frame + raw force + hand-rolled NOS PTFX); "Infinite Native Boost" targets the separate rocket-boost family; no vanilla nitrous toggle; its `VehicleMod` enum names slot 17 `Unknown17`.
- **Ecosystem hash-name conflict**: Menyoo binds `0x465EEA70AF251045` as `SET_NITROUS_IS_ACTIVE` (these notes call it `_SET_NITROUS_IS_VISIBLE`) — trust behaviour over the name.

### What actually pushes the car (leaked-engine read, build 715)

- **The cheat multiplier is the live lever, for every racer including the player.** `CTransmission::ProcessEngine` / `ProcessEngineCvt` consume `GetCheatPowerIncrease()` on the drive force unconditionally; the only reset is at the end of `CVehicle::ProcessPostPhysics`, i.e. after the step, so a once-per-frame script write is in place when the next drive force is computed. The player's task touches it only inside `#if __DEV` (`USE_THROTTLE_LIMITING_FOR_PLAYER = false`), so retail neither fades nor clears it; the AI go-to task *writes* and *fades* it.
- **The engine's own nitro never activates by itself.** `CTransmission::ProcessNitrous` applies its 1 + 3·power boost only while `GetNitrousActive()`; `SET_OVERRIDE_NITROUS_LEVEL` merely sets `m_scriptOverridesNitrous`, and `m_nitrousActive` has **no true-writer in the engine** — the only setter is the `SET_NITROUS_IS_ACTIVE` native, which ARS never called. So both racers' visible gain today is the cheat 2.5×, not a nitro burn, and mod slot 17 is unnecessary while the override is set.
- **A real burn is a separate change and must replace, not stack**: the override's power 1.0 is already 4×, so 4× × the 2.5 cheat = 10×. Drop the override power to 0.5 for the window (2.5× total) and call `SET_NITROUS_IS_ACTIVE` to get flames, sound and HUD. Filed as `nitrous-native-burn` in `AGENTS-BACKLOG.md`.
- **The bottle is self-charged at fire** — `FULLY_CHARGE_NITROUS` inside `StartNitrous`. The old 1 s top-up loop, `NitroChargedLap` and `TopUpNitrous` are removed: that gate refused the player's fire in the second after every start or finish line, but removing it did **not** restore the player's burn (driver, build 715), so the remaining fault is upstream of the charge — filed as `player-nitrous-fire` in `AGENTS-BACKLOG.md` with the suspects and the log lines that separate them.

## The Gs correction reaches the player as power, not as pedal

GTA lets an uphill car accelerate beyond what its wheel power should produce, measured as `measuredGs - wheelGs - 0.1`
(`VehicleData.OverspeedExcessGs`, sampled at ~3 Hz). The AI's answer is a pedal cap — `MaxThrottleFromOverspeed`, glided
at 3.5/s down and half that back up. **The player's pedal is not ARS's to cap**, so the same glided level is multiplied
into `CheatPowerIncrease` instead: for an input the engine reads as a full 1.0, cutting the drive force is as close to
capping the pedal as the mod can get, and it costs the same thing — acceleration, not speed.

Two details that are not the same on both sides, and must not be flattened:

- **The arm test.** The AI arms on its own steer command under 2°, which ARS writes and can read. The player has no such
  command in ARS, so theirs arms on **lateral gs** under 0.25 — the same "barely turning" the command test allows, read
  from what the car is actually doing. Using `Control.SteerDegrees` on the player would read a stale zero and arm
  through every corner.
- **Both read the same level**, so a future change to the cut rate or the start threshold moves the AI's pedal and the
  player's power together. The `Player power cut` log line (2 s, only while below 0.99) is the only read-out that the
  player's side is biting.

## Contact avoidance reaches past the boxes

`Rival.CombinedSize.Y` — half of each car's length plus a metre ahead, a quarter behind — is what **touching** means, and
it is the right number for classifying a relative position and for the side-by-side match. It is the wrong number for the
steer-away term, which used the same half-sum plus a metre: the moment a rival left the box, the push stopped looking at
it, and that is exactly when a car that has just been passed starts moving across the nose. The box answers "are we in
each other"; the push needs "can he be in my way", and those are different distances.

The reach is now the box **plus `ContactPushReachSeconds` 0.3 of the car's own travel**, capped at 20 m, applied only to
rivals **ahead** — a rival behind is the rival's problem, and the behind case keeps the bare box. Own speed rather than
closing speed is deliberate: two cars at the same speed have zero closing, and the same-speed case is the one where the
leader drifts over without ever approaching.

## `Remap` and the descending-range trap

`ARS.Remap(x, in_min, in_max, out_min, out_max, clamp)` computes the line and then, when `clamp` is set, runs
`Clamp(r, out_min, out_max)`. `Clamp` tests the **minimum first**, so a descending output range (`out_min` > `out_max`)
returns `out_min` for every value below it — the result is a constant, and a silent one. This pinned the projection's
throttle cap at 1.0 for two builds before the log gave it away (`cap=1.00` with `outside > half`).

**The rule: write the remap ascending on both sides, then `clamp` is honest.** A mapping that reads naturally as
"1.0 at three metres, 0.5 at contact" is `Remap(gap, 0, 3, 0.5, 1, true)` — same function, no inversion, clamps
correctly.

**Audited 2026-10-23: 23 calls, 12 with clamp, none broken.** Every clamped call is written with an ascending output
range — several have a *descending input* range (`Aggression` 100 to 0, the steer ramp's end-to-start, the off-track
mph), which is harmless because `Clamp` only ever sees the output. One call's ordering depended on a fact about the
model rather than on the code (`GetWheelBase`'s dimension heuristic returns width at 0 degrees and length at 90, so it
needs length > width); it now clamps the input and remaps unclamped, so a vehicle measuring wider than it is long
cannot collapse it to a constant.

**The exception:** a mapping that is genuinely descending in the world (the projection's cap, 1.0 at the edge falling to
0.0 beyond it) cannot be written ascending without negating its input. There the rule is the other one: clamp the input
and remap unclamped — `Remap(Clamp(x, lo, hi), lo, hi, out_hi, out_lo)` — which is what that site does, and its comment
says why. Prefer the ascending form wherever the physics allows it.

## The two lookaheads — same quantity, two planes, and why they stay two

Two systems read the road ahead every tick and each derives its own governor. They look redundant and they are not.

| | Route curvature (`RouteRadiusSampled`) | Crest / dip (`CrestGripSpeedFactor`) |
|---|---|---|
| Plane | horizontal (X, Y) | vertical (horizontal arc length, Z) |
| Quantity | the route's turn, `R = 1/κ` | the profile's bend, `ΔG = v²·κ/g` |
| Estimator | least-squares circle through **4** points | **Menger** curvature through **3** points |
| Span | `2·v/grip` **nodes** | `1 s` and `2 s` of travel, in **metres** |
| Advance | index arithmetic (`carNode + k`) | metric walk (`NodeAhead`) |
| Symmetry | left and right alike | **lift only**: `ΔG > 0` (compression) is discarded |
| Output | a radius, fed to `√(μ·g·R)` | a factor, multiplied into both corner and route speed |

**Every lane colour has its own height, and the ladder is named (driver, 2026-10-23).** The lane chain draws four lines over the
same strip of road, so where two offsets agree the colours bleed into one. The heights are now four constants in
`AutosportRacingSystem.cs` - `LaneHeightCentre` **0.075**, `LaneHeightCurrent` **0.100**, `LaneHeightCarried` **0.125**,
`LaneHeightRequest` **0.150** - one step of 0.025 per lane in chain order, low enough to be read against the road, and clear of
the 0.5 where `DrawTrackCrossingLine` puts the corner, crest and radius checks. The edge chevrons, the one drawing that sat at a lane height (0.2, over the green line where a car runs
wide), moved to 0.6.

**`fTractionCurveMax` and `fTractionCurveLateral` are a PAIR and move together (driver, measured, 2026-10-24).** The first is peak
longitudinal grip in G, the second is peak slip **angle** in degrees, and the two are not independent in practice even though the
meta declares them separately: the reference point where a car feels right is **2 G with 22 degrees**, and the pairing scales
about **1:1** - roughly **11 degrees per G**. Drop the grip and leave the angle and the tyre is too *flexible laterally*: the car
does not grip less in a straight line, it slides constantly, because 22 degrees of peak slip angle is a long way round for a tyre
that only makes 1 G. Measured case: **1 G with 22 degrees slides on its own**; the same 1 G with about 11 degrees behaves.
Authoring rule: halve the grip, halve the angle; raise one, raise the other. ARS reads the angle as `LateralTractionCurve` (degrees)
and the grip as G, so a car authored outside this pairing also invalidates every threshold ARS compares against the curve - the
slide blend's band, `SlidingFraction`, the steer ceiling and now the ABS taper all assume a peak at the authored angle.

**The ABS switch is OFF and greyed, and the taper is behind it (build 883, 2026-10-24).** `AbsEnabled` now defaults false and the
reader forces false whatever the stored key says, because the checkbox is greyed: a restored value would be a switch the user cannot
see and the car would still obey it. The menu copy is "GTA forces native ABS on non-player driven cars. I'm working on undoing that."
The taper itself is unchanged behind the flag and comes back with one line. Why it is off: `AGENTS-FLAGS.md` and
`AGENTS-VEHICLE-STATUS.md` - `Automobile.cpp:3775` re-grants `WF_ABS` to every `STATUS_PHYSICS` car each tick, and the engine's own
clamp holds slip at 0.6, so on an AI car our 0.5 knee has 0.1 of slip to work in.

**The ABS guard is instrumented, and its response rate is the open question (2026-10-24).** `ARS.MinWheelRotation` publishes the
smallest per-wheel `m_fRotAngVel` (`wheel+0x170`, rad/s, absolute value) and `UpdateBrakeReasonCaps` logs
`ABS <car>: locked=.. minWheel=.. rad/s cap=.. pedal=.. mph=..` at the moment a wheel crosses `AbsLockRadPerSecond` 2, rate-limited
to twice a second. Why it matters: the detector is instant, but `Control.MaxBrakeFromABS` **glides** at
`AbsBrakeFallPerSecond` **0.2/s**, so from 1.0 to the `AbsBrakeFloor` 0.2 takes **four seconds** - the wheel is locked long
before the pedal lets go. A car with no ABS of its own is the first case where that shows, because the engine does not clamp
`+0x174` for it. Numbers for the decision: 0.2/s is 4 s; 2/s is 0.4 s; 6/s is 0.13 s, which is ABS-shaped. The rise is a
separate question - slow reapplication is the point of ABS.

**The brake learner's verdict is the arrival speed, not the pedal (driver, 2026-10-23).** The old law scored the *share
of the braking phase spent above 0.9 of pedal* against a 20 % target and multiplied the factor by the error. That asked
the factor to reproduce a braking **style** rather than a braking **point**: a corner taken exactly right with a gentle
pedal scored zero and kept inflating the factor every lap, and the route brake cap meant the pedal could not reach the
share the target wanted even when the corner was perfect. Now there are two verdicts and they are the ones already
measured: **inside `BrakeEntryDeadbandMps` (5 mph) of the speed the corner asks for at the entrance, the factor gains a
flat `BrakeGoodArrivalStep` 0.05**; above the deadband the existing deducer applies its cut, `BrakeEntryFactorStep` 0.2 for
20 mph over, linear beyond. The skid verdict is untouched. The whole full-pedal machinery went with it - `_brakeSampleSeconds`,
`_brakeSampleFullSeconds` and their commit copies, `BrakeSampleThreshold` 0.25, `BrakeFullPedalThreshold` 0.9,
`BrakeFullFractionTarget` 0.2 - and so did the **Brake Learn Gain** setting, which stepped the old share error and has no
meaning now; the step is a constant in one place. The learner therefore searches: credit until the arrival goes hot, cut
until it comes back inside the band.

**The corner plan carries no terrain factor, and the route carries all of it (driver, 2026-10-23).** `cornerSpd` is
multiplied by neither the slope's `sqrt(hill grip)` nor the crest's `routeCrestFactor`; `followTrackSpd` is multiplied by
both. The reason is where each factor is **sampled**: the hill angle is the mean grade over the 1.0-2.0 s window ahead of
the car and the crest is read at the 1.0 s and 2.0 s nodes ahead of the car, so multiplying a corner target by them made an
apex two hundred metres away rise and fall with the road under the wheels — and a crest passed on the way in sank a target
that had nothing to do with it. Found from a corner that read as strangely slow on every lap while its geometry was
ordinary; with the corner side removed it took its authored `sqrt(grip * g * radius)` again and the car was faster through
it, while the route term went on cutting the speed at the crests the car actually crosses. `MaxCrestLift` (0.1-2.0 g,
default 1.0) is live again on the route, which is the only place its multiplier survives. The falsifier: a corner taken
**too fast** while the car is going over a crest — that would say the route term is not enough when the corner itself sits on
a crest, and the fix would be a slope factor read **at the apex node** from `TrackPoint.Elevation`, not the car's sample
restored. Unused `apexTargetWithCurrentRouteGrip` was deleted with it: a copy of `_cornerSpd` that nothing read.

**The span bases differ on purpose.** Curvature is scaled by grip because it stands in for braking distance, which is; a 2 g car stops in half the distance, so it looks half as far. Lift is a **time** phenomenon — how long the wheels stay unloaded — so it must not scale with grip. Merging the spans would either blind a high-grip car to a crest 2 s out or make a low-grip car sample a vertical profile it never reaches.

**The estimators differ for the same reason.** A four-point least-squares circle is stable; Menger divides by `abLen · bcLen · acLen`, so three nearly collinear samples blow the curvature up, and the only guard is `|κ| < 1e-5`. That is the same degeneracy the four-point fit met on a straight and needed a sagitta test for.

**Merging was considered and dropped (driver, 2026-10-23).** The one real gain was density: the elevation side has three points and a single parabola, so two features inside its 2 s window average into one shape the road never had. Sharing the sampler would hand it 4-5 points — but Menger cannot use them; the estimator would have to become a least-squares fit in (s, Z), which moves every `ΔG` and invalidates `MaxCrestLift` until it is driven again. Worth doing only alongside that estimator change, and not before 0.9.

**Two latent faults found while comparing them, neither fixed:**
- `NodeAhead` stops after **200 steps**, which at 1 m spacing is 200 m. The crest asks for `2 s · v`, so the cap binds at **360 km/h (223 mph)** — past every stock car and past almost every mod, which is why it has never shown. It is still the first suspect for a report of a car going light at absurd speed: the far sample would sit 200 m out instead of where the law asked, and the drawn node would agree with it. **Only the crest walks**, so the curvature is not exposed today; the figure that matters if it ever moves onto a metric walk is `2·v/grip` = 200 m at 50 m/s with grip 0.5, which is an ordinary speed — that conversion could not ship without lifting the cap.
- `RouteRadiusSampled` advances by **node index** and therefore treats every node as one metre. Every route in the game comes from the editor (`separationDist = 1f`), so the assumption is structural rather than accidental — but measured across the fourteen shipped tracks the spacing runs **0.78 m to 2.45 m with a 1.00 m median**, so the span is right on average and locally off by up to 2.4x on the longest segments. The four-point fit takes the real positions, so a uneven spread along the arc is what it pays, not a wrong circle: the span is the approximate half. `docs/track-spacing.py` prints that distribution for any route file — run it before and after a track is regenerated. The shape it found on the fourteen shipped tracks is a **skipped step, never a short one**: no segment is under 0.5 m, medians sit at 0.993-1.004 m, and 1.4-4.3 % of steps land at ~2.0 m, which is the generator taking the next candidate when the 1 m search misses.

**Fixed at load (`DensifyRoute`, build 780).** The route is resampled to the metre the file promises: any segment longer than 1.5 m gets evenly spaced midpoints inserted, widths interpolated, and the pass runs after `RefreshRouteTopology` and before `GenerateRouteInfo`, so geometry, apex table, crests and grid all see one spacing. Simulated on the shipped files: F8 2350 -> 2405 nodes with the worst gap 2.001 -> 1.001 m, Figureight 2316 -> 2363 and 2.446 -> 1.389, LSIA 1944 -> 1972 and 2.005 -> 1.011, Highway 2884 -> 2953 and 2.353 -> 1.361. No gap over 1.5 m survives. **Consequence: node indices shift, so a corner's `Nº` in a log or notice is not comparable across this build** — the learned brake factors are in memory per session, not on disk, so nothing is left pointing at a stale index.

**The radius readout is honest, and the radius is an authoring property (verified 2026-10-23).** An independent
circumradius over a +/-5 m window on the raw polylines reproduces what the game reports to within 1.1 m on every corner
checked (33.6 against 33.6, 9.6 against 9.5, 14.8 against 14.9, 26.1 against 26.0, 120.0 against 118.9), so
`SmoothedRadius` is measuring the road and nothing else. What the same check found beside it matters more: Figureight and
the F8 rebuild trace the **same layout to 0.1 % of length** and their corners differ by **13 % to 39 %** in radius
(39 % wider at one, 26 % tighter at another, 29 % wider at a third). That difference is in the XML, not in the estimator,
so two generations of one circuit yield corner speeds that disagree by roughly a third and neither is "the" answer. Two
consequences: never compare radii across a regenerated track, and when a car enters a corner badly the trace is the first
suspect, not the curvature maths. The corner **count** is stable across the rebuild (ten corners and one blur cull each,
with the cull landing at R 162.0 and 162.8), which is what a screening rule that reads shape rather than size should do.

**Measured A/B on one layout (driver, 2026-10-23).** Figureight rebuilt as F8 by the current editor: same circuit to 0.1 % (2379.0 m against 2381.5 m), 2350 nodes against 2316. What the newer editor fixed is **precision**: the median step goes 1.0034 -> 0.9999, the shortest 0.8202 -> 0.9174, and the worst **2.4462 -> 2.0014**, so a miss is now exactly one skipped step rather than an irregular one. What it did not fix is the miss itself: steps over 1.5 m stay at 2.0-2.3 %, so the skip lives in the step search, not in the stored decimals. The old track was not a bad outlier - it was the same circuit with looser arithmetic.

## Two-projection route speed (future idea)

- Long-term: replace `followTrackSpd`'s geometric `√(g·grip·r)` with a two-projection system — a *true* ballistic projection (`ProjectAhead`, self-calibrating) and a *pessimistic* reduced-grip projection.
- Caveats the rebuild must solve:
  - a projection is a **limiter, not a planner** — it assumes current velocity+accel continue, so it cannot see future braking (the apex braking map stays);
  - multi-second ballistic horizons are physically wrong;
  - a target derived from a projection that depends on current speed risks a self-referential feedback loop (needs damping or latched verdicts).
- The pessimistic variant's value is anticipatory — ease speed *before* the edge, not the offshoot cap's after-the-fact emergency. Reference pattern: `ApplyOffshootBlend`.

## TRlat ladder

- The slide-response envelope is parameterized by `Handling.LateralTractionCurve` alone.
- The two **steering-limit rungs are RETIRED** (allowance base ×0.33, ceiling ×0.5) — replaced by the two-sided corner-geometry ceiling (AGENTS.md pipeline step 4). The formula is kept as history, not as a fallback: **restoring the rungs would *loosen* the limit, not tighten it** — Ackermann sits below them above the ~17 mph crossover.
- Still live: the two **slide-handling rungs** — `SlideBlendStartFraction` and `SlideBlendFullFraction`, both fractions of `Handling.LateralTractionCurve` — plus the `IsFullCountersteer()` pedal gate (`Racer.cs`). The fractions this note once quoted have moved since; read them there, not here.
- Do not confuse either with the removed MaxBrake rampdown threshold (`2 + TRlat × 0.2`) — a different use of the same fraction.
- **Corrected**: `_slideCountersteerDegrees` (once cited as the stored countersteer) **no longer exists** — the live value is the local `countersteerTarget`.
- The blend lerps the final steer toward "damped course steer − countersteer correction"; the correction itself is at **1 × slip**; lane steer is live again.
- **Measured band** (parsed from `Log.log` `TRlat for <car>` lines): ~10.75–12°, drift variants far above (`ISSI8` 21.75°, `DRIFTCHAV6` 28°) — "a slide" is a per-car quantity up to 2.5× apart. The `[1,100]` guard's fallback is 22 — re-check that log line after any handling swap, every ladder threshold doubles if the read falls out of band. **The band is per-fleet, not universal**: the ARS test roster reads 21–23° (`Log.log`: ASBO 22.5, KURUMA 23, WARRENER and zion3 22.5, COMET2 21), so a note quoting ~11° describes another fleet's cars. The steer ceiling is proportional to this value (`Racer.cs:1067`), so one `SteerCeilingFactor` caps a 22.5° car at twice the angle it caps an 11° one.
- **The tyre's slip axis, and what ARS reads on it.** Every wheel publishes `m_fSideSlipAngle`, `m_fFwdSlipAngle` and `m_fEffectiveSlipAngle` (`wheel.h`) on one axis, fixed by `sfTractionPeakAngle = 1.0` and `sfTractionMinAngle = 2.5` (`wheel.cpp`): `GetTractionCoefficientFromRatio` ramps the coefficient to its peak at 1.0 and falls to `fTractionCurveMin` at 2.5, flat past it. The published value is `|fTotalRatio| × 2.5`, the magnitude of the (lateral, longitudinal) slip-ratio vector, so **1.0 is the top of the traction curve and 2.5 is where it goes flat**; in a purely lateral case the effective and the side values are the same number, the lateral ratio being the raw slip angle over the authored `fTractionCurveLateral` with the speed stiffness applied.
- **The three crossings: 1.0, 2.0, 2.5.** The audible skid volume is a *data* curve of the effective value (`SKID_CURVES_FWD_SLIP_TO_MAIN_VOL`, `vehicleaudioentity.cpp`), so its knee is not in the code; the chirp beside it is a **rate** trigger — 32/s of side-slip, player-car only, re-arming when the effective value falls below 0.25 and the brake below 0.25. The only slip **level** the code fixes is the controller-rumble skid test at **2.0** — 3.5 with trigger rumble, and 3.17 for a front-drive car (5.17 with trigger rumble, saturating at 10 or 25). So the game's own line for calling a car a skid is two-thirds of the way down the fall from the peak to the flat end, and the audio's onset is the earlier of the two.
- **ARS is on the same ruler but reads the wrong member of it.** `LateralPeakAtSpeed` is the engine's speed-stiffness law with the same constants (`sfTractionStiffnessSpeedMult = 0.1`, cap `5`, `USE_LOAD_STIFFNESS_MOD = false`), so ARS's modelled peak slip angle *is* the engine's 1.0 — yet the only wheel slip the driving laws read is the rotational ratio at `wheel+0x174`, so nothing that drives sees the lateral or combined value the squeal is made of — the lateral member is readable now, at `wheel+0x1C4`, but only the debug spheres read it. **Measured with those spheres**: at Steer Limit At Speed 1.00 a cornering car's tyres sit near the top of the traction curve rather than past it, so the ceiling's 1.00 is calibrated at the peak — now for the outer wheel, the loaded one, rather than the axle midpoint — and 0.75 sits below it. The ceiling is stated at the outer front wheel, so `SteerCeilingFactor` 1.00 sizes the command at 4/3 of the modelled peak (the outer lands on it, the inner runs past) and the menu's 1.25 top reaches 5/3: the engine's 2.0 line is still beyond anything the menu can ask for, and a car can still run past it because the cap bounds the wheel angle asked for, not the slip the tyre does.
- **The ceiling's measured-slip allowance** (`Racer.cs`). The ceiling in force is the `min` of the model law and an allowance on the tyre's own axis: `SteerSlipLeadShare` over the measured side slip is its floor, the allowance climbs to the whole peak over `SteerSlipClimbSeconds` while the command keeps asking for more than it grants, and falls at the same rate once it stops. The climb is timed to the peak, so `SteerCeilingFactor` cuts the plateau without moving the timing, and the step is `SteerSlipClimbPerSecond * TickScale` — per second, not per pass, so it does not shorten as the grid grows. `SlipPeakCeiling` is the off switch, and a slide sends the allowance to the whole peak rather than bypassing at once, which leaves the countersteer allowance and the damper bypass raising on top throughout. Driven once: swerves read slower, and the climb time was then doubled. **Closed (driver)**: the allowance is a switch that is off and the open question was settled at the outer wheel, so nothing is owed here; `SlipPeakCeiling` is off and the update returns early, so reviving it is one flag.

Related durable lesson (also in AGENTS.md): **corrections are corrections — never reuse one as an absolute target.** A value stored as "subtract from the PD" carries the *opposite* sign of the steer direction it wants; lerping toward it steers *into* the slide (this exact mistake inverted countersteer at full slide priority, caught in-game). Reconstruct the full target (trajectory terms + correction), not the correction alone.

## Steering limit (`ApplySteerLimits`)

- Two side limits, one clamp; it runs **last** in the pipeline.
- `SteerLimitRight` / `SteerLimitLeft` default to `min(vanilla, Ackermann)`.
- Vanilla's curve is `SteeringLock / (1 + k × v)` (the `−5` shift removed); Ackermann is `atan(wheelbase × grip × g / v²)` on a **bone-derived wheelbase** (`ARS.GetWheelBase`: both axle centres averaged, projected on forward, bounded 1–6 m, fallback 2.7). The pair crosses at ~17 mph; **Ackermann owns everything above**. It is the tightest corner the grip allows, and `SteerLimitedSpeed` inverts that same grip and gravity — retune one without the other and the speed plan and the steer cap desynchronise silently.
- **Countersteer is not exempt**: the side the wheel is on is *raised* (gated on the steer-vs-yaw sign test **and** the slide blend engaged) to `Math.Max(ceiling, min(|SlideAngle|, lock))` — a raise that can never lower a limit. This replaced a sign-test exemption that let the countersteer side run **unbounded**.
- **Two order constraints**: the limiter sits after every steering-request writer in `ProcessAI` (the stuck-recovery override writes `Control.SteerDegrees`, not `Control.SteerInput`, to stay inside it); `TranslateSteerToInput` converts the request afterwards — **a steering writer added below the limiter is a silent bypass**.
- The brake release lives in `ConvertSpeedToPedals` (runs first; its consumer, the post-slew `Min`, is there).
- **Grip source is `CurrentMechanicalGrip`, not `BaseMechanicalGrip`**: the base has the downforce term divided out, so it reads *low* on downforce cars and would tighten the cap for exactly the grippiest ones.
- **The declared grip ceiling is `CurrentMechanicalGrip` — never multiply grip by gravity and treat the result as G**, even though the engine somewhere does.
- **A removed system, named so it is not rebuilt blind**: an empirical peak-memory scheme once learned the steer angle that produced the best *measured* lateral G. It was built and deleted — its constants were the only survivors and had no readers left — so treat it as a decision already made rather than an open idea; recover the code from git if it is ever revisited.

## Side-by-side heading match (`ComputeSideBySideSteerCorrection`, `Racer.cs`)

- **The match is one-way**: it applies only while the overlapping rival is moving toward this car's side (the rival's *own* velocity against the separating axis). A rival drifting away is leaving room; this car's own closure stays the rival-walls' business.
- **The side convention, verified**: `+ = right` — `SignedLaneOffset` (`AutosportRacingSystem.cs:550`) and `RelativeOffset.X` / `LateralGap` (`DataStructures.cs:163`) are the same `Cross(dir, WorldUp)` dot; `Cross(forward, up)` really is world-right. `TryPickAvoidanceSide`'s `passLeft` names the side it *passes on*, not the rival's side.

## Lane steer — pure pursuit on the aim, scaled by how far the car is crossed

- **The flat degrees-per-metre P this section described is gone from the code.** The live lane term is pure pursuit on the bearing to its aim point (`PursuitSteerFromBearing`, `Racer.cs`), turned into an angle by the wheelbase, and `LaneGainDegPerMeter` / `LaneSteerOutsidePercent` no longer exist — only the unread `LaneGainExponent` survives.
- **What bounds the lane ask is the crossing angle, not the wheel** (`LaneCrossingThresholdDegrees` / `LaneCrossingShare`, `Racer.cs`): the car's heading against the track direction at the car, turned into a share of the ask by the allowance — `allowance / (allowance + crossing)` — where the allowance is whatever heading carries the car sideways at `LaneCrossingLateralSpeedMps`, so it follows `1/speed` and falls away to almost nothing at speed. Half the ask survives at the allowance and a third at twice it, so it is **a softness scale, not a boundary**: the two rejected shapes were a hard cap on the wheel and a step on the crossing, and this is neither. The wheel angle was the wrong quantity: a couple of degrees of wheel at speed is plenty to cross the track, while a couple of degrees of crossing needs a fraction of one, and the ask that unwinds a crossing is never scaled.
- **Corner entry is exempt, and no schedule could fix that**: turn-in is a crossing on purpose — the car has to point into the turn to rotate — so the limit stands down for the entry itself, from the braking target to the apex, and no earlier (`Racer.cs`). The object being bounded is what fights turn-in, not the shape of the bound, so neither a grip-scaled threshold nor a different curve removes that: the exemption is the lever. **The first cut of the gate keyed on the corner owning the lane at all (`cornerLane`), and the positioning window opens seconds before the corner — so on a twisty track it silenced the limit for most of a lap and the swerve it exists to stop came back.**
- **What stays unbounded**: the side-by-side heading match, the yaw damper and the contact term.

## Pedal map (`ComputeCombinedInput`)

- One linear map for both pedals, **no feedforward**: `Clamp(speedError / divisor, ±1)`, the brake's divisor being the throttle's × `BrakeErrorMultiplier`. ## `vecInertiaMultiplier` — engine translation

`handling.meta`'s `vecInertiaMultiplier` is a **per-axis dimensionless scale on the angular inertia the model already has**, never an absolute inertia: the engine takes the tensor from the model's own collision **bound**, scales it with the mass, then multiplies. It parses into `CHandlingData::m_vecInertiaMultiplier` (`handlingMgr.h:879`; schema `Metadata\HandlingInfo.psc:16`, description "Inertia override"), and the only consumer in the tree is `CVehicleModelInfo::InitFragType` (`VehicleModelInfo.cpp:6318`), reached from `InitPhys` at `:4177` under `if(!GetFragType()->GetIsUserModified())`. After the fragment's mass and inertia are scaled to the handling values (`:6869-6871`), the archetype's aggregate angular inertia is multiplied componentwise by this vector and redistributed across the un-tuned groups (`:6873-6893`); the whole block is skipped when every axis sits within `V_FLT_SMALL_3` of `1.0` (`1e-3`, `rage\base\src\vectormath\vectortypes.h:729`).

A child's baseline inertia is computed from that child's **collision bound**, not the render mesh — `phBound::GetComputeAngularInertia(child mass)` (`VehicleModelInfo.cpp:6215`, `:6224`), the same rule every physics archetype follows (`BaseModelInfo.cpp:1008`), peds and weapons included. The bones the engine pins instead (`SetBonesGroupMassAndAngularInertia`, `:6094`, marking them `tunedGroups`) keep their own values and are **excluded from the scaling** — the nine door slots take one door constant each with their whole subtrees (four doors, bonnet, boot, boot2, two folding wings, `:6241`), wheels take the wheel constants, and the low-LOD/dummy chassis pins exist only to keep those groups out of the mass distribution. Because the multiplier's target is the **total** tensor (`:6886`), the pins never move and the un-tuned body has to absorb *more* than the nominal factor to reach it; the mass-only pins (`SetBonesGroupMass` → `SetGroupMass`, `:6190`) fix a mass but recompute that group's inertia from its bound (`:6215`). So a converted car carries whatever bounds its asset shipped.

**A detached part is the fragment engine's business, not the game's**: the break routines only cut the child out (`fragInst::BreakOffAbove` / `DeleteAbove`, `vehicleDamage.cpp:6481`, `:6550`) and then touch the loose part itself (cloned archetype + extra damping `:6491-6500`), while the vehicle side merely hides the bone for rendering and sets `bPartsBrokenOff` (`CVehicle::PartHasBrokenOff`, `Vehicle.cpp:10817`) — no game code edits the parent's mass or inertia. The car is an articulated body whose inertia is recomputed from its links whenever that configuration changes (`phArticulatedBody::CalculateInertias`: `LandingGear.cpp:714`, `VehicleGadgets.cpp:4543`, `DraftVehicle.cpp:243`, `Vehicle.cpp:12010` — the last because otherwise "some of the doors might fall off"), so a lost part takes its pinned inertia and its offset term with it while the per-child values written by `ScaleUndamagedChildren` keep the multiplier on the survivors. `rage\fragment` is absent from the leak, so the recompute-on-break step itself stays unverified.

One trap on that path: `CPhysical::SetMass` (`Physical.cpp:953-982`) clones the archetype and recomputes inertia straight from the bound (`GetComputeAngularInertia`) with **no multiplier anywhere in it**, so a runtime mass change through that function would silently reset a car's tuned inertia — the fragment break path is the one place I cannot rule it out. No game code writes a vehicle body's mass at runtime (every `SetMass` call under `Vehicles\` targets a detached part, a prop or the parachute), and `GET_VEHICLE_MASS` is registered unused (`commands_vehicle.cpp:16271`).

Axes are *rotation* axes, per the engine's own comments (`Automobile.cpp:1176` pitch, `:1201` roll, `:1299` yaw): **X = pitch, Y = roll, Z = yaw**. Because `InitFragType` runs once on the shared fragment type before any instance exists, the value is baked per **model** — not per instance and not per spawn — so a mid-session handling reload does not reapply it, and the override is gated to bikes, cars, trailers, quads, drafts and the submarine/amphibious cars (`:6875-6882`), leaving planes, helis, boats and trains untouched.

**Omitting the element is not the same as writing `1.0`.** The constructor seeds `(0,0,0)` (`handlingMgr.cpp:1251`) and the schema declares no default, so an omitted tag takes the override branch asking for zero inertia — which is why the dev-only assert at `:6888` reports a target it could not reach.

## Mods, neons and the centre of mass — what a fitted mod can actually change

**Neons have no physics path at all**: the system is a colour plus four on/off flags (`VehicleVariationInstance`, script natives `commands_vehicle.cpp:13027-13212`, replayed in vehicle packets), and the only reference inside `Vehicles\` is an ambient-occlusion/audio offset for the `MID_NEON` bone (`Automobile.cpp:314-315`, applied `:5633-5635`). **No fitted mod anywhere writes mass, centre of mass or inertia** — the sole runtime CoM writer in the whole game tree is the hard-coded trailer hack (`m_vecCentreOfMassOffset.SetZf(-1.0f)`, `VehicleModelInfo.cpp:1448`), and everything else consumes the handling value at model load. So the recurring community claim that neons, skirts or bumpers lower the CoM and reduce lean is false as stated.

The slots that do carry physics are all in `VehicleModelInfoVariation.cpp`: front bumper sets *front* downforce and spoiler sets *rear* downforce, and only when the car has `CF_USE_DOWNFORCE_BIAS` (`:1039-1058`, `:974-1037`). Suspension is the one that answers the lean question — it sets a fake lowering amount (`:945-953`) that the wheel's roll-centre height bias adds **only** under `CF_REDUCE_BODY_ROLL_WITH_SUSPENSION_MODS` (`wheel.cpp:3621-3624`, `:4044-4046`), which is why a slammed car leans less while its CoM never moves. Hydraulics set bounds and rate (`:955-972`), and engine / ICE / gearbox / brakes change power, top speed, gear count and plane handling; side skirts, chassis and the rest have no branch at all. The belief almost certainly rides the mod-shop confound: neons and skirts get fitted in the same visit as the suspension, and the suspension mod is doing the work.

One `[MENU]` section per file, one key per persistable item (buttons never persist); the authority for the exact key set, its defaults and its domains is `SettingsRepair.BuildSchema()`, never a list kept here.
- `src\MenuSettings.cs` (`MenuSettings`) is the store: one lazy `ScriptSettings` per file (never `Load` the same file twice), `Set` saves on every change, `Migrate(key, legacy)` seeds a legacy value only if the new file lacks the key.
- **Live readers** read the stores directly rather than through a copy: `PlaceCars` takes `GridSorting` as the stored enum name (`AutosportRacingSystem.cs:2326`), and the race timeout is read in `OnTick`. The autofix mode is the exception since `f0df8a3` (dev build 628): it is the `ARS.Autofix` **field**, seeded in `LoadSettings` and assigned by the menu, so no settings read sits on the tick path — a value the hot path wants is cached where the key is loaded and written, never fetched per call. The old `ARS.RaceSettingsFile` static and `SaveOptionSetting` are gone; `Settings.ini`/`Options.ini` are retired and deleted after load.
- Lists store **values, never indexes**; dynamic lists restore at population time (`RefreshTrackList` self-heals; `RefreshPowerControls` reads PaceTarget with an `IsNaN` guard). The immersive join point deliberately does **not** save — session convenience, not menu state.
- **LemonUI fires `ItemChanged` for a programmatic `SelectedIndex` assignment.** Read from the IL of `libs\LemonUI.SHVDN2.dll` (1.5.2, the MVID the deployed copy carries; dump it with `~\.dsh\tools\lemonui-il-dump.ps1`): `set_SelectedIndex` calls `TriggerEvent` before `UpdateIndex`, so a restore is indistinguishable from a user change except that it carries `args.Direction == Direction.Unknown` where a scroll carries Left or Right. It fires **only when the index actually moves**, and it **throws rather than clamping** out of range (`'There are no available items.'`, `'The index is under zero.'`, `'The index is over the limit of {0}'`) — which is what the `Math.Max(0, Items.IndexOf(...))` idiom everywhere in this file is holding off. The `Items` setter raises no event but calls `UpdateIndex` → `get_SelectedItem`, whose `Items[SelectedIndex]` is **unclamped**.
- **No restore-path handler is load-bearing**, which is why a global restore-suppress flag was declined: every handler writes back the value just read and `MenuSettings.Set` discards an equal write, the repair pass persists its own GridSorting coercion before the menu is built, and the two cases that did carry a write are already covered — `_carPoolRefreshing` with its explicit save after the block, and the `PaceTarget` autoselect with `RaceMenuStore.Migrate` at `:1548`. `_carPoolRefreshing` is the precedent if a case ever needs suppressing; `args.Direction == Direction.Unknown` is the cheaper check for one handler.

**A menu item and its consumer can name two different stores, so check which store a consumer reads before trusting an item's label.** `Laps` was the case: the knob the menu wrote was not the one the race read.

## Pace selection — current state, and two lessons from the window→ranking switch

**Current**: selection is a **ranking** — `VehicleSelector.SelectClosestByPace` does one pool pass, sorts by `|pace − target|` and takes the closest N (shuffled for ties). The bracket, the widen loop (`Options.WidenBracketFill`), `PowerBracketScale` and `VehicleSelector.Select` (plus its never-called `CreateDuplicate`) are deleted; a stale `PaceBracket`/`WidenBracketFill` key is never read, because `LoadSettings` walks the `DebugToggles` **dictionary**, not the enum. `Pace Offset` is a fixed signed integer list; Relative resolves `playerPace + offset` **once per `InstanceGrid`** into a local, and must never be written back into `PowerTargetScale` — that write-back corrupts the persisted absolute target. Pace Mode alone decides the anchor for every grid; `ComputePlayerCarPaceIndex` is gone with the join override. The b845170-era wording is in git at `b845170` if ever needed.

**Lesson 1 — clamping an anchor is inert for a ranking.** Clamping into `[min,max]` cannot change a distance *ordering*: every candidate's pace lies inside the span by construction, so the sequence is identical. The fleet-span clamps were load-bearing only for a **fixed-width window**, so they were removed with it. The single surviving span use is a diagnostic log when the anchor sits outside the fleet.

**Lesson 2 — the switch inverted non-finite-pace handling.** A window *excluded* non-finite paces; `OrderBy` over a ranking sorts **NaN first**, so a NaN score would have been preferred — the opposite of before. Root cause: `BuildPaceIndex` filtered grip and mph but **not** `accel`. The computed score is now validated before entering `ModelPaceIndexCache`.

**Electric detection — a real bug found and fixed (`96f5a72`)**: this file used to record `GET_IS_VEHICLE_ELECTRIC` as `0xD839450756ED5A80`. That hash **is not a native at all** (not in SHVDN2's `Hash` enum, no member name contains "ELECTRIC"), and calling it returned non-zero for *every* model, so `ModelElectricCache` flagged all 488 cars as electric and the correction was silently applied **to the whole fleet**. The real native is `0x1FCB07FE230B6639`, model-hash based, build 3258+; verified in game: 19 electrics. **A native hash nobody has verified in game is a guess, and a wrong one fails silently and plausibly.** **Follow-up**: `96f5a72` repointed only the *selection* path — `Racer.Initialize` and the player-pace fallback kept calling the bad hash, so spawn-time pace over-applied the bonus while the grid was ranked on the corrected flag. `Racer` now reads `ModelElectricCache`, the fallback calls `ARS.IsElectricModel`; the bad hash appears nowhere in `src`.

## Settings folder — declared inventory + repair (`3fa7737`, `0fd4e0a`)

`src\SettingsRepair.cs` is the inventory: which ini files ARS expects, which keys each must hold, and what a healthy value looks like. Three passes run from `LoadSettings`, in an order that is load-bearing:

1. `CreateMissingFiles()` — first, before anything reads a store. Creates `Settings\` and moves `DevSettings.ini` to its legacy migration name when necessary.
2. `PruneOwnedFiles()` — still before any store reads its file, so no cached `ScriptSettings` object exists that could later `Save()` a pruned key back. Line-level filter: inside `[MENU]`, a `key = value` line survives only if the schema declares the key; every other line is preserved verbatim. Rewrite goes through a temp file + `File.Replace`.
3. `CompleteOwnedKeys(...)` — last, **after** the legacy migrations and the `LoadSettings` reads. Fills missing keys with declared defaults and normalises rejected values, through the `MenuSettings` API (`Get(key, null)` is a side-effect-free existence probe — `SeedIfMissing` returns early when the fallback is null).

**Ownership rule** — `Menu-*.ini` are the only active settings files and the schema owns them outright. `Settings.ini`, `Options.ini`, `DevSettings.ini`, `DevConfig.ini`, and `MemoryOffsets.ini` are retired: the remaining migratable values are copied into the menu stores, then all are deleted.

**Invariant: a created file holds exactly the values the code would use if the key were absent**, so creating one cannot change behaviour. That is why `Track` and `PaceTarget` are declared *optional* (no default): absence is meaningful for both (an absent `PaceTarget` triggers the fleet-span middle autoselect in `RefreshPowerControls`).

**Value policy**: `Bool` and plain numbers must parse (garbage → declared default); a number with a domain list (`TimeoutSeconds`, `TcsSlipLimitPct`) **snaps to the nearest offered value**; list-backed strings (`GridSorting`, `RubberbandMode`, `PaceMode`) must match a spelling exactly, a case-only difference is rewritten to canonical, anything else resets; `GridSize` is range-clamped. Optional keys are handled by the prune pass: a declared **numeric** key that does not hold a finite number has its line dropped. That rule exists because of a defect caught in-game (`0fd4e0a`): seed-on-read wrote the sentinel `PaceTarget = NaN`, defeating the "absent → middle of span" branch. **Gotcha: never hand a non-value sentinel (NaN) to a seeding getter as its fallback; probe with `MenuSettings.TryGetFloat` (non-seeding) when absence is meaningful.**
**Gotcha: a missing key is written from the seeding static, not the schema default** — the getters run before `CompleteOwnedKeys`, and only keys no getter seeded are filled from the schema. Every static/together pair must therefore move by hand; nothing checks that a C# default still equals its `KeySpec`, and the settings checker only validates a declared value against its own domain.

## Menu structure and items

**LemonUI SHVDN2** replaces the hand-drawn menu (reference dll deployed beside `ARS.dll`); every menu is built in `InitializeMenu`.

- **Only a 10-row window is ever drawn** (`NativeMenu.maxItems`, LemonUI 1.5.2's default, never overridden): `Draw` iterates `visibleItems` = `[firstItem, firstItem + 10)`, and `Add` appends — so an item added **at runtime lands below the fold** and reads as "it didn't work" until scrolled into view (the Race menu is 12 rows with the spawn items, 10 without).
- **Assigning `SelectedIndex` fires `ItemChanged`** — so a handler that touches *other* menu items must not run before those items exist: building Grid PI Mode above the two PI items it rewrites threw a constructor NRE that stopped the script loading (`9b8da25`).
- **A submenu needs two registrations, not one.** `_arsMenu.AddSubMenu(x)` is only the navigation edge; every submenu is also added to the `ObjectPool` individually (`_menuPool.Add(x)`) at the end of `InitializeMenu`, and one that is missing there is linked but never processed — it opens and draws **with no items at all**, which reads exactly like an empty menu rather than a missing registration (the Development menu, `7bd6a77`).
- **Root (`ARS`)** = eight submenus in frequency order — **Race, Rivals, Race Rules, Interface, Controls, Debug, Development, Track Creator** — plus **Reset To Track** as its last child, nine rows inside the window. Reset stays at the root because Race would reach 13 rows with staged spawns on, and it is **enabled only while a race is running** (`ARS.RaceIsRunning`, the same gate the HUD and the nitrous top-ups read, refreshed on `_arsMenu.Shown`) — outside a race there is nothing to reset onto, so LemonUI draws the row disabled; **Start Race is a Race item, not a root one**.
- **Race**: track selection, Laps, **Reverse Route** (`Menu-Race.ini`), **Load Track** (after Laps), grid size, the **PI Settings** submenu — Grid PI Mode above PI Offset, then PI Target, then Max PI Deviation — **Build Grid** (after the submenu, before Start Race), Start Race, **Restart Race** (same racers when `PlayerParticipating`, else a fresh grid via `StartRaceFromMenu`), End Race. **The two staged rows are six slots apart by design, not a pair, and both vanish while Show Track & Grid Rows is off.**
- **The rest of the tree**, each level sorted by one criterion: at the root, the occasion (race now / rivals are off / a rule for good / what I see / the mod's keys / something is broken / authoring); inside a menu, the subject. **Rivals** = roster and looks (Car Roster, Grid Sorting, Repeat Cars To Fill Grid, Auto Styling, Menyoo Skins) plus three behaviour submenus, **Rival Pace**, **Rival Traction** and **Rival Steering**. **Race Rules** = Timeout, Racer Autofix, Hide DNFs, Rubberbanding, Rubberband Mode, No Collision, Nitrous, Online Downforce Curve. **Interface** = Racing Tips, the show toggles, Show Track & Grid Rows, Freecam. **Controls** = Hotkeys, Menu Modifier, Menu Key. General Settings, Advanced Settings and the one-item Other menu are gone, and the old Settings container (which held no items of its own) with them.
- **Freecam (Interface)** — it **borrows the player's own camera view, so `Toggle()` must put it back** — activation forces `SET_FOLLOW_PED_CAM_VIEW_MODE` 4 (first person) with the ped made invisible/no-collision/no-gravity; deactivation restores a `GET_FOLLOW_PED_CAM_VIEW_MODE` captured on entry. Restoring a *captured* mode (not a "third person" constant) is deliberate — entering while already in first person must leave the player in first person. Opens via the configured virtual-key chord (Left Shift + E by default, while Hotkeys is enabled) or `arsmenu`, only when nothing else is visible.

## Grid pace selection — pace score, electrics and PI ballpark

- **Pace score** (`ModelPaceIndexCache` + `ComputePaceIndex`): a raw per-model score, **not** 0–1 (`topSpeedMph + cornerSpeedMph + effectiveAccel × k`, three terms sized to a 50/30/20 split by `f3fc274`; the old normalized/ceiling/weights consts were dead code, removed). **Electrics** are flagged live at table-build time by `GET_IS_VEHICLE_ELECTRIC` (model-hash native, build 3258+, probed once) and their raw G is scored at the **peak of the game's own drive-force ramp** — with **no top-speed discount** (the old code misread the ramp's endpoint as one *and* used a hash that flagged all 488 cars as electric). **`f3fc274` replaced the ×2.95 midpoint that `96f5a72` had driver-verified with the ramp's peak — measured, not assumed: the four fastest electrics (tezeract, virtue, suzume, X-treme) score above the fastest ICE model in the fleet, the rest sit 20-70 PI above their class's ICE median, so the fast electrics are effectively unselectable against an ICE-based target — deliberately left that way.** Class membership must not influence an electric's treatment (`3d589d6`, user decision) — the slow electrics R* classes as Super are simply mis-classed. ## Gs-aware preview steering (lane error blend)

**This design is LIVE again** — the authority chain containing it was restored from `1f4516d`. The notes describe what is actually executing, not history.
- Nose-aimed steering measures lane error at the car, but at speed centrifugal force (already measured by `ProjectAhead`) curves the real path, so it overshoots. The lane error in `ComputeSteering` is therefore blended (at the car) with the **0.5 s Gs-aware projection** (`LookAhead.HalfSec` + `ProjectAhead(0.5f)`, a hardcoded local half-and-half — no knob); the **1 s** slice is the off-track cap's read, not this one.
- **Lane steer conversion (proportional, `b333dc4`)**: lane error (metres) → steer angle by a **flat degrees-per-metre gain with no ceiling**, halved when heading to the outside of a tight curve — a two-value step, **not** a speed-scaled clamp. The old `atan2(laneError, lookahead)` is gone (its gain shrank exactly when speed rose or grip fell). A NaN guard sits before the clamp. `LaneGainExponent` is a dead field — declared, never read, in no ini.
- **Physical repulsion** (velocity-oriented box, separate from walls): inside it, react only to rivals **actually closing laterally** and **add** a steer-away term to the lane steer — never overwrite it (overwriting broke the lane steer: parallel traffic made the sign filter coin-flip and replaced the bias with ~0). Magnitude scales with closing speed × distance.
- The projection read is one frame stale by design (`RunTimedCore` runs before `ProcessTick` refreshes `AccelerationVector`) — same staleness all projection consumers accept.

## Corner outside approach — the release window

- **The release is a flat time before the entrance, not a width-scaled one.** `ComputeCornerLane` gates the hold on `timeToEntrance`, and the window is `[OutsideReleaseSeconds, OutsideReleaseSeconds + 3 s]` — the outside phase is always 3 s long and retuning the release **shifts** the whole phase rather than lengthening it. `timeToEntrance = fwdToEntrance / max(speedMps, 1f)`, where `fwdToEntrance` is a **node count** (treated as metres, modulo-wrapped on circuits).
- **Driven: 0.5 s let go too late to help the apex; 1.05 s has the cars touching the apex better** (driver-verified), which is why the value moved.
- **The current-speed divisor makes it release early under braking, never late** — the car always has slightly *more* than the nominal time left (the safe direction); dividing by a predicted entrance speed is the fix if it ever reads short.
- **A separate hard kill at `fwdToEntrance <= 2` clears the latch**, so a released hold cannot re-engage mid-corner. It beats the time gate only at crawl speed, a backstop rather than the normal release.
- **`OutsideReleaseSeconds` is a `static float` with no writer** — effectively a constant, left mutable; not a menu item and not a save key.
- The entrance is the corner's own: `c.StartNode` when the track file supplies it, else `apexNode - c.LengthStart`. Returning `0f` means *no override* — the caller keeps the lean's answer, and the car's own lane when that has none (`Racer.cs:413-417`).

## Steer-In Bias — the deliberate skew on the steer ceiling

- **The one knob that is knowingly not physics.** The ceiling is computed 1:1 (vanilla curve vs Ackermann, whichever is lower) and then **Steer-In Bias** adds a fixed number of degrees, floored at half the geometry and clamped to the car's lock (`Racer.cs`, `ApplySteerLimits`).
- **It is additive, not multiplicative, and that choice is the whole design**: a multiplier's absolute effect is largest at low speed and negligible at speed — the opposite of what "steer in" needs; an additive bias applies the same degrees everywhere, so it is proportionally largest exactly where the ceiling is smallest (at speed). Driven and kept in the positive direction; the negative half saturates against the floor above ~70 mph.
- **The floor is not optional**: `geometry + bias` can go negative at speed (which would invert the clamp), and even exactly zero is a car that physically cannot steer — so the result is held at **half the geometry**.
- **Wiring is the `SteerDampingScale` pattern, four places**: the static in `AutosportRacingSystem.cs` assigned in the item's own `ItemChanged` (a `Racer`-read static must be, or the save only lands on restart), `SaveRacerSetting` into `Menu-Settings.ini`, the `LoadSettings` read, and the `SettingsRepair` `KeySpec`. A numeric key **snaps an out-of-range stored value to the nearest offer**, so a hand-edited value cannot survive a load.
- **The range is deliberately not recorded here** — it is a tuned value; the options array and the `KeySpec` are the source of truth.

## Logging — levels, and why `None` is the default

- `LogImportance` is a **floor**, not a switch: `Log()` returns when `LogLevel > i`. `None` is deliberately the **last (highest) enum member**, so it silences every level through that same test with no second branch; the **shipped default** is `Error` (code static *and* `SettingsRepair` KeySpec), so a fresh install records errors without the Info chatter. Levels persist by **name**, so adding a member renumbers nothing.
- **The session banner** (truncate + separator) is written in the ctor **before `LoadSettings`**, so it cannot consult the stored level — 2 writes a session; it also stops a stale log reading as current evidence.
- **`forced: true` calls** — all error paths: settings repair, model and ped load failures, the `OnTick` catch, the bridge probe. Keeping those is the whole reason `None` is a floor rather than a hard kill — `VerifyScriptBridge` runs *before* `LoadSettings`, so a suppressed forced line would make a bad SHVDN asi/dll pairing completely silent in our log. That is why the release README's "the log names the reason" stays true under the default.
- Verified in game: with `None` the live `Log.log` is exactly the two banner lines plus the single forced `Initialization complete.` line.

## Crash triage — Rockstar writes the dump, and this install has a recurring crash

**Rockstar's own handler captures a game crash, so there is a record even when Windows reports nothing.** A crash writes a minidump plus a context file to `%LOCALAPPDATA%\Rockstar Games\GTAV\CrashLogs\`:

- `<guid>.dmp` — a **user minidump**. Its structures are readable without a debugger: the **exception stream** gives the exception code, faulting address, faulting thread id and — for an access violation — `ExceptionInformation[0]` = read(0)/write(1)/execute(8) and `[1]` = the address touched; the **module list** resolves that address to module+offset; each thread's **stack range** is in the file, so scanning it for pointers into module ranges gives a crude backtrace. The Windows Application log stays **silent** for these (no `Application Error`, no WER, no `%LOCALAPPDATA%\CrashDumps` entry) — a missing WER event is not evidence that nothing crashed.
- `crashcontext.log` — the **last** crash only (overwritten), with game state at the crash. Useful for "what was the session doing", useless for older crashes.

**A real unwind needs a debugger, and the CLI is one install away**: `winget install Microsoft.WinDbg` registers `cdbX64.exe` (classic engine, runs headless) in `%LOCALAPPDATA%\Microsoft\WindowsApps` — where to look when it is installed but not on `PATH`. `cdbX64.exe -z <dump> -y "" -c ".ecxr; k; !analyze -v; q"` gives the faulting instruction with operands, the properly unwound stack, and the `AV.Type` / `WRITE_ADDRESS` / `FAILURE_BUCKET_ID` verdicts. `GTA5.exe` has no public symbols, so a game offset **cannot be resolved to a function name** — module+offset and the call chain's offsets are the fingerprint; the bucket reads `INVALID_POINTER_WRITE_c0000005_GTA5.exe!Unknown` for game-side null writes.

**This install's recurring crash (three occurrences, one signature).** `GTA5+0x652263`, `mov byte ptr [rdx+rcx+10h],al` with `rcx = rdx = 0` — a **one-byte write to address 0x10, i.e. into a null object's field** — from a thread rooted at `kernel32!BaseThreadInitThunk`. The unwind is **18 frames, every one `GTA5`** (no mod module, not JIT-managed code), byte-identical across all three: `0x652263 → 0x63c7e3 → 0x638fab → 0x6416cc → 0x168e909 → 0x16946c4 → 0x169b630 → 0x169b7be → 0x16a2de5 → 0x8157dc → 0x1687bad → 0x168739f → 0x28574 → 0x21c4b → 0x1686fa8 → 0x13cc → 0x1344e07 → 0x187f5d0`. Only the ASLR slide differs. Sessions: **08-15, 09-04 and 09-19**, all with `ARS.dll`, `LemonUI.SHVDN2.dll`, `NativeUI.DLL`, `TrainerV.asi`, `RTHandlingEditor.asi` and `HandlingReplacement.asi` loaded (the newest session additionally carried `HandlingIsolation.dll`, `HandlingIsolationDemo.dll`, `ModManager.*` and `NewChaseCam.dll`, so those are not its cause either).

**What that fingerprint does and does not settle.** It **exonerates any change made after 09-04** — the same crash predates it by five weeks: compare the faulting instruction *and* the call chain against older dumps rather than reasoning about coincidence. It does **not** exonerate the mods present in all three sessions, ARS included: a deterministic null write in game code is the usual shape of the game reacting to an entity a script deleted or invalidated (the `*Delete()` / teardown / script-reload lifecycle) — if it needs chasing, the repro candidates are a **scripts reload mid-race** and the **race-end entity cleanup**, not the raw memory writes. Other crash modes in the same folder: `0xE0434352` (a CLR exception faulting in `KERNELBASE.dll`, four occurrences) and `0x80000003` (int3 breakpoints, five in one 09-12 session — hooking/debug tooling, not a game fault).

**A second signature, measured 10-13: the sideloader's packed `vsl` aggregate, and the script domain is not in the window.** Five loads died 32–38 s in, before the player existed (`crashcontext.log`: player position 0,0,0, health 0, peds 0/256, camera at the void), at `GTA5+0x6057E1` — `call qword ptr [rax+38h]` on a garbage `rax` — with the chain `GTA5+0x642c7b → TrainerV+0x130a58 → GTA5+0x6057E1`, byte-identical across them, so the trainer frame is incidental. Three bisect states separate cause from coincidence: both opt-ins off (stock) **boots**; `enable.overlay` alone with loose off **crashes identically**; overlay with `dlcpacks:/vsl/` removed from the served `update.rpf`'s `dlclist.xml` **boots**. It is therefore the aggregate's packed content, not `VSLooseStream`, not the loose tree, not ARS — and VSideloader's `VSLOOSE_NOTES.md` had already bisected this address to the packed lineup. **On the booting run SHVDN and ARS initialized at +88 s**, fifty seconds after the crashes land, so no C# script had loaded in any crashing session: a stale `ScriptHookVDotNet.log` here is proof the crash precedes the domain, not a hint that a script caused it.

**Possible misleading load failure — an external USB hard disk (observed once, not reproduced).** With a plain external HDD connected, GTA5 launched straight into a fatal `ERR_GFX_D3D_SWAPCHAIN_ALLOC_2` dialog and stopped responding; disconnecting the disk made the game load. WER already held earlier `AppHang_GTA5.exe` (`AppHangB1`) entries, so the condition is neither new nor ours — but the disk stays a **possible** cause, not a rule, until reconnecting brings the failure back. The trap is the error's name: it points at the DXGI swapchain and steers diagnosis to D3D/DXVK/display, while the hang it reports is a stalled main thread — the shape a slow or failing disk produces while the game enumerates drives at startup.

**Clearing the C# mods for a pre-script load failure is cheap and decisive.** On the failing launches `ScriptHookVDotNet.log` stayed stale while `ScriptHookV.log` and `asiloader.log` were rewritten, so the .NET script domain never started and no SHVDN script ran — ARS included. Establish the load order before reasoning about whether a recent change caused it.

## Vehicle memory layer — one implementation, memoized scans

- **`VehicleMemory.cs` owns every offset and every pattern scan.** The four control-struct setters, the handling-struct readers and the shared AOB scanner all live there, and `Racer` calls nothing else. `ARS.SetThrottle` was the only write path in the codebase with **no `CanWeUse` guard**, dereferencing `handle.MemoryAddress` unchecked — the exact shape of the `NullReferenceException` a ScriptHookVDotNet maintainer reported against the tracker's issue #8 after a game update moved the pattern.
- **The scanner is memoized, and that is the load-bearing part.** `FindPattern` caches per `pattern|mask` in a static dictionary (sound because the module base cannot move inside a game process). Before, an **unmatched** pattern bought a full module walk *on every call*, and every caller is per-tick and per-car — on a build where the pattern moved, that would have presented as a **frozen game** rather than "the brakes don't work". The cache reduces a miss to a dictionary lookup, so the failure mode is degradation instead of a hang.
- **Two misses report once, and forced** (`LogImportance.Error` with `forced: true`, so Log Level `None` cannot hide them): the control pattern (*"ARS cannot drive the cars"*) and the handling pattern (*"grip, steering lock, downforce and handling flags all read as zero"*), both naming `Game.Version`. Every other pattern miss stays at `Info` on purpose — the wheel-power pattern has a documented `0x1D8` fallback.

## Randomness helpers — the exclusive max, and what it silently costs

- **`ARS.GetRandomInt` is `Random.Next`, so its `max` is EXCLUSIVE.** An *index* bound written `Length - 1` loses the last element for good — that is how Steel Gray in `_randomColors`, the last matching Menyoo tuning file and the last `StreetRacerModels` ped were unreachable, while index bounds written as the length itself, and every *jitter range* (`(10, 50)`, `(0, 500)`), are correct as they stand. The helper now says so where it is declared — check that, not the call sites, before "fixing" a `-1`.
- **The sweep above missed five more sites, all in `SmartTuner`** (`9517976`): the style pick, the chosen group's livery options, `veh.SetMod(slot, random(0, count))`, the palette pick and the matte pick each passed `Count - 1`. They now pass the length — when this trap is next suspected, grep **every** `random(0,` call site rather than trusting the list here.
- **The shuffle idiom is `random(0, i + 1)`**: `Tips.cs` and `GridBuilder.cs` have it right, and `VehicleSelector.Shuffle` was a character short — passing `i` gives Sattolo's algorithm (uniform over *cycles*), so a shuffled list could never keep its own order and a two-item list always reversed. **One off-by-one of this family is deliberately left in place**: the tip roll is `GetRandomInt(1, Denominator)` — a rate, not an index, so fixing it is a tuning decision rather than a bug fix (the `9517976` audit changed it to `Denominator + 1` and the change was reverted).

## Cross-session hindsight notes

- **`TrackLoader` sets `Thread.CurrentThread.CurrentCulture = en-US` and never restores it**, so every later `ToString`/`TryParse` on the game thread is silently reformatted — and the track files already carry several incompatible culture conventions. Same family: `TrackFile`'s `int.TryParse(float.ToString())` truncates fractional widths and writes 0 with no else branch.
- **Crest handling has a sign and a home.** `CrestGs` negative = crest / positive = dip; the crest multiplier belongs on the grip-limited decel base, not the grade term, and a positive value must be discarded before the floor. The behind-guard is the **extent test**, not the sign of `toCrest` (`CrestDecelFactor` `Racer.cs:3194` bails when the whole ramp is behind the car) — a car still inside the crest's extent keeps the portion ahead of it, which a bare `toCrest < 0` guard would wrongly drop. The earlier note calling this a point-to-point bug is retired.
- **The brake learner's full-pedal threshold sits above the downshift gate, so its own target pushes the car into engine braking it cannot see.** Separately, `Corner.SecondsToEntrance` is declared and never assigned (dead field); the real value is computed locally in `ComputeCornerLane`.
- **DXVK/AMD startup hang can dead-end the game before SHVDN hosts anything.** The DXVK fail-fast shows up in the Windows `Application Hang 1002` log with a 3–6 second kill window; `ScriptHookVDotNet.log` is *not* updated, so SHVDN's v2 script domain never came up and ARS was never attempted — the guard error is upstream of ARS, not its cause. Stack on this install at the failure window: DXVK `v2.4.1` over `d3d11.dll` / `d3d8.dll` / `d3d10core.dll` / `dxgi.dll` (all 9/26/2024) plus the `VSAssetWatch.asi` / `VSOverlay.asi` / `VSLooseStream.asi` overlay trio (`VSAssetWatch.log` grows to ~141 MB on this machine) on a `Radeon RX Vega` with the AMD `2.0.279` proprietary driver. **Recovery is a clean second launch** — same scripts folder, same deployed `ARS.dll`, no rebuild. When this hits, do **not** touch `bin\Release\ARS.dll` or restart SHVDN; rerun the launcher and check `Log.log` for `Initialization complete.` to confirm ARS came up.

## Sideloaded fleet handling

- **The grid's cars are custom and their handling is sideloaded, not in the game's own meta**: `VSLooseStream.asi` mounts loose FiveM-style resources from `Sideload\`, each declaring `data_file 'HANDLING_FILE'`. **ARS reads the live `CHandlingData` from memory, never these files** (`VehicleMemory.cs`), and it reads the per-racer handling values once per racer at racer init, so a mid-session edit moves the car without moving those reads.
- **`Sideload\0_vsl-handling\handling.meta` is the file of record and the only declaration of these names** — the per-car copies were emptied to stubs, their contents kept beside them as `*.bak-vslpriority` and **never to be restored**: while those duplicates existed, boot could serve a stale generation of the shared file. It is a **hand-balancing** surface, judged by driving rather than by ARS — tuned at LSIA, settled at NURBGP. **Its `<strHandlingFlags>` is a numeric hex string parsed straight into `hFlags`** (`handlingMgr.cpp:1699`), and nearly every car sets `TYRES_CAN_CLIP`, which *raises* the wheel's compression cap so the tyre sinks into the ground when bottoming out (`wheel.cpp:1359–1367`) — so a car that looks sunk or clips is a per-model flag, never a player-vs-AI difference (`AGENTS-VANILLA-STEERING.md`).

## Grid car selection (pace-matched)

- **Model stat natives need an int hash, not a spawned handle** — that is what makes pre-race evaluation free, with no car in existence. The spawned-handle natives are *different functions*, so don't mix them up; the hash table is in this file.
- **The roster is one flat hand-editable file** — `Scripts\AutosportRacingSystem\Vehicles\cars.txt`, one model key per line, `#` comments ignored (`VehicleCatalog.cs:17`). `BuildPowerCache` (`AutosportRacingSystem.cs:447`) hashes each line and **rewrites the pool in place to canonical hash-string keys**, which every consumer is keyed by; the `arsbuild*` cheats only *append* and refresh the roster live.
- **Threading contract**: the load thread only *discovers* the pool by pure file I/O, while `BuildPowerCache` reads the natives on the **main thread**. **Calling GTA natives on the background thread hard-crashes the game.**
- **Pace score (`AutosportRacingSystem.cs:93`) is a raw per-model number, not 0–1**, and the leaderboard prefix is the same metric the grid ranks by. Electric models are scored at the **peak** of the game's own drive-force ramp — `f3fc274` replaced the driver-verified ×2.95 midpoint — with the flag from a verified native.
- **Selection (`VehicleSelector.cs:12`) is a ranking, not a window** — one pool pass ranks every paced model by distance from the target, takes the closest N with a shuffled tie-break, and returns model keys without touching a file. `SelectHardcoded` (`VehicleSelector.cs:42`) is the full-roster test bypass.
- **Repeat Cars To Fill Grid (Rivals, `ForceFillGrid`) recycles the models that actually spawned, round-robin, until the grid target is met** (`AutosportRacingSystem.cs:3657`) — a one-car pool like `tests.txt` fields a full grid of it, and a model that spawned nobody is never retried, so a broken roster line costs its load wait once.
- **Grid slots are built to order and the count must include the player.** `BuildGridSlots` (`TrackLoader.cs:588`) runs again for `Racers.Count` right before `GridBuilder.Place` (`GridBuilder.cs:17`) because `Place` reads **two slots past each car**, and `AddPlayerToGrid` (`AutosportRacingSystem.cs:1920`) adds the player *after* the grid was sized — `470a1a1` shipped exactly that crash.
- **Pace Mode is the sole authority on the anchor (`759a36a`)**: Relative resolves from the player's pace, Absolute from the persisted target, and **every** start path resolves from the mode with no override of its own. `PowerTargetScale` has exactly two writers — its own menu item and `RefreshPowerControls` (`AutosportRacingSystem.cs:1236`).
- **Menu vocabulary**: the items are `Grid PI Mode` / `PI Offset` / `PI Target` / `Max PI Deviation`, all four inside the **PI Settings** submenu, while keys and code keep the name pace. **`PaceTarget` is a seed, not a preference** — `RefreshPowerControls` clamps it to the live fleet span on every menu build and saves the result, so do not reconcile a live-vs-Dist difference in it.
- **A menu description carries only what the name and the visible options cannot** (user-stated): a hidden rule, an exclusion, the unit, or which way to turn the dial. Never restate the label or enumerate the options — the player can already read both in front of them.
- **Max PI Deviation** (`PaceDeviation`) filters the pool before the ranking in `VehicleSelector.SelectClosestByPace`, on `|round(pace) - round(target)| <= limit`, so the window matches the PI a player reads and it holds in both PI modes because it measures the resolved target. Off is the shipped default; a pool thinner than the window yields a short grid, which Repeat Cars To Fill Grid then fills with repeats, and the `HardcodedRoster` test bypass ignores the limit.

  overwritten by the next build with no warning, so a change that has to survive is made at the source and mirrored, never the reverse.
- **SHVDN `ScriptSettings` quirk**: `Load` never returns `null` (a fresh empty object), and `Save` creates the file via `File.CreateText`, so a deleted file regenerates on the next write. Booleans are `True`/`False`, parsed case-insensitively.
- **LemonUI SHVDN2** replaces the hand-drawn menu; every menu is built in `InitializeMenu` (`AutosportRacingSystem.cs:618`). Three invariants: **only a 10-row window is drawn** (`NativeMenu.maxItems`, never overridden) so an item added at runtime lands below the fold and reads as "it didn't work"; **assigning `SelectedIndex` fires `ItemChanged`** so a handler must not touch items that don't exist yet (`9b8da25`); and the two staged rows sit six slots apart in Race, hidden while Show Track & Grid Rows is off.
- **LemonUI ships with the release** (`libs\LemonUI.SHVDN2.dll`, MIT, author's permission; 1.5.2 is the last v2-API release) and is staged **by name** in `deploy.yml`. The API dll is deliberately the opposite case, so never replace that line with a `bin\Release\*` wildcard (`AGENTS-SHVDN.md`).

## Durable gotchas — code, helpers, rendering, settings

**Trigger**: inverted gate, De Morgan, negated filter, early continue, Remap, NaN, dead null-check, OnTick pause, positional Options enum, `DrawMarker` budget, marker rotation and pitch, prop `RightVector`, streaming ptfx, **a setting ignored until reload, a settings read on a tick path, a cached value that disagrees with the ini**.

- **`if (1 == 2) return;` is an INVERTED gate — it disables nothing**, because the return only fires when the condition is true and it never is. Correct idioms are a bare `return;` or the block form; this bit the start-line flare disable (`bdd1b29`) for weeks.
- **Remap with a descending output range + `clamp=true` is inverted** by `Clamp` when `min > max`, and NaN compares less-than-anything. Keep output clamps ascending and use a descending *input* range for a reversed map.
- **NaN discipline**: `Clamp(NaN, -limit, +limit)` returns the min bound, i.e. instant full-lock — guard steering outputs and any clamp input that can be non-finite. Never hand a non-value sentinel to a *seeding* getter either, or it writes the sentinel into the ini.
- **An early-continue guard is the accept filter negated, so De Morgan inverts its NaN case**: `!(A && B)` is `!A || !B`, and a NaN makes every comparison false — the filter `Distance <= 30f && Gap < 0f` drops a NaN rival, while its rewritten guard `Distance > 30f || Gap >= 0f` does not fire and passes it. Rewriting a `Where` into a loop keeps the positive accept form (`bool closes = ...; if (!closes) continue;`) (`Racer.cs` card scans, `601313c`).
- **A null-check on a freshly `new`-ed object is dead code.** Two "cannot find file" popups lived behind `if (new XmlDocument() == null)` while the real failures *throw*, so those paths have **no** error handling.
- Synchronous setup work can pause `OnTick` and temporarily suppress per-frame debug visuals; make it incremental if that matters.
- **`Options` enum values are positional**, so retiring a member renumbers the rest and one must never be persisted or exchanged as an int. Nothing does today, but re-check before any numeric consumer appears.
- **`World.DrawMarker` has a per-frame render budget**: markers past it are **silently not drawn** and draw order decides who loses, so long debug geometry belongs in `DRAW_LINE` instead. The budget is shared with every other marker the script draws that frame, so a visual can break because something *else* got greedy.
- **A marker's rotation vector collapses at a 90° middle slot**: with the middle component at 90 — the value that lies a chevron flat — the first slot yaws and the last two roll in opposite senses, so **no single slot can pitch it**, however many are tried. Pitch a marker by tilting the `direction` vector it faces along and leave the rotation at the flat pointing configuration (the input trail's chevrons, `6111f6c`).
- **Two traps the flare rebuild exposed, both reusable**: a prop's own `RightVector` is perpendicular to *that prop's* forward, so an offset applied after its heading is turned 90° comes out parallel to the track — offset from the source direction instead; and a **named ptfx asset streams between frames**, so requesting it in a same-frame loop can never succeed — queue the entity and attach it from a tick (`TrackLoader.TickQueuedFlares`), logging a failed start rather than swallowing it.
- **A cached settings field is only as fresh as its writers — suspect the cache before the key.** `ARS.Autofix` became a plain field in `f0df8a3` (dev build 628): seeded in `LoadSettings` after its legacy `0`/`1`/`2` migration, assigned by the menu handler, and read by the spawn-time damage-proof block (`Racer.cs:413`) and the per-tick repair gate (`:3657`). The symptoms it can produce are narrow: the Racer Autofix choice not taking effect, reverting to `Invincible`, or disagreeing between the menu and the cars' damage handling, and an ini edited by hand mid-session no longer reaching it at all. The analysis is two questions — is the field assigned on the path that changed the value, and is it seeded before `InitializeMenu` builds the item, whose order in the constructor is `LoadSettings` then `InitializeMenu`. The reverse symptom is why the change exists: a store read on a tick path scales with cars × frames, so a repeated "declares no key" line or a per-tick stall means a value that belongs in a field is still being fetched. Any new writer of a cached key must assign its field.
- **LemonUI's `Items` setter reads `Items[index]` as it lands, with no clamp**, so replacing a populated list while the selected index sits past the new end throws inside the setter — park the index on a valid entry first, as `RefreshCarPoolItem` does (`AutosportRacingSystem.cs:538-544`, with the comment saying exactly this). `RefreshTrackList` (`:1492`) does **not** park it, and `SelectedIndex = 0` on an emptied list throws `'There are no available items.'`, so both orders of the hazard are live there; the fix is filed as `track-list-index-throw`. The related facts — the setter's unclamped read, the event firing for a programmatic assignment, and the three throw messages — are in the per-menu persistence section.
